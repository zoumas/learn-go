# Chapter 5: Structs

## 5.1 Structs in Go

- A struct's zero value has every field set to its zero value, so `var m messageToSend` is ready to use. Measured: `%v` prints `{0 }`, `%+v` prints `{phoneNumber:0 message:}`, and `%#v` prints `main.messageToSend{phoneNumber:0, message:""}`. Use `%+v` in log lines so that an empty string field stays visible.
- A struct whose fields are all comparable is comparable with `==`. Measured: two `messageToSend{1, "x"}` values compare equal. Such a struct can also be a map key.
- Size is the sum of the fields plus alignment padding. Measured on amd64: `messageToSend` is 24 bytes (8 for `int`, 16 for the string header). The lesson's `car` is 48 bytes. Field order affects padding when small and large fields are mixed.
- `int` is 32 bits on 32-bit targets. The course's test cases use `148255510981`, which needs more than 32 bits. Measured: `GOARCH=arm GOARM=7 go vet ./ch05/l01` fails with `cannot use 148255510981 (untyped int constant) as int value in struct literal (overflows)`. On an ARMv7 gateway, use `int64` for any value that can pass 2^31.
- In production, a phone number is a `string`, usually in E.164 form (`+30697...`). An integer drops the `+` and any leading zero, and it allows arithmetic that has no meaning. A literal with a leading zero is octal in Go. Measured: `0030697123456` fails with `invalid digit '9' in octal literal`.

## 5.2 Nested Structs in Go

- A nested struct field is a value, not a pointer. Its zero value is a usable `user{}`, so `m.sender.name = "a"` on a zero `messageToSend` needs no allocation and cannot panic. Measured: `messageToSend` is 64 bytes on amd64 (16 for the string header and 24 for each `user`), and the whole value is copied when passed to `canSendMessage`.
- The solution uses a local closure, `isValidUser`, so the check is written once for sender and recipient. It costs nothing. Measured with `go test -gcflags=-m`: `can inline canSendMessage.func1`, `inlining call to canSendMessage.func1` at both call sites, and `mToSend does not escape`. Compare 4.16, where a closure that escaped moved its variable to the heap. The usual home for this check is a method, `func (u user) valid() bool`, which a later lesson introduces.
- `u != user{}` is not the same check. It is true when any field is set, and the spec needs every field set. Measured: `user{name: "x"} != user{}` is `true`, but that user has no number.
- In production, validation returns an `error` that names the missing field, not a `bool`. The caller can then log or reject with a reason, for example `errors.Join` of `recipient: missing number` and `sender: missing name`. A `bool` says only that something is wrong. The same applies to rejecting an IoT message with a missing device ID or topic.
