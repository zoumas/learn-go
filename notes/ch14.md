# Chapter 14: Mutexes

## 14.1 Mutexes in Go

- `inc` and `val` each take `sc.mu.Lock()` and `defer sc.mu.Unlock()` around the slow helper. `val` locks too, because a read that overlaps a write is still a data race. `go test -race` passes for all four cases.
- Without the locks, a normal build crashes with `fatal error: concurrent map writes`, and `-race` reports `WARNING: DATA RACE`. Both measured. The crash is a runtime fatal error, not a panic, so `recover` cannot catch it.
- The value receivers work only because `mu` is a `*sync.Mutex` and `counts` is a map. Each method call copies the struct, but the copies share the same mutex and the same map. With a `sync.Mutex` field held by value, every call would lock its own copy and nothing would be protected. `go vet` catches it: `inc passes lock by value: scratch/valmu.c contains sync.Mutex` (measured).
- Production note: the usual form is a `sync.Mutex` value field (its zero value is ready to use, so no constructor) with pointer receivers, and the mutex declared directly above the fields it guards. A pointer mutex adds a separate allocation and a nil value to forget. Keep the critical section short: here it includes `time.Sleep`, which serializes every goroutine on that sleep. In a pipeline that counts per-device messages, lock only the map update, never the I/O.

## 14.2 Why Is It Called a "mutex"?

Quiz:

1. What does the term 'mutex' refer to? **Mutual Exclusion.**

Notes:

- A mutex excludes all goroutines but one from the guarded data at a time. By convention the field is named `mu` and sits directly above the fields it guards.
- A Go mutex has no owner. One goroutine can lock it and a different goroutine can unlock it. Measured: unlocking from a second goroutine works, as the `sync.Mutex.Unlock` doc states.
- A Go mutex is not reentrant. A second `Lock` on the same goroutine blocks forever. Measured: `fatal error: all goroutines are asleep - deadlock!`. The common case is an exported method that locks and then calls another exported method that also locks. Fix: put the logic in an unexported helper that assumes the lock is held, and lock only in the exported method.

## 14.3 Mutex Review

Quiz:

1. How many goroutines can hold the same mutex lock at once? **1.**
2. Why would you use a mutex? **To safely access shared resources concurrently.**

Notes:

- The lesson says the unguarded map "can panic". It is a runtime fatal error, not a panic, so `recover` cannot catch it (14.1). Measured on 16 cores: the course's unguarded `writeLoop`/`readLoop` program stopped with `fatal error: concurrent map iteration and map write` in 3 of 3 runs. The runtime detects this only on a best-effort basis. `-race` is the reliable check.
- The course calls `Lock`/`Unlock` without `defer` inside the loops, and that is right. A `defer` in a loop runs only when the function returns, so `defer mu.Unlock()` in `writeLoop` would never release the lock, and the second `Lock` would deadlock (14.2: not reentrant). To use `defer` per iteration, move the loop body into its own function.
- `readLoop` holds the lock across the whole `range` and every `fmt.Println`, so the writer waits for terminal I/O. Production fix: copy the data under the lock, unlock, and then do the I/O on the copy. `maps.Clone` (Go 1.21) makes that copy in one call. When reads far outnumber writes, `sync.RWMutex` lets readers share the lock.

## 14.4 RW Mutex

- `val` takes `RLock`/`RUnlock` and `inc` keeps `Lock`/`Unlock`. `go test -race` passes all four cases.
- Why the course test hangs before the fix: the test calls `sc.mu.RLock()` and `defer sc.mu.RUnlock()` itself, then calls `sc.val`. The `defer` sits in a loop, so the read lock stays held until `Test` returns (14.3). A `val` that calls `Lock` then waits for that reader forever. Measured: with `Lock` in `val`, `go test -timeout 5s` ends with `panic: test timed out after 5s` in `sync.(*RWMutex).Lock`.
- The fixed version passes only because no writer is waiting. That is a recursive read lock: the test goroutine already holds `RLock` and `val` takes a second one. The `sync.RWMutex` doc forbids this. A waiting `Lock` blocks new readers, so the second `RLock` waits for the writer, and the writer waits for the first `RLock`. Measured: `RLock`, then a goroutine calls `Lock`, then `RLock` again gives `fatal error: all goroutines are asleep - deadlock!`. The course test avoids this only because `wg.Wait()` runs before it.
- Writer preference is the point of that rule. Once a writer waits, new readers queue behind it, so a constant stream of readers cannot starve the writer.
- Production note: `RLock` is not free. Every `RLock` and `RUnlock` does an atomic add on one shared `readerCount` field, so parallel readers still fight over one cache line. Measured with `b.RunParallel` around a one-key map read: with 1 CPU, `Mutex` takes 7.7 ns/op and `RLock` 7.7 ns/op. With 16 CPUs, `Mutex` takes 37.8 ns/op and `RLock` 16.9 ns/op. Reads get faster, but they do not scale linearly. `RWMutex` pays off when reads clearly outnumber writes. Benchmark your own workload before you switch. Per-device counters with many writers fit a plain `Mutex`, sharding, or `atomic.Int64` values better.

## 14.5 Read/Write Mutex Review

Quiz:

1. How many writers can access a RWMutex at once? **1.**
2. How many readers can access a RWMutex at once? **infinite.**
3. Can readers and writers lock a RWMutex at the same time? **No.**

Notes:

- "Infinite" is the course's simplification. `sync/rwmutex.go` caps readers at `rwmutexMaxReaders = 1 << 30`. `Lock` subtracts that value from `readerCount` to tell new readers that a writer is waiting. No real program comes close to the cap.
- Concurrent reads of a map with no writer are safe. Measured: 8 goroutines ranging over the same map 10,000 times each, under `-race`, report no race. A single writer anywhere makes every access need the lock.
- Writers are not starved. Measured: one writer and four goroutines that hold `RLock` in a tight loop. The writer completed 534,506 `Lock`/`Unlock` cycles in 1 s, because a waiting writer blocks new readers (14.4).
- Production note: for a map that is written once and then only read, such as config or a device lookup table loaded at startup, no lock is needed at all. Publish it before you start the readers, or swap a fresh copy through `atomic.Pointer[map[K]V]` for hot reload. `sync.Map` fits keys that are written once and read many times, or goroutines that touch disjoint keys. For everything else, the `sync.Map` doc recommends a plain map with its own lock, for better type safety and easier upkeep of other invariants.
