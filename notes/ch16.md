# Chapter 16: Enums

## 16.1 Lack of Enums

- `handleEmailBounce` checks `updateStatus`, then `track`, and wraps each error with `fmt.Errorf("...: %w", err)`, using the spec's prefixes. If the status update fails, tracking is skipped, so a rejected status is never counted. `go test -race` passes all four cases.
- The compiler does not force error checks, but the linter does. Measured: the lesson's unchecked version gives two golangci-lint `errcheck` reports, for example ``Error return value of `a.track` is not checked``. Keep errcheck on in CI. Assigning to `_` is the explicit way to ignore an error.
- `%w` keeps the cause in the chain. Measured: `errors.Unwrap` on the wrapped error returns `invalid event: x`. The course's `user.go` builds its errors with `fmt.Errorf` and no sentinel, so a caller can match only the text. Production code declares `var errInvalidStatus = errors.New("invalid status")`, wraps it with the value (`fmt.Errorf("%w: %s", errInvalidStatus, status)`), and callers test it with `errors.Is`.
- Style: Go error strings usually leave out "error" and "failed to", because every layer adds its own prefix: `updating user status: invalid status: email_sent`. The course mandates the `error ...:` prefixes, so the solution keeps them.
- Course test gap: the test declares `expectedStatus` and `expectedBounces` but never checks them. Only the error text is compared.
- The status values are free-form strings (`"email_bounced"`, `"email_failed"`), so a typo compiles. The next two lessons replace them with a named type and `iota` constants.

## 16.2 Type Definitions

Quiz:

1. In which case will the Go compiler raise an error? **`checkPermission(Admin)`.**
2. Will `checkPermission(perm(Admin))` raise an error from the compiler? **No.**

Notes:

- Measured with the lesson's code: only `checkPermission(Admin)` fails, with `cannot use Admin (variable of type string) as perm value in argument to checkPermission`. `Write`, `User` and `Read` already have type `perm`. `perm(Admin)` is an explicit conversion. `checkPermission("slack")` also compiles, because an untyped string constant converts implicitly to any type whose underlying type is `string`.
- The rule: assignability fails only for a typed value of a different named type. Untyped constants and explicit conversions both pass, so a type definition guards against mixing variables, not against invalid values.
- Production options when the set must be closed:
  - Validate at the boundary. Give the type a `Valid() bool` method, or parse it with `parsePerm(string) (perm, error)`, where external strings enter (JSON, MQTT topics, CLI flags).
  - Use the `exhaustive` linter. It checks that a `switch` covers every constant of the type. Measured: a switch with `Read` and `Write` only gives `missing cases in expression switch: Exec (exhaustive)`. It is off by default in golangci-lint, so enable it.
  - Make invalid values hard to construct: an unexported struct type such as `type perm struct{ name string }`, with exported package-level values. Code outside the package can only use the values the package exports, apart from the zero value.

## 16.3 Iota

- `type emailStatus int` with `EmailBounced emailStatus = iota` followed by `EmailInvalid`, `EmailDelivered` and `EmailOpened` gives 0, 1, 2 and 3. A constant with no expression repeats the previous type and expression, so all four have type `emailStatus`, and `iota` counts up by line. `go test -race` passes all five cases, including `emailStatus(17)`, which maps to `"Unknown"`.
- Zero-value trap: `EmailBounced` is 0, so every status that was never set reads as "bounced". Measured: a zero `email{}` gives `Status == EmailBounced` as `true`, and so does `json.Unmarshal` of `{}`. In production, put an invalid or unknown value at 0 (`EmailUnknown emailStatus = iota`), or start real values at `iota + 1`. Then a missing field cannot pass as a real state.
- `iota` numbers are positional. Inserting a constant in the middle renumbers every constant after it. That is harmless inside one binary but breaks anything persisted or sent over the wire: database rows, MQTT or CAN payloads, or logs that store the integer. For values that leave the process, assign explicit numbers or use string values (16.2).
- `getEmailStatusName` in the course test is a hand-written `String()`. Named `String() string` on the type, it would make `fmt` print names instead of numbers. The `golang.org/x/tools/cmd/stringer` tool generates that method with `go generate`. Not measured here, because `stringer` is not installed.
