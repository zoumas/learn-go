# Chapter 9: Slices

## 9.1 Arrays in Go

- The length is part of the type. `[3]int` and `[4]int` are different types, and an array literal can let the compiler count: `[...]int{5: 1}` has length 6.
- Arrays are values, not references. Assignment, passing to a function, and returning all copy every element. Measured: after `b := a; b[0] = 7` and a call that sets `a[0] = 99` on its parameter, `a` is still `[1 2 3]`. This is the main difference from slices, which share a backing array.
- Arrays of comparable elements are comparable with `==`, so they can be map keys: `map[[2]int]string` works. The course test compares six elements one by one; `actualMessages != test.expectedMessages || actualCosts != test.expectedCosts` does the same.
- `len` on a string counts bytes, not characters. Measured: `len("café")` is 5, `utf8.RuneCountInString("café")` is 4. The lesson's cost is bytes, which is the right unit for an SMS or MQTT payload budget, but not for a character count shown to a user.
- Size: `[3]string` is 48 bytes (three 16-byte headers, pointer and length), `[3]int` is 24 on amd64. The string data itself is not copied when the array is copied, only the headers.
- Production note: a fixed-size array is the natural type for fixed-layout data, for example a CAN frame payload `[8]byte`. It lives on the stack or inline in a struct, needs no allocation, and copying it is cheap. For a variable number of retries, a slice fits better.

## 9.2 Slices in Go

- A slice is a header of three words: pointer to the backing array, length, and capacity. `a[low:high]` gives length `high-low` and capacity `cap(a)-low`, so the elements after `high` are still reachable.
- Measured on the free-plan result: `messages[:2]` has `len 2, cap 3`, and `s[:cap(s)][2]` still reads the third message. An `append(s, "X")` does not allocate. It writes `"X"` into the third element of the shared backing array. A caller that appends to a returned slice can overwrite data the callee still holds.
- The full slice expression `a[low:high:max]` caps the capacity at `max-low`. `messages[:2:2]` has `cap 2`, so the next `append` must copy to a new array. Use it when returning a sub-slice of an array or buffer the function keeps.
- `messages` is an array parameter, so the function slices its own copy, not the caller's array. Slicing a local array makes the compiler move it to the heap: `go build -gcflags=-m` reports `moved to heap: messages`. The returned slice never aliases the caller's array.
- A `nil` slice has `len 0`, and `range`, `len` and `append` all work on it. Return `nil`, not `[]string{}`, on the error path. The difference shows only in `== nil` checks and in JSON, where `nil` encodes as `null` and an empty slice as `[]`.
- Production note: a function that returns a fixed error text usually declares a sentinel, `var ErrUnsupportedPlan = errors.New("unsupported plan")`, so callers can test it with `errors.Is`. `errors.New` in the return statement makes a new value each call, and callers can only compare the message string.

## 9.3 Slices Review

Quiz:

1. Which references the other? **Slices reference arrays.**
2. Multiple slices can point to the same array. **True.**
3. A function that only has access to a slice can modify the elements of the underlying array. **True.**

Notes:

- Overlapping slices see each other's writes. Measured: with `a := arr[0:2]` and `b := arr[1:3]`, setting `b[0] = 99` inside a function changes `arr[1]` and `a[1]` too.
- The slice header is passed by value, so a callee can change the elements but not the caller's length or capacity. Measured: a function that runs `s = append(s, 4)` on `arr[:3]` writes `4` into `arr[3]`, because the capacity allowed it, but the caller's slice still has `len 3`. The new element is in memory and invisible to the caller.
- When `append` has to grow, the callee's slice moves to a new array and later writes stop reaching the caller. Measured: on `[]int{1, 2, 3}` (full capacity), `append` then `s[1] = 77` leaves the caller's slice as `[1 2 3]`. Whether a write is visible depends on the capacity at run time. That is why functions that grow a slice return it, as `append` itself does.
- `io.Reader`'s `Read(p []byte) (n int, err error)` follows this rule. The caller owns the buffer and its length is the limit. The callee fills `p[:n]` and returns `n`, not a new slice. In a pipeline that reuses one read buffer, data a consumer keeps must be copied out before the next `Read`, or it is overwritten. The same applies to frames from a `bufio.Scanner`: `Bytes()` is only valid until the next `Scan`.

## 9.4 Make

- `make([]T, n)` gives `len n, cap n`, filled with zero values, so the loop assigns by index: `costs[i] = ...`. `make([]T, 0, n)` gives `len 0, cap n`, and the loop must `append`. Mixing the two is a common bug: `make([]T, n)` followed by `append` leaves `n` zeros at the front. The course test checks `cap(output)`, so either form must preallocate exactly `len(messages)`.
- `for i, msg := range messages` replaces `for i := 0; i < l; i++` plus `messages[i]`. It needs no length variable and cannot index out of range.
- Float money is not exact. Measured: `float64(57) * 0.01` is `0.5700000000000001`, while `float64(57) / 100` is `0.57`. Ten additions of `0.1` give `0.9999999999999999`. The course test compares with `!=`, and passes only because its message lengths happen to round cleanly. Dividing by 100 gives the correctly rounded result because 100 is exact in binary and 0.01 is not.
- Production note: store money as integer minor units (cents, or a smaller unit for per-message pricing) in `int64`, and format at the edge. Compare computed floats in tests with a tolerance, for example `cmpopts.EquateApprox`. The same applies to sensor values: keep raw integer counts from the device and scale once, not on every step of a pipeline.

## 9.5 Len and Cap Review

Quiz:

1. What does the `cap()` function return? **The maximum length of the slice before reallocation of the array is necessary.**
2. What does the `len()` function return? **The current length of the slice.**
3. What do `len()` and `cap()` do when a slice is nil? **Return 0.**

Notes:

- `len` and `cap` never panic on nil. Measured: a nil slice, map (`len` only), channel, and string all give 0. A nil `*[3]int` gives `len 3, cap 3`, because the length is part of the type and the pointer is never read. Ranging over that nil pointer with a value variable does read it, and panics with `invalid memory address or nil pointer dereference`.
- The lesson's `Append`, from Effective Go, shows what the built-in `append` does: if `len + len(data)` fits in `cap`, it reslices in place (`slice[0:l+len(data)]`) and copies. Otherwise it allocates a bigger array and copies the old elements first. The reslice past `len` and up to `cap` is legal; past `cap` it panics.
- The real growth rule is not "double". Measured on go1.27.3, amd64, appending one `int` at a time: `4 8 16 32 64 128 256 512 848 1280 1792 2560`. It doubles up to 256 elements, then grows by a smaller factor that falls toward 1.25×, and every step is rounded up to a malloc size class, which is why 848 appears. Appending single bytes gives `32 64 128`: the first allocation is already a 32-byte size class. Do not write tests or logic that depend on these values.
- Production note: `append` on a slice that is about to grow costs one allocation plus a copy of every element. For a buffer that collects readings per batch, allocate once with `make([]T, 0, batchSize)` and reuse it with `buf = buf[:0]`, which keeps the capacity. `slices.Grow(s, n)` reserves room for `n` more elements in one step when the count is known later.

## 9.6 Variadic

- Inside the function, `nums ...int` is a plain `[]int`. Called with no arguments it is `nil`. Called as `f(s...)`, the function gets `s` itself, not a copy. Measured: a function that sets `nums[0] = 0` changes the caller's slice when called as `zero(s...)`, and leaves `a` and `b` unchanged when called as `zero(a, b)`, because Go builds a new slice from separate arguments.
- `nil...` and `[]int{}...` pass through unchanged: `nums == nil` is `true` for `f()` and `f(nil...)`, and `false` for `f([]int{}...)`.
- Separate arguments and a spread slice cannot be mixed. `sum(1, s...)` fails with `too many arguments in call to sum` and `have (number, []int...)`. Build the slice first, for example `sum(append([]int{1}, s...)...)`.
- A `[]string` does not spread into `...any`. `fmt.Println(names...)` fails with `cannot use names (variable of type []string) as []any value in argument to fmt.Println`. `[]string` and `[]any` have different memory layouts, so the conversion needs a loop that builds a `[]any`.
- Production note: `log/slog` uses variadic key-value pairs, `logger.Info("msg", "device", id, "rssi", v)`, and `go vet` checks them for a missing value. Functional options, `New(addr string, opts ...Option)`, are the common pattern for constructors with optional settings, for example an MQTT client's timeouts and TLS config.

## 9.7 Append

- The lesson asks for an empty, non-nil slice, so `[]float64{}` is required here, not `var dayCosts []float64`. `append` works on both. The difference shows in JSON: measured, a nil `[]float64` encodes as `null` and an empty one as `[]`. An API whose clients expect an array must return the non-nil form.
- `[]float64{}` has `cap 0`, so the first `append` allocates. When the result count is unknown, that is fine. When an upper bound is cheap, `make([]float64, 0, len(costs))` allocates once, at the cost of holding unused capacity.
- Always assign the result of `append`, to the same slice in most cases. `append` writes into the old array when the capacity allows. Measured: `y := append(x[:1], 9)` on `x = [1 2 3 4]` gives `y = [1 9]` and changes `x` to `[1 9 3 4]`.
- Production note: the standard library has no `slices.Filter`. The plain loop is the idiom. For a large batch filtered in place, reuse the input array: `out := costs[:0]`, then append the kept elements. Measured on `[1 2 3 4 5 6]`, keeping even values: `out` is `[2 4 6]` and the input becomes `[2 4 6 4 5 6]`, so the input is no longer usable. `slices.DeleteFunc` does the same and zeroes the tail: the input becomes `[2 4 6 0 0 0]`, which lets the garbage collector free pointers in the removed elements.

## 9.8 Range

- The element variable is a copy. Measured: `for _, d := range ds { d.seen++ }` on a `[]dev` leaves every `seen` at 0. To change the elements, index: `for i := range ds { ds[i].seen++ }`. Copying also costs time for large structs, which is another reason to index or to range over a slice of pointers.
- `range` evaluates its operand once, before the loop starts. Measured: appending inside `for range s` on a 3-element slice runs 3 iterations and leaves `len 6`. The loop does not see the new elements.
- Over a slice, the loop reads each element when it gets there, so writes to later elements are visible. Over an array, `range arr` copies the whole array first, so they are not. Measured: setting element 2 to 99 during iteration 0 gives `v = 99` for the slice and `v = 3` for the array. `range &arr` or `range arr[:]` avoids the copy.
- The nested loop is O(len(msg) × len(badWords)), and returning from inside both loops is the clean exit; no labeled `break` is needed. The standard library form is `slices.IndexFunc(msg, func(w string) bool { return slices.Contains(badWords, w) })`, measured to return `3` on the lesson example.
- Production note: for a word list of real size, build a `map[string]struct{}` set once, outside the per-message path, so each lookup is O(1). The same applies to an allow-list of device IDs or CAN arbitration IDs checked per frame. A real profanity filter also normalizes case and punctuation before the lookup.
