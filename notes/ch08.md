# Chapter 8: Loops

## 8.1 Loops in Go

- The solution uses `for i := range numMessages` (range over int, Go 1.22) instead of the lesson's three-clause `for i := 0; i < numMessages; i++`. Both run `0` to `n-1`. A negative or zero count gives zero iterations. Measured: `for range -5` runs 0 times.
- Since Go 1.22, the three-clause loop also creates a new `i` for each iteration. Measured: closures that capture `i` in `for i := 0; i < 3; i++` print `0 1 2`. In a file with `//go:build go1.21`, the same code prints `3 3 3`. The per-file build tag sets the language version, so old semantics can come back in one file of a 1.27 module. Range over int is also rejected there: `cannot range over -5 (untyped int constant): requires go1.22 or later (file declares //go:build go1.21)`.
- Adding `0.01` again and again in a `float64` drifts. Measured: for 30 messages the loop gives `34.349999999999994`, and the closed form `n + 0.01*n*(n-1)/2` gives `34.350000000000001`. The test passes only because it compares `%.2f` strings. Summing integer cents (`100 + i`) gives exactly `3435`. See 7.2 for money in `float64`.
- The loop is O(n), and the total has a closed form that is O(1). The lesson asks for a loop on purpose. In a billing path, use the formula in integer cents.

## 8.2 Omitting Conditions from a for Loop in Go

- `for i := 0; ; i++` with no condition runs until `return` or `break`. The loop has no exit at the bottom, so the function needs no final `return`. The compiler accepts this because a `for` with no condition and no `break` is a terminating statement.
- The check `acc > thresh` comes after the add, so `i` is the count of messages that fit. `thresh = 100` returns 1 and `thresh = 0` returns 0. A negative `thresh` also returns 0. Measured: `maxMessages(-1)` is `0`.
- The loop terminates only because `acc` reaches `thresh`. Near `math.MaxInt`, `acc` overflows and wraps negative before it passes `thresh`. Signed overflow in Go wraps silently. It is not undefined behavior and does not panic. Measured: `maxMessages(math.MaxInt)` did not return after 20s. In production, bound the loop or compute the answer directly.
- The answer has a closed form: the largest `n` with `100n + n(n-1)/2 <= thresh`, from the quadratic formula, plus an integer correction step for float rounding. Measured: it matches the loop for every `thresh` from -500 to 2000000. A budget check in a billing or rate-limit path should use the formula, or at least cap the iteration count.

## 8.3 There Is No While Loop in Go

- The fix is the condition `for balance > 0`. Go has no `while` keyword. A `for` with only a condition is the while loop, and a bare `for {}` is the infinite loop.
- The loop terminates only when the costs sum past the budget. With `costMultiplier < 1`, the costs form a convergent geometric series, so the total never exceeds `1/(1-m)`. With `costMultiplier == 0`, every message after the first is free. Measured: `(0.5, 2)`, `(0.5, 3)` and `(0, 5)` did not return after 3s. `(1.0, 5)` returns `5` and `(0.5, 1)` returns `1`.
- With `m = 1.0` and budget 5, `balance` reaches exactly `0.0`. Whole numbers are exact in `float64`, so the `balance < 0` check does not fire and the answer is 5. With fractional multipliers, an exact zero depends on rounding. Production code would validate `costMultiplier > 1` at the boundary, or cap the message count, and keep money in integer pennies (see 7.2 and 8.1).

## 8.4 Fizzbuzz

- Check the combined case first. The `i%3 == 0 && i%5 == 0` branch must come before the single checks, or 15 prints `fizz`. `i%15 == 0` is the same test, because 3 and 5 are coprime.
- Idiom: a tagless `switch` is the Go way to write a long `if`/`else if` chain. Effective Go: "It's therefore possible—and idiomatic—to write an if-else-if-else chain as a switch." Cases are checked top to bottom and the first match wins, with no fallthrough.

  ```go
  switch {
  case i%15 == 0:
      fmt.Println("fizzbuzz")
  case i%3 == 0:
      fmt.Println("fizz")
  case i%5 == 0:
      fmt.Println("buzz")
  default:
      fmt.Println(i)
  }
  ```

- `os.Stdout` is an unbuffered `*os.File`, so each `fmt.Println` is one `Write`, which is one syscall. Measured with a writer that counts calls: 100 lines make 100 `Write` calls directly, and 1 call through `bufio.NewWriter` followed by `Flush`. For high-volume output, such as a log or CAN frame dump on a slow embedded console, wrap the writer in `bufio` and `Flush` before exit. A missed `Flush` drops the tail of the output silently. Taking an `io.Writer` parameter instead of printing to `os.Stdout` also makes the function testable.

## 8.5 Continue & Break

- `continue` skips to the next iteration (the post statement still runs). `break` leaves the innermost `for`, `switch` or `select`. A `break` inside a `switch` or `select` inside a loop only exits that `switch` or `select`, not the loop. To leave the loop, use a label: `outer: for ... { switch { case x: break outer } }`. This catches people in `for { select { ... } }` event loops, which are common in concurrent pipelines.
- The parameter name `max` comes from the starter code. It shadows the `max` builtin added in Go 1.21. The code is legal, but inside the function the builtin can no longer be called. Measured: `max(max, 3)` fails with `invalid operation: cannot call max (variable of type int): int is not a function`. The `predeclared` linter flags this, but the `golangci-lint` config here does not enable it. Avoid `max`, `min`, `len`, `new`, `clear` and `cap` as identifiers in your own code.
- `n <= max` reads better than `n < max+1` and does the same thing. Both are wrong at `math.MaxInt`: `max+1` wraps to `MinInt` and the loop does not run, while `n <= MaxInt` is always true.
- The output matches a reference built from coreutils `factor` for 10, 20 and 30, including the headings. Trial division up to `sqrt(n)` is O(n·sqrt(n)) for the whole range. To print every prime up to `max`, the sieve of Eratosthenes is O(n log log n). For a single large number, `math/big`'s `(*Int).ProbablyPrime` runs Miller-Rabin plus Baillie-PSW.
