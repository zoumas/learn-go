# Chapter 10: Maps

## 10.1 Maps

- `make(map[K]V, n)` takes a size hint, so the map is built at the right size instead of growing in steps. Measured for 1000 string keys: 22 allocations without the hint, 6 with `make(map[string]int, len(keys))`. Here the final size is known: `len(names)`.
- Assigning to an existing key overwrites it with no error. Measured: names `["Eren", "Eren"]` give `map[Eren:1]` with `len 1`, so the second phone number silently replaces the first. If duplicates matter, check with `if _, ok := m[name]; ok` before the write.
- A nil map can be read but not written. Measured: indexing a nil `map[string]int` returns `0` and `len` is `0`, but a write panics with `assignment to entry in nil map`. Returning `nil` with an error, as here, is safe because callers only read it.
- Phone numbers as `int` do not fit on 32-bit targets. Measured: `GOARCH=arm go vet` rejects the course test with `cannot use 14355550987 (untyped int constant) as int value in array or slice literal (overflows)`. The `int` type also drops a leading `0` or `+`. Production code stores phone numbers as strings, normalized to E.164 (`+14355550987`).
- Production note: map iteration order is randomized, so code that ranges over a map to build output must sort the keys first (`slices.Sorted(maps.Keys(m))`) for stable logs, test output or JSON. Concurrent writes are not just a race: measured, four goroutines writing one map without a lock crash the process with `fatal error: concurrent map writes`, which `recover` cannot catch. A device registry updated from several goroutines needs a `sync.Mutex` or `sync.Map`.
