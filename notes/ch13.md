# Chapter 13: Channels

## 13.1 Concurrency

- `go func() { ... }()` starts the closure and returns at once, so `Email sent` prints first and `Email received` 250 ms later. The closure captures the parameter `message`, which no one changes afterwards, so sharing it is safe. `go run -race` reports nothing.
- The order on screen comes from the sleeps (250 ms in the goroutine, 500 ms in `test`), not from any synchronization. The Go memory model orders events only through synchronization (channels, `sync`, `atomic`). A sleep does not order anything, so on a loaded machine the 250 ms goroutine could in principle print after `test` moves on.
- When `main` returns, the program exits and every other goroutine stops mid-flight. Measured: without the sleep in `test`, a `main` that starts the goroutine and prints `sent` prints only `sent`. `received` never appears, and there is no error. The next lessons replace the sleep with channels; `sync.WaitGroup` (chapter 14) is the other common way to wait.
- Goroutines are cheap but not free. Measured: 100,000 goroutines blocked on a channel used 2,053 bytes of stack each (the initial 2 KiB stack) and about 2.7 KB of total memory each, about 270 MB in all. A blocked goroutine is never collected, so one that waits forever is a memory leak.
- Production note: every goroutine needs an owner who knows how it ends, usually through a `context.Context` and a `WaitGroup` or `errgroup.Group`. "Send thousands of emails at once" means one goroutine per email only up to a limit: bound the concurrency with a worker pool or a semaphore, or the remote server's rate limit, the file descriptor limit, or memory will set the limit for you. To test timing code like this without real sleeps, use `testing/synctest` (stable since Go 1.25). Measured: inside `synctest.Test`, a goroutine sleeping 250 ms reports `fake elapsed: 250ms` while the test takes `0.004s`.

## 13.2 Channels

- Fix: `go sendIsOld(isOldChan, emails)`, then three receives on the calling goroutine. Before the fix, `main` sends on an unbuffered channel with no receiver. Measured: `fatal error: all goroutines are asleep - deadlock!` with `goroutine 1 [chan send]`. Tests pass under `go test -race` with `-count=200` and `GOMAXPROCS` set to 1, 2 and 16.
- Why it is correct (memory model): on an unbuffered channel the send and the receive meet, and a send is synchronized before the matching receive completes. The three values arrive in the order they were sent, because a channel is FIFO and there is a single sender. No memory is shared: `emails` is an array, so `go sendIsOld(..., emails)` copies it, and the bools are copied through the channel. That is why `-race` finds nothing.
- Deadlock detection only fires when *every* goroutine is blocked. Measured: with one unrelated goroutine looping on `time.Sleep`, an extra `<-ch` hangs forever and nothing fatal is printed (killed by `timeout`). The same extra receive inside `go test` shows no deadlock message either. It hangs until `-timeout` (`panic: test timed out after 3s`; the default is 10m). A production service always has live goroutines, so a deadlock there shows up as a stall, not a crash.
- The receiver must take exactly as many values as the sender sends. Too many receives deadlock (above). Too few leak the sender. Measured: 1000 runs that read 2 of 3 values left `goroutines: 1001`, each sender stuck forever in `chan send`. `for i := range isOld { isOld[i] = <-isOldChan }` removes the repetition but keeps the coupling. The usual fix is for the sender to `close` the channel and the receiver to `range` over it, which comes later in this chapter.
- `time.Date` normalizes out-of-range fields. Measured: `time.Date(2020, 0, 0, ...)` is `2019-11-30` (month 0 is December 2019, day 0 is the last day of the month before), so the cutoff in `sendIsOld` is not 2020-01-01. `time.Date(2019, 2, 0, ...)` is `2019-01-31`.
- Production note: a pipeline stage that sends with a bare `ch <- v` leaks as soon as its consumer stops early (error, shutdown, a `break` in the loop). Make every blocking send cancellable: `select { case out <- v: case <-ctx.Done(): return ctx.Err() }`. Measured: the 1000-run leak above with the sender selecting on `ctx.Done()` and the receiver calling `cancel()` ends with `goroutines: 1`. The unbuffered handoff is also natural backpressure: a slow consumer (an MQTT publish, say) slows the CAN reader instead of letting a queue grow without limit.

## 13.3 Channels

- `waitForDBs` receives one token per database: `for range numDBs { <-dbChan }`. A bare `<-ch` waits for the signal and throws the value away. `chan struct{}` is the usual type for a signal, since the value carries no data.
- The course's own code has a data race. The browser passes because it runs Go as WebAssembly, and the race detector is not available there (measured: `-race is not supported on js/wasm`). Without `-race`, the test also passes locally. Under `go test -race`, the test's reads of `*count` (main_test.go:37) race with `count++` in the goroutine. The goroutine increments the count *after* its send. A receive only makes visible the writes the sender did *before* the matching send. So the test's read has no synchronization with the increment.
- Running on one thread does not hide a race. Measured: `GOMAXPROCS=1 go test -race` still reports it. The detector checks happens-before order (vector clocks), not whether two threads actually ran at the same time.
- Repo change from the course: `count++` moved above `ch <- struct{}{}` in the "don't touch" code. Now the final receive in `waitForDBs` comes after the last increment, so the test's read is synchronized. Measured: `go test -race -count=50` is clean with `GOMAXPROCS` set to 1, 2 and 16.
- The test's `for *count != n { ... }` is a spin-wait on shared memory. The Go memory model gives a matching example (`for !done {}`) and says a racy read like this is not guaranteed to ever see the write. Measured: a call-free spin on a racy `*p` did see the write today, but that is luck from today's compiler, not a guarantee.
- Production note: to wait until N dependencies are up, use `sync.WaitGroup` (or `errgroup.Group` if startup can fail) rather than counting tokens. To share a counter, use `atomic.Int64`, or send the value through the channel. Never spin on shared memory. A boot wait also needs a deadline: `select` on the ready signal and on `ctx.Done()`, so a database that never comes up fails startup instead of hanging it.
