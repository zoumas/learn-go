# Chapter 6: Interfaces

## 6.1 Interfaces in Go

- A type satisfies an interface implicitly: it only needs the methods. There is no `implements` keyword. The usual way to check it at compile time is a blank assignment next to the type, `var _ message = birthdayMessage{}`. Measured: when the method has a pointer receiver, the value does not satisfy the interface, and vet reports `t does not implement message (method getMessage has pointer receiver)`.
- An interface value is two words: a pointer to the type information and a pointer to the data. Measured: `unsafe.Sizeof` of a `message` is 16 on amd64.
- Storing a non-pointer value in an interface can allocate, because the data word must point to a copy. Measured with `testing.AllocsPerRun`: assigning a 40-byte `birthdayMessage` to an escaping `message` variable makes 1 allocation, and assigning `&bm` makes 0. In a hot path, such as a pipeline stage that wraps every CAN frame in an interface, this is a per-message heap allocation. Pass pointers or concrete types there.
- An interface that holds a nil pointer is not nil. Measured: `var p *birthdayMessage; var m message = p` gives `m == nil` as `false`. Return a literal `nil`, not a typed nil pointer, from a function whose result is an interface, especially `error`.
- `interface{}` has an alias, `any`, since Go 1.18. Prefer `any` in new code.
- `len` counts bytes, so the cost is per byte, not per character (see 5.10).

## 6.2 Interface Implementation

- Without `getSalary` on `contractor`, the error appears where a `contractor` is used as an `employee`, not at the type declaration. Measured: `cannot use contractor{…} (value of struct type contractor) as employee value in struct literal: contractor does not implement employee (missing method getSalary)`, reported in `main_test.go`. If no code ever uses the type as the interface, there is no error at all. A `var _ employee = contractor{}` line next to the type moves the check to the type's own file (see 6.1).
- Method order does not matter: `fullTime` declares `getSalary` before `getName`, and it still satisfies the interface.
- The interface is declared next to the types that implement it, as the lesson needs. In production Go, the consumer defines the interface, with only the methods the consumer calls. For example, a payroll package declares `type salaried interface{ getSalary() int }` and the employee types do not import it. Implicit satisfaction is what makes this possible.

## 6.3 Interfaces Are Implemented Implicitly

Quiz:

1. How is an interface fulfilled? A type has all the required interface's methods defined on it.
2. Can a type fulfill multiple interfaces? Yes.

Notes:

- The wrong answer to question 1, "a struct embeds the interface in its definition", also compiles. Embedding an interface promotes its methods, so the struct satisfies the interface. But the embedded field is a nil interface unless it is set. Measured: `type stub struct{ employee }` can be assigned to an `employee`, and calling `getName()` on it panics with `invalid memory address or nil pointer dereference`. The real use is a decorator, which wraps an existing value and overrides one method. For example, a struct that embeds an `io.Writer`, sets it to the real writer, and overrides `Write` to count bytes. Test fakes use the same trick: embed the interface and implement only the methods the test calls. Any other call panics.
- One type usually satisfies many interfaces. Measured: `os.Stdout` (`*os.File`) satisfies `io.Reader`, `io.Writer` and `io.Closer`. Small interfaces, such as the one-method interfaces in `io`, are what make this useful: a function that takes an `io.Writer` accepts a file, a `bytes.Buffer`, a network connection, or a serial port.

## 6.4 Interfaces Quiz

Quiz:

1. Go uses the ___ keyword to show that a type implements an interface. There is no keyword in Go.
2. In the example given, the ___ type implements the ___ interface. `circle`, `shape`.

Notes:

- The method's name is not enough: the whole signature must match. Measured: `area() float32` against `area() float64` gives `circle does not implement shape (wrong type for method area)`, followed by `have area() float32` and `want area() float64`.
- The lesson's `circle.area` uses `3.14` instead of `math.Pi`. Measured: for radius 10, `3.14` gives `314` and `math.Pi` gives `314.1592653589793`, which is 0.05% low. Use `math.Pi`. The 6.1 example already does.
- Java's `class Circle implements Shape` makes the dependency point from the type to the interface. In Go, the type does not know about the interface, so a package can define an interface that a type from the standard library or a vendor SDK already satisfies, without changing that type (see 6.2).

## 6.5 Multiple Interfaces

- `email` satisfies both `expense` and `formatter`, but nothing in the package uses either interface, so golangci-lint's `unused` reports `type expense is unused` and `type formatter is unused`. The interfaces come from the starter code. Measured: adding `var _ expense = email{}` and `var _ formatter = email{}` clears both reports and checks at compile time that `email` satisfies both (see 6.1).
- The format has single quotes around the body. `%q` is not a shortcut here: it uses double quotes and escapes the content. Measured: `fmt.Sprintf("%q", "it's")` gives `"it's"`. Use `%q` for logs, where escaping control characters and showing the string's boundaries matters, and `'%s'` when the format is fixed by a spec.
- The cost is an `int` in cents, not a `float64` in dollars. This is the correct choice for money: integer cents add up exactly, and floats do not. Measured: adding `0.1` ten times to a `float64` gives `0.9999999999999999`, not `1`. Production code also makes the rates named constants (`const subscribedRate, unsubscribedRate = 2, 5`).

## 6.6 Name Your Interface Parameters

Quiz:

1. Are you required to name the parameters of an interface method in order for your code to compile properly? No.
2. Why would you name your interface's method's parameters? Readability and clarity.

Notes:

- The names are documentation only. They are not part of the method's type, so an implementation can use other names or none. Measured: `copy(sourceFile string, destinationFile string) (bytesCopied int)` in the interface is satisfied by `func (fake) copy(a, b string) int`.
- In one parameter list, all parameters are named or none are. Measured: `copy(sourceFile string, string) int` fails with `missing parameter type`.
- Parameters of the same type can share it: `Copy(sourceFile, destinationFile string) (bytesCopied int)`. The lesson's long form also compiles, and gofmt does not change it.
- The standard library names results in interfaces when two results of different meaning would be unclear otherwise. `io.Reader` is `Read(p []byte) (n int, err error)` (`src/io/io.go`). On an implementation, named results also allow a bare `return`. CodeReviewComments ("Named Result Parameters") advises against naming results only for that. Name them when the name documents something, such as two results of the same type, or when a deferred function must change a result, such as an error from `Close`.

## 6.7 Type Assertions in Go

- Use the two-value form, `v, ok := e.(email)`. The one-value form panics when the type is wrong. Measured: `e.(email)` on an `sms` panics with `interface conversion: main.expense is main.sms, not main.email`. Asserting on a nil interface does not panic in the two-value form, and `ok` is `false`.
- The lesson calls this a cast. Go has no casts. `float64(n)` is a conversion, which is checked at compile time. `e.(email)` is a type assertion, which is checked at run time against the dynamic type stored in the interface. A type assertion never changes the value: it only gets it back out.
- Two `if` statements with assertions work. A `switch v := e.(type)` (lesson 6.8) is shorter for more than one type, and it has a `default` case for "any other type".
- The asserted type can also be an interface. This is how optional behavior is detected. Measured: an `io.Writer` holding a `*bytes.Buffer` asserts to `io.StringWriter` as `true` and to `io.Closer` as `false`. An `io.Writer` holding `os.Stdout` asserts to `io.Closer` as `true`. The standard library does this, for example `io.Copy` checks for `io.WriterTo` and `io.ReaderFrom`, and an HTTP handler checks for `http.Flusher` to stream a response.
- Asserting to concrete types in a function like `getExpenseReport` means every new expense type needs a new branch. Production code adds a method to the interface (for example `recipient() string`), so a new type cannot be forgotten: it fails to compile until it has the method.

## 6.8 Type Switches

- In a case with one type, `v` has that type. In a case with several types, `case email, sms:`, `v` keeps the switch expression's type, here `expense`. Measured: `v.toAddress` in that case fails with `v.toAddress undefined (type expense has no field or method toAddress)`.
- `case nil:` matches a nil interface. Without it, a nil interface goes to `default`. Measured: `kind(nil)` returns `"nil"` from the `case nil` branch. `%T` prints the dynamic type with the package, `main.email`.
- Cases are checked in order, and the first match wins. With interface types in the cases, one value can match more than one. Measured: a type with both `String()` and `cost()` matches `case fmt.Stringer:` first, even though the next case also matches. Put the more specific interface first. With only concrete types, as in this lesson, the order does not matter.
- `return "", 0.0` and `return "", 0` are the same: the untyped constant `0` converts to `float64`.
- The test file for this lesson uses unkeyed struct literals, `email{true, "hello there", "kit@boga.com"}`. They break as soon as a field is added or reordered. `go vet`'s `composites` check only reports unkeyed literals of types from other packages, so it does not report these.

## 6.9 Clean Interfaces

Quiz:

1. Interfaces should have as ___ methods as possible. Few.
2. It's okay for interfaces to be aware of the types that satisfy them. False.
3. According to the lesson, what is the primary goal of keeping interfaces small? To only define the essential behaviors.
4. Interfaces allow you to define a method's implementation once and use it for many different types. False.

Notes:

The lesson gives three rules: keep interfaces small, an interface knows nothing about the types that satisfy it, and interfaces are not classes. The official guidance adds where to put an interface and when to create one.

### Keep interfaces small

- Go Proverbs (Rob Pike, Gopherfest 2015): "The bigger the interface, the weaker the abstraction." Every method added to an interface is one more thing each implementation and each test fake must provide, and one fewer type that can satisfy it.
- The standard library follows it. Measured by counting the entries in each exported interface in `src/io/io.go`: 12 interfaces have one entry, 7 have two, and 3 have three. None has more. The larger ones are built by embedding smaller ones: `ReadWriter` is `Reader` plus `Writer`.
- The lesson's `http.File` example has five entries, three of them embedded `io` interfaces. In Go 1.27 the source (`src/net/http/fs.go`) returns `fs.FileInfo`, not `os.FileInfo` as in the lesson. `os.FileInfo` is an alias of `fs.FileInfo`, so both spellings name the same type (`src/os/types.go`: `type FileInfo = fs.FileInfo`).
- A function should ask for the smallest interface it uses. A function that only writes takes an `io.Writer`, not an `*os.File` and not an `io.ReadWriteCloser`. Then a file, a `bytes.Buffer`, a TCP connection, a serial port and a test fake all work.

### An interface knows nothing about the types that satisfy it

- `IsFiretruck() bool` on `car` forces every car to know about firetrucks. The fix in the lesson is a larger interface that embeds the smaller one, and a type assertion to it. Measured: with `type firetruck interface { car; HoseLength() int }`, `describe(c car)` uses `if ft, ok := c.(firetruck); ok` and prints `red firetruck, hose 30` for a type with `HoseLength`, and `blue car` for one without. This is the optional-interface pattern from 6.7, the same one `io.Copy` uses for `io.WriterTo`.
- The same smell in production: a `Device` interface with `IsGateway() bool` or `SupportsOTA() bool`. Use a separate `updater interface { Update(ctx context.Context, image io.Reader) error }` and assert to it where it matters.

### Interfaces are not classes

- An interface has no data, no constructor, and no implementation. It only lists method signatures. Question 4 is false for this reason: each of five `fmt.Stringer` types still writes its own `String()`.
- To share an implementation, use one of these:
  - Embed a struct that has the method. The method is promoted and counts toward the outer type's method set. Measured: `sedan` embeds `base`, which has `String()` and `Color()`, so `sedan` satisfies `fmt.Stringer` and prints `car:blue`.
  - Write one function that takes the interface, such as `fmt.Fprintf(w io.Writer, ...)`.
  - Write a generic function (Go 1.18 and later) when the code must keep the concrete type, for example to return it.
- Embedding is not inheritance. The embedded `base` does not know about `sedan`, so a method on `base` that calls another method calls `base`'s version, never one that `sedan` overrides. Measured: `base.describe()` returns `"I am " + b.name()`, and `sedan{}.describe()` prints `I am base` even though `sedan` has its own `name()`.

### Where an interface goes (CodeReviewComments, "Interfaces")

- "Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values. The implementing package should return concrete (usually pointer or struct) types." This is the rule behind "accept interfaces, return structs". The producer can then add methods without breaking anyone.
- "Do not define interfaces on the implementor side of an API 'for mocking'." The consumer declares the small interface it needs, and its test defines a fake for it.
- "Do not define interfaces before they are used." Without a real caller, there is no way to tell which methods the interface needs, or whether it is needed at all.
- Example from the IoT domain: a telemetry uploader needs one call from the MQTT client. The uploader package declares `type publisher interface { Publish(ctx context.Context, topic string, payload []byte) error }`, and an adapter wraps the AWS IoT SDK client to satisfy it. The uploader's test uses a fake that records the published messages. Nothing in the uploader depends on the SDK's full client type, and swapping the transport (MQTT over WebSocket, a local broker, a file on the device for offline buffering) changes only the adapter.
- "interface{} says nothing" (Go Proverbs). A parameter of type `any` gives the compiler nothing to check. Use a small interface or a type parameter instead.

## 6.10 Message Formatter

- The three types differ only in their `format` method. Each is a separate struct because the spec asks for a `message` field. A named type on `string` also works: `type italic string` with `func (i italic) format() string` satisfies `formatter`, and `italic("hi").format()` gives `_hi_`. Use a struct when the type needs more than one field. For example, the "encrypted" format the lesson mentions needs a key.
- The method is `format()`, so `fmt` does not use it. Measured: `fmt.Println(bold{message: "x"})` prints `{x}`. A method named `String() string` satisfies `fmt.Stringer`, and then `fmt.Println` prints `**x**`. Use `String()` when the formatted form is the value's normal text form.
- The formatters do not escape the message. Measured: ``code{message: "a`b"}.format()`` gives `` `a`b` ``. In Markdown, the first two backticks form the code span, and the third is a literal backtick. CommonMark's fix is a longer fence of two backticks: ``` ``a`b`` ```. Production formatters escape their input, the same reason `html/template` exists. Reasoned from the CommonMark spec, not rendered here.
- The starter's `sendMessage(format formatter)` names the parameter like the method. `format.format()` works, because the method is selected on the value, but the name reads badly. Its comment says `Format`, which does not exist. Both come from the starter code.
- This is the strategy pattern: the caller chooses the behavior by choosing the type, and `sendMessage` does not change when a new format is added. In an IoT pipeline the same shape is a payload encoder: `type encoder interface { Encode(r Reading) ([]byte, error) }` with JSON for debugging, and CBOR or Protocol Buffers on a metered cellular link.

## 6.11 Process Notifications

- `importance()` is part of the `notification` interface, so the type switch does not need it. Each case only has to pick the name: `n.importance()` can be called once on the interface, before or after the switch. Calling `v.importance()` in each case gives the same result. The type switch is needed only for the fields that the interface does not expose.
- The name is the same problem as in 6.7: each new notification type needs a new case, and nothing checks that one was added. A `source() string` method on the interface would remove the type switch completely, and a new type without it would not compile. The lesson asks for the type switch, so the solution uses one.
- `50` and `100` are scores with a meaning. In production code they are named constants (`const urgentImportance, alertImportance = 50, 100`), so a reader can tell that the urgent DM score is deliberately half the system-alert score.
- Sizes on amd64: `directMessage` is 48 bytes (two strings, an `int` and a `bool`, with 7 bytes of padding after the `bool`), `groupMessage` is 40 and `systemAlert` is 32. The padding is at the end, so no field order makes `directMessage` smaller, and `fieldalignment` reports nothing.
- Interface values passed to `processNotification` hold copies of these structs. Each conversion of a 48-byte `directMessage` to `notification` can allocate when the value escapes (see 6.1). For a high-rate notification queue, store pointers (`*directMessage`) in the interface.
