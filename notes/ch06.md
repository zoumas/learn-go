# Chapter 6: Interfaces

## 6.1 Interfaces in Go

- A type satisfies an interface implicitly: it only needs the methods. There is no `implements` keyword. The usual way to check it at compile time is a blank assignment next to the type, `var _ message = birthdayMessage{}`. Measured: when the method has a pointer receiver, the value does not satisfy the interface, and vet reports `t does not implement message (method getMessage has pointer receiver)`.
- An interface value is two words: a pointer to the type information and a pointer to the data. Measured: `unsafe.Sizeof` of a `message` is 16 on amd64.
- Storing a non-pointer value in an interface can allocate, because the data word must point to a copy. Measured with `testing.AllocsPerRun`: assigning a 40-byte `birthdayMessage` to an escaping `message` variable makes 1 allocation, and assigning `&bm` makes 0. In a hot path, such as a pipeline stage that wraps every CAN frame in an interface, this is a per-message heap allocation. Pass pointers or concrete types there.
- An interface that holds a nil pointer is not nil. Measured: `var p *birthdayMessage; var m message = p` gives `m == nil` as `false`. Return a literal `nil`, not a typed nil pointer, from a function whose result is an interface, especially `error`.
- `interface{}` has an alias, `any`, since Go 1.18. Prefer `any` in new code.
- `len` counts bytes, so the cost is per byte, not per character (see 5.10).

## 6.2 Interface Implementation

- Without `getSalary` on `contractor`, the error appears where a `contractor` is used as an `employee`, not at the type declaration. Measured: `cannot use contractor{…} (value of struct type contractor) as employee value in struct literal: contractor does not implement employee (missing method getSalary)`, reported in `main_test.go`. If no code ever uses the type as the interface, there is no error at all. A `var _ employee = contractor{}` line next to the type moves the check to the type's own file (see 6.1).
- Method order does not matter: `fullTime` declares `getSalary` before `getName`, and it still satisfies the interface.
- The interface is declared next to the types that implement it, as the lesson needs. In production Go, the consumer defines the interface, with only the methods the consumer calls. For example, a payroll package declares `type salaried interface{ getSalary() int }` and the employee types do not import it. Implicit satisfaction is what makes this possible.

## 6.3 Interfaces Are Implemented Implicitly

Quiz:

1. How is an interface fulfilled? A type has all the required interface's methods defined on it.
2. Can a type fulfill multiple interfaces? Yes.

Notes:

- The wrong answer to question 1, "a struct embeds the interface in its definition", also compiles. Embedding an interface promotes its methods, so the struct satisfies the interface. But the embedded field is a nil interface unless it is set. Measured: `type stub struct{ employee }` can be assigned to an `employee`, and calling `getName()` on it panics with `invalid memory address or nil pointer dereference`. The real use is a decorator, which wraps an existing value and overrides one method. For example, a struct that embeds an `io.Writer`, sets it to the real writer, and overrides `Write` to count bytes. Test fakes use the same trick: embed the interface and implement only the methods the test calls. Any other call panics.
- One type usually satisfies many interfaces. Measured: `os.Stdout` (`*os.File`) satisfies `io.Reader`, `io.Writer` and `io.Closer`. Small interfaces, such as the one-method interfaces in `io`, are what make this useful: a function that takes an `io.Writer` accepts a file, a `bytes.Buffer`, a network connection, or a serial port.

## 6.4 Interfaces Quiz

Quiz:

1. Go uses the ___ keyword to show that a type implements an interface. There is no keyword in Go.
2. In the example given, the ___ type implements the ___ interface. `circle`, `shape`.

Notes:

- The method's name is not enough: the whole signature must match. Measured: `area() float32` against `area() float64` gives `circle does not implement shape (wrong type for method area)`, followed by `have area() float32` and `want area() float64`.
- The lesson's `circle.area` uses `3.14` instead of `math.Pi`. Measured: for radius 10, `3.14` gives `314` and `math.Pi` gives `314.1592653589793`, which is 0.05% low. Use `math.Pi`. The 6.1 example already does.
- Java's `class Circle implements Shape` makes the dependency point from the type to the interface. In Go, the type does not know about the interface, so a package can define an interface that a type from the standard library or a vendor SDK already satisfies, without changing that type (see 6.2).

## 6.5 Multiple Interfaces

- `email` satisfies both `expense` and `formatter`, but nothing in the package uses either interface, so golangci-lint's `unused` reports `type expense is unused` and `type formatter is unused`. The interfaces come from the starter code. Measured: adding `var _ expense = email{}` and `var _ formatter = email{}` clears both reports and checks at compile time that `email` satisfies both (see 6.1).
- The format has single quotes around the body. `%q` is not a shortcut here: it uses double quotes and escapes the content. Measured: `fmt.Sprintf("%q", "it's")` gives `"it's"`. Use `%q` for logs, where escaping control characters and showing the string's boundaries matters, and `'%s'` when the format is fixed by a spec.
- The cost is an `int` in cents, not a `float64` in dollars. This is the correct choice for money: integer cents add up exactly, and floats do not. Measured: adding `0.1` ten times to a `float64` gives `0.9999999999999999`, not `1`. Production code also makes the rates named constants (`const subscribedRate, unsubscribedRate = 2, 5`).

## 6.6 Name Your Interface Parameters

Quiz:

1. Are you required to name the parameters of an interface method in order for your code to compile properly? No.
2. Why would you name your interface's method's parameters? Readability and clarity.

Notes:

- The names are documentation only. They are not part of the method's type, so an implementation can use other names or none. Measured: `copy(sourceFile string, destinationFile string) (bytesCopied int)` in the interface is satisfied by `func (fake) copy(a, b string) int`.
- In one parameter list, all parameters are named or none are. Measured: `copy(sourceFile string, string) int` fails with `missing parameter type`.
- Parameters of the same type can share it: `Copy(sourceFile, destinationFile string) (bytesCopied int)`. The lesson's long form also compiles, and gofmt does not change it.
- The standard library names results in interfaces when two results of different meaning would be unclear otherwise. `io.Reader` is `Read(p []byte) (n int, err error)` (`src/io/io.go`). On an implementation, named results also allow a bare `return`. CodeReviewComments ("Named Result Parameters") advises against naming results only for that. Name them when the name documents something, such as two results of the same type, or when a deferred function must change a result, such as an error from `Close`.
