# Chapter 15: Generics

## 15.1 Generics in Go

- `getLast[T any](s []T) T` returns `s[len(s)-1]`, or the zero value from `var zero T` when the slice is empty. `go test -race` passes all four cases.
- `var zero T; return zero` is the usual way to write a generic zero value. `return *new(T)` does the same in one line and also compiles. `T{}` does not work for every `T`, because `int` or `*int` have no composite literal.
- The zero value is ambiguous. Measured: `getLast([]int{})` and `getLast([]int{0})` both print `0`. Production code returns `(T, bool)`, as a comma-ok map lookup does. The standard library has no `slices.Last`. `slices.Max` makes the opposite choice and panics on an empty slice ("It panics if x is empty").
- Type inference: callers write `getLast(v)`, not `getLast[int](v)`, because `T` is inferred from the argument. An untyped `nil` argument gives the compiler nothing to infer from, so `getLast(nil)` fails with `in call to getLast, cannot infer T` and needs `getLast[*int](nil)` (measured).
- The course test compares the `T` result with an `any` field (`output != test.expected`). That compiles because a value is comparable with an interface value its type implements. The comparison is done at run time and is true only when the dynamic type and the value both match.

## 15.2 Why Generics?

Quiz:

1. Which code would generics be most likely to help with? **A binary tree.**
2. Go's approach to language design is... **Resist adding new features unless they're extremely important.**
3. Generics will probably be used more heavily in... **Library packages.**

Notes:

- The standard library shows where generics pay off: containers and algorithms that do not care about the element type. Examples: `slices` and `maps`, `cmp.Ordered`, `sync/atomic.Pointer[T]`, and the iterator types `iter.Seq[V]` and `iter.Seq2[K, V]`.
- Rule of thumb from the Go blog post "When To Use Generics" (Ian Lance Taylor): write the concrete code first, and add a type parameter only when the same logic repeats for different types. When the types differ in behavior rather than in data, use an interface. A method set gives dynamic dispatch, and a type parameter cannot replace it.
- Production note: in application code, generics fit small helpers. Examples: a typed ring buffer for sensor samples, a `Set[K comparable]`, or one decode-and-validate function for several message types. A device's protocol handlers differ in behavior, so they stay behind an interface.

## 15.3 Constraints

- `chargeForLineItem[T lineItem]` returns `nil, 0, errors.New("insufficient funds")` when `cost > balance`. Otherwise it appends `newItem` and subtracts the cost. A cost equal to the balance goes through, which is the right edge. `go test -race` passes.
- A constraint is an interface, so `T` can be the interface type itself. The course test passes `lineItem` values, so `T` is inferred as `lineItem`, not as `subscription`. The function body then calls `GetCost` through the interface as usual. A type parameter gives a different result from a plain `[]lineItem` parameter only when the caller passes a concrete slice such as `[]subscription`: the generic version returns `[]subscription`, and a non-generic version would not accept it.
- `append(oldItems, newItem)` writes into the caller's backing array when it has spare capacity. Measured: two calls on the same `make([]int, 2, 4)` history both returned `[0 0 20]`, because the second append overwrote the first. In production, copy before you append (`slices.Clip(oldItems)` forces a fresh array on the next append), or document that the function takes ownership of the slice.
- Production notes:
  - Return a sentinel, `var errInsufficientFunds = errors.New("insufficient funds")`, so callers can test it with `errors.Is` instead of comparing error strings, which the course test does.
  - Do not keep money in `float64`. Measured: `x, y := 0.1, 0.2; x+y == 0.3` is `false`. The constant expression `0.1+0.2 == 0.3` is `true`, because untyped constants are exact, and that hides the bug in small examples. Store integer cents (`int64`) or use a decimal type.

## 15.4 Interface Type Lists

Quiz:

1. Why might you create an interface using a type list? **You know exactly which types satisfy your interface.**

Notes:

- The lesson's `Ordered` is word for word `cmp.Ordered` (Go 1.21). Import it instead of writing your own. Since Go 1.21, the built-in `min` and `max` already take any ordered type and any number of arguments, so a `Min[T]` helper is not needed. Measured: `min(3, 1, 2)` is `1`.
- `~T` means "any type whose underlying type is `T`". Without the `~`, named types are rejected. Measured with `type celsius float64` against `interface{ float64 }`: `celsius does not satisfy exact (possibly missing ~ for float64 in exact)`. With `cmp.Ordered`, `lo(celsius(21.5), 19)` compiles and returns `19`. Domain types like `celsius`, `deviceID` or `canID` are why the standard constraints use `~` everywhere.
- An interface that contains a type list is a constraint only. It cannot be the type of a variable, field or parameter. Measured: `var x num` gives `cannot use type num outside a type constraint: interface contains type constraints`. Go has no sum types, so `int | float64` cannot be a runtime "either". Use a sealed interface with an unexported method, or a type switch over `any`.
- A constraint can list types and methods together, for example `interface{ ~int; String() string }`. A type must then satisfy both, and the body can use `+` and `<` as well as the method. Measured: `canID` with a `String` method passes. `type plain int` fails with `T (type plain) does not satisfy idLike (missing method String)`.

## 15.5 Parametric Constraints

- `biller[C customer]` declares `Charge(C) bill` and `Name() string`. `userBiller` satisfies `biller[user]` and `orgBiller` satisfies `biller[org]`. `go test -race` passes both tests.
- A generic interface is a family of interfaces, one for each type argument. Each instance is a separate type:
  - `biller` on its own is not a type. Measured: `[]biller{userBiller{}, orgBiller{}}` gives `cannot use generic type biller[C customer] without instantiation`.
  - `biller[user]` and `biller[org]` do not mix. Measured: `var _ biller[user] = orgBiller{}` gives `orgBiller does not implement biller[user] (wrong type for method Charge)`, with `have Charge(org) bill` and `want Charge(user) bill`.
  - So one slice cannot hold both billers. Code that must loop over every biller needs a non-generic interface (for example `Name() string` plus `Charge(customer) bill`), with a type assertion inside each `Charge`.
- What the parameter buys: `Charge` takes the concrete `user` or `org`, not the `customer` interface. A wrong pairing such as an `org` passed to a `userBiller` fails to compile instead of failing a type assertion at run time. The course's `testBiller[C customer](b biller[C], c C, ...)` infers `C` from the `c` argument and then checks `b` against `biller[C]`.
- Production note: `var _ biller[user] = userBiller{}` at package level is the usual compile-time check that a type implements an interface. It costs nothing at run time and fails the build as soon as a method signature drifts.

## 15.6 Naming Generic Types

Quiz:

1. The name of a type parameter... **...can be anything, but 'T' is a common convention.**

Notes:

- Standard library conventions: `T` for one arbitrary type (`atomic.Pointer[T any]`), `K` and `V` for map keys and values, and `E` for slice elements with `S` for the slice itself: `slices.Index[S ~[]E, E comparable](s S, v E) int`. The `S ~[]E` form keeps the caller's named slice type in the result. Measured with `type samples []float64`: `func[S ~[]E, E any](s S) S` returns `main.samples`, so `Mean()` still works on the result, while `func[E any](s []E) []E` returns plain `[]float64`. A domain letter is fine when it reads better, as `C customer` in 15.5 and `P product` in the 15.5 lesson text.
- `maps.Keys[Map ~map[K]V, K comparable, V any]` shows a longer name used where one letter would be unclear. Use a short, capitalized name, or a full word when several parameters are in play.
- A type parameter is an ordinary identifier, so it can shadow a predeclared type. Measured: `func double[int any](x int) int { return x + x }` fails with `operator + not defined on x (variable of type int/* type parameter */ constrained by any)`. Inside the function, `int` is the type parameter, not the built-in type.

## 15.7 Generic Structs

- `envelope[T any]` holds `recipient string` and `payload T`. `createEnvelopes[T any]` appends one `envelope[T]` per recipient and starts from `[]envelope[T]{}`, so no recipients gives an empty, non-nil slice. `go test -race` passes.
- Spec trap: "one entry per recipient, in the same order" means one envelope per element of `recipients`, not one per unique address. The lesson never mentions deduplication. The test checks `len(envelopes) == len(recipients)` and `envelopes[i].recipient == recipients[i]`. Deduplicating fails the count check and shifts every index after the first duplicate. Treat the function as a 1:1 map over its input, and let the caller decide whether duplicates are allowed.
- A generic struct literal always needs its type argument (`envelope[T]{...}`). Only function calls infer type arguments. Inside the generic function, the type parameter `T` that is in scope serves as the argument.
- The course test writes `var envelopes []envelope[T] = createEnvelopes(...)`, which staticcheck flags as ST1023. In a test, the explicit type is a compile-time assertion that the function returns `[]envelope[T]`.
- Production note: the payload is copied into each envelope only one level deep. Measured: with `tags []string` in the payload, `es[0].payload.tags[0] = "CHANGED"` also shows in `es[1]`. Before you fan one payload out to many senders, especially concurrent ones, make it immutable or deep-copy it per envelope. Otherwise one change reaches every message, and concurrent writes race.

## 15.8 Generic Methods

- `func (i inbox) Select[T any]() []T` starts from `[]T{}` and appends every event where the type assertion `e.(T)` succeeds. Order is kept, nothing matching gives an empty, non-nil slice, and `i.events` is only read. `go test -race` passes. golangci-lint v2.15.0 parses the Go 1.27 method type parameter; its only report is ST1023 in the course test.
- Go 1.27 adds type parameters on methods. Before 1.27 the same code had to be a top-level function, `func selectEvents[T any](in inbox) []T`, because only types and functions could take type parameters. Measured: the same file with `go 1.26` in `go.mod` fails with `generic method requires go1.27 or later`.
- `Select` takes no arguments, so `T` can never be inferred. Every call names it: `in.Select[email]()`. Measured: `in.Select()` gives `in call to in.Select, cannot infer T`. The method value `in.Select[receipt]` is an ordinary `func() []main.receipt` (measured).
- `e.(T)` behaves differently when `T` is an interface. It then matches every event whose dynamic type implements `T`, not one exact type. Measured: `Select[error]()` returns the `errors.New("boom")` event. A `nil` event never matches: `Select[any]()` on `{nil, 1, "s", err, receipt{5}}` returns 4 events, because a type assertion on a nil interface value fails even for `any`.
- Production note: `[]any` plus a type assertion is how event buses and CAN or MQTT message routers are often written. The generic method removes the per-type copies, but the event set stays open, so the compiler cannot report a missing case. When the set of message kinds is closed, a sealed interface with a type switch in one place keeps the dispatch in a single spot.

## 15.9 Generic Methods and Interfaces

Quiz:

1. Which type shown in the lesson implements `stringRepeater`? **`typedRepeater[string]`.**

Notes:

- A generic method never satisfies an interface method, even when one instantiation would match. Measured: `var _ stringRepeater = repeater{count: 3}` fails with `repeater does not implement stringRepeater (wrong type for method Repeat)`, with `have Repeat[T any](T) []T` and `want Repeat(string) []string`. Go infers type arguments for calls only, not for interface satisfaction.
- Interface methods cannot declare type parameters. Measured: `interface{ Repeat[T any](T) []T }` gives `interface method must have no type parameters`. A named interface type can take one instead: `type repeaterOf[T any] interface{ Repeat(T) []T }`, as `biller[C]` in 15.5.
- Generic methods are not in the runtime method set. Measured: `reflect.TypeFor[repeater]().NumMethod()` is `0`. Reasoned, not measured: each instantiation is generated at compile time from its call sites, so there is no single method for an interface table or `reflect` to point at. That explains both rules above.
- An explicit instantiation is an ordinary method value. Measured: `var f func(string) []string = repeater{count: 2}.Repeat[string]` works and prints `[Go Go]`. That is the adapter when a caller needs a plain function.
- Rule of thumb: put the type parameter on the struct (`typedRepeater[T]`) when the type must satisfy an interface or one value works with one element type. Put it on the method when one value serves many element types and is only called directly, as `inbox.Select[T]` in 15.8.
