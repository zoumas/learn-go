# Chapter 4: Functions

## 4.1 Functions

- Adjacent parameters of the same type can share one type: `func concat(s1, s2 string) string`. Every parameter still needs a type. `func f(x, y) int` does not mean "infer the type": the parser reads it as two unnamed parameters of types `x` and `y`. Measured: the compiler reports `undefined: x` and `undefined: y`, not a missing-type error.
- Function order in a file does not matter, and neither does order across files in a package. Package-level declarations are resolved before any body is checked.
- `s1 + s2` allocates a new string, because strings are immutable. One expression with several operands is still one allocation. Measured with `testing.AllocsPerRun`: `a + b + c + d` makes 1 allocation. `s += a` in a loop of 100 makes 99, and the copying is quadratic in the final length. A `strings.Builder` with `Grow` makes 1. Build log lines or payloads in a loop, for example joining decoded CAN frame fields, with `strings.Builder`, `strings.Join`, or `fmt.Fprintf` to a writer.

## 4.2 Multiple Parameters

Quiz:

1. Which is the shortest and clearest way to write a valid function signature? `func createUser(firstName, lastName string, age int)`. The form `firstName string, lastName string, age int` is valid but longer. The form `firstName, age, lastName string int` does not compile.

Notes:

- A type applies to the run of names before it, back to the previous type. Grouping only works for adjacent parameters, so `firstName string, age int, lastName string` cannot be shortened without reordering.
- Two types in a row is a syntax error. Measured: `func createUser(firstName, age, lastName string int)` fails with `syntax error: unexpected name int in parameter list; possibly missing comma or )`. Mixing named and unnamed parameters also fails: `func f(a int, string)` gives `syntax error: missing parameter type`.
- `gofmt -s` does not merge repeated types. The gocritic check `paramTypeCombine` does. Measured: it reports `func(firstName string, lastName string, age int) could be replaced with func(firstName, lastName string, age int)`. It is off by default in golangci-lint.
- Several adjacent parameters of one type are easy to swap at the call site, and the compiler cannot catch it: `createUser("Smith", "Jane", 30)` compiles. In production, a struct parameter or distinct named types (for example `type DeviceID string` and `type Topic string` in an IoT publisher) make a swap a compile error.

## 4.3 Unit Test Lessons

- A `main` package with no `func main` passes `go vet` and `go test`, but `go build` fails. Measured: `runtime.main_main·f: function main is undeclared in the main package`. The course's test-driven lessons rely on this. In a real project, put the function in a non-`main` package and keep `main` thin.
- `100 * penniesPerDollar` is a constant expression. The compiler folds it to `10000`, so it costs nothing at run time. An untyped constant takes its type from context, here `int` from the return type. The first version named the constant `inPennies`, which reads like a unit label. `penniesPerDollar` says what the factor is.
- Prices are integer pennies, which is the 2.8 advice: integer minor units, no float rounding. An unknown tier still returns `0` with no error, the same problem as the plan switch in 3.3.
- The course's test builds `submitCases := append(runCases, ...)`. That is safe only because a slice literal has `cap == len`, so `append` must copy. Measured: with `run := []int{1, 2, 3}` (cap 3), changing the appended slice left `run[0]` at `1`. With `make([]int, 3, 8)`, the appended slice shared the backing array: writing `sub2[0] = 99` changed the original, and a second `append` to the original overwrote `sub2[3]`. In a pipeline that fans one base slice out to several goroutines, the second case is also a data race. Use `slices.Concat(run, extra)` or `slices.Clip(run)` first when the base slice may have spare capacity.
- The provided test prints pass/fail lines with `fmt` and loops without `t.Run`. Production style is table-driven subtests (`t.Run(tc.tier, ...)`) so that `go test -run 'Test/premium'` selects one case and a failure names the case.

## 4.4 Declaration Syntax

Quiz:

1. What are we talking about when we discuss "declaration syntax"? The style of language used to create new variables, types, functions, and so on.
2. Which language's declaration syntax reads like English from left to right? Go.
3. Given `var f func(func(int,int) int, int) int`, what is `f`? A function named `f` that takes a function and an int as arguments and returns an int.

Notes:

- Further reading: Rob Pike, "Go's Declaration Syntax", https://go.dev/blog/declaration-syntax.
- Strictly, `var f func(...) int` declares a variable of function type, not a function. Its zero value is `nil`. Measured: `%T` prints `func(func(int, int) int, int) int`, `f == nil` is `true`, and calling a nil function panics with `invalid memory address or nil pointer dereference`. Check optional callbacks, such as an `OnMessage` hook on an MQTT client config, for `nil` before calling them.
- Types read left to right in every position: `[]*[3]int` is a slice of pointers to arrays of 3 ints. `%T` prints it the same way.
- A named function type makes a long signature readable, but it is a different type. Measured: with `type binOp func(int, int) int`, a `func(binOp, int) int` is not assignable to `func(func(int, int) int, int) int`. The compiler reports `cannot use g (variable of type func(binOp, int) int) as func(func(int, int) int, int) int value in assignment`. An alias, `type binOpAlias = func(int, int) int`, keeps the types identical and the assignment compiles. A function literal is assignable to a named function type, because the literal's type is unnamed.

## 4.5 Passing Variables by Value

- Go passes every argument by value. For slices, maps, channels, pointers and functions, the value copied is a small header or pointer that refers to shared data. That is why they look like "pass by reference", and it is not the same thing. Measured:
  - Slice: `s[0] = 99` inside the function is visible to the caller. An `append` that exceeds capacity gives the function a new backing array, so a later `s[1] = 77` is not visible. The caller still saw `[99 2 3]`.
  - Map: `m["k"] = 1` is visible to the caller. Assigning a new map to the parameter is not: the caller's nil map stayed `nil`.
  - Struct: a `frame` with an `[8]byte` array is copied whole, so `f.data[0] = 0xFF` on the copy left the caller's byte at `0`. Through `*frame`, the caller saw `255`.
- Arrays are values, unlike C, where an array decays to a pointer. A CAN frame struct with a `[8]byte` payload is 12 bytes or more and cheap to copy. Pass it by value unless the function must change it.
- Returning the result, as this lesson does, is the idiomatic fix. An out-parameter (`func getBill(..., bill *int)`) is C style and rare in Go.
- `var lastMonthBill int` followed by `lastMonthBill = getBillForMonth(...)` is two lines where `lastMonthBill := getBillForMonth(...)` is one. The `var` declarations look like starter code; that could not be checked. Here, `return getBillForMonth(c, this) - getBillForMonth(c, last)` reads just as well.

## 4.6 Ignoring Return Values

- An unused local variable is a compile error. Measured: `q, p, extra := three()` with `extra` unused fails with `declared and not used: extra`. Unused package-level variables and unused function parameters compile.
- The left side must match the number of results. Measured: `x := three()` fails with `assignment mismatch: 1 variable but three returns 3 values`. `:=` also needs at least one new name: `_, _, _ := three()` fails with `no new variables on left side of :=`. Use `=` there, or call the function bare.
- A bare call that discards every result compiles: `three()` and `os.Remove("nope")` both build. The compiler never forces you to read an error. golangci-lint's `errcheck` does. Measured: ``Error return value of `os.Remove` is not checked (errcheck)``. Writing `_ = os.Remove(...)` silences it and tells the reader the discard is deliberate.
- In production, `_` on an `error` is the case to review. On a device, an ignored error from `Close` on a file opened for writing can hide a failed flush to flash. The usual pattern is a named error result and a deferred close that joins its error in, or `errors.Join`.
- The starter's `if`/`else if` chain on `tier` gives staticcheck QF1003 (`could use tagged switch on tier`). It is starter code, not a finding.

## 4.7 Named Return Values

- Named results with the same type can share it, as in 4.2: `(yearsUntilAdult, yearsUntilDrinking, yearsUntilCarRental int)`. Repeating `int` three times is valid but longer.
- A naked `return` cannot return a named result that is shadowed at that point. Measured: `n, err := strconv.Atoi(s)` inside an `if` block, followed by a bare `return` in that block, fails with `result parameter err not in scope at return` and `inner declaration of var err error`. The compiler catches only that case. If the block uses the inner `n` and `err` and then falls through to a bare `return` after the block, the function returns the outer zero values. Measured: `parse("x")` and `parse("42")` both returned `0 <nil>`, and `go vet` reported nothing.
- A deferred function can change a named result after `return` has set it. With an unnamed result it cannot. Measured: a `defer` that set `err` on a local variable left the function returning `<nil>`. With a named `err`, a deferred `recover` turned `panic("boom")` into the returned error `"recovered: boom"`. Defers run last-in first-out, so in that run the `errors.Join(err, errors.New("close failed"))` defer, which was registered second, ran first, and the `recover` defer then overwrote its result. Order the defers with that in mind. This is the main production use of named results: `defer func() { err = errors.Join(err, f.Close()) }()` on a file opened for writing (see 4.6).
- CodeReviewComments "Named Result Parameters": name results when it documents them, for example several results of one type, as here. Do not name them only to allow a naked return. Avoid naked returns in anything longer than a few lines.
- Since Go 1.21, the built-in `max` replaces each clamp: `yearsUntilAdult = max(0, 18-age)`. Measured: `max(0, 18-30)` is `0` and `max(0, 18-4)` is `14`. The lesson body is fixed, so this is for later code.

## 4.8 The Benefits of Named Returns

Quiz:

1. When might you use naked returns? For small functions.
2. When should named returns be used? When there are many values being returned.

Notes:

- The names are part of the documentation. Measured: `go doc` prints the full signature, `func Calculator(a, b int) (mul, div int, err error)`. For two results of the same type, such as `(mul, div int)`, the names are the only thing that tells the caller which is which.
- Linting naked returns: golangci-lint's `nakedret` is off by default. Enabled with its defaults, it flagged a naked return in a 34-line function (``naked return in func `long` with 34 lines of code (nakedret)``) and not one in a 3-line function. Its documented default limit is 30 lines.
- The lesson's `b == 0` guard is required, not defensive. Integer division by zero panics at run time: `panic: runtime error: integer divide by zero`. A constant divisor is caught at compile time: `invalid operation: division by zero`. Floats do not panic: `1/f` with `f == 0` gives `+Inf`, and `-1/f` gives `-Inf`. A sensor pipeline that computes rates with `float64` can pass `Inf` or `NaN` downstream with no error, so check the divisor or test with `math.IsInf` and `math.IsNaN`.
- The lesson's named version still writes `return mul, div, nil`. That is the usual recommendation: name results for documentation and keep explicit returns.
