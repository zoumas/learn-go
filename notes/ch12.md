# Chapter 12: Packages and Modules

## 12.1 Packages

- Only `package main` with a `func main()` builds an executable. The same file under `package mailio` still compiles: `go build` exits 0, writes no binary, and `func main` is an ordinary unexported function. `go run` refuses it with `package pkg/lib is not a main package`.
- `math/rand` has been seeded randomly at startup since Go 1.20, and since Go 1.24 `rand.Seed` does nothing (`GODEBUG=randseednop=0` restores the old behavior). Older examples that call `rand.Seed(time.Now().UnixNano())` are dead code now. New code uses `math/rand/v2`, or `crypto/rand` for anything security-related such as tokens or keys.
- Production note: keep `package main` thin. Parse flags and config, build dependencies, and call into library packages. `main` cannot be imported, so code that lives there cannot be tested or reused from another binary. A repo with several binaries puts each one in `cmd/<name>/`.

## 12.2 Package Naming

Quiz:
- What would be the conventional package name of a package with the path `github.com/wagslane/parser`? Answer: `parser`.
- Given the import path `path/to/rand`, which of these package names are allowed by the Go compiler: `spam`, `random`, `rand`, `path`? Answer: any of these.

Notes:
- The import path finds the directory. The `package` clause sets the name the code uses. Measured: a directory `path/to/rand` holding `package spam` imports as `"pn/path/to/rand"` and is called as `spam.Eggs()`. Nothing at the import site shows the name `spam`, which is why the convention exists. When a name must differ, write it at the import: `spam "pn/path/to/rand"`.
- Two packages in one directory fail with `found packages a (a.go) and b (b.go) in .../mixed`. The one exception is an external test package: `package spam_test` in a `_test.go` file next to `package spam` builds and runs. Any other suffix fails, for example `package other_test` gives `found packages other (o_test.go) and spam (r.go)`.
- A repo or directory named with a dash, such as `go-parser`, cannot be the package name, because `-` is not valid in an identifier. Name the package `parser`.
- Production note: name packages by what they provide, short and lowercase, without `util`, `common` or `helpers`. Callers read the name at every call site, so avoid repeating it in exported names: `can.Frame`, not `can.CANFrame`.

## 12.3 Install

CLI lesson: install Go 1.27 or newer and the `bootdev` CLI, then run `bootdev run <lesson-id>`. The check "Check Go is installed" passed.

- Local setup: `go version` prints `go1.27.3-X:nodwarf5 linux/amd64` for the Arch package at `/usr/bin/go` (`GOROOT=/usr/lib/go`). The `-X:nodwarf5` suffix means the toolchain was built with `GOEXPERIMENT=nodwarf5`, and `go env GOEXPERIMENT` prints `nodwarf5`, so binaries built here default to DWARF 4 debug info instead of DWARF 5. Measured with `readelf --debug-dump=info`: `Version: 4` by default, `Version: 5` with `GOEXPERIMENT=dwarf5`.
- `GOBIN=~/.local/bin` is set, so `go install` puts binaries there instead of `$GOPATH/bin` (`~/go/bin`). `GOPATH` (`~/go`) now holds only the module cache and the default install directory. Code no longer has to live under it.
- The `go` line in `go.mod` is a minimum toolchain version, not a hint. Measured: with `go 1.99.0` and `GOTOOLCHAIN=local`, the build fails with `go: go.mod requires go >= 1.99.0 (running go 1.27.3; GOTOOLCHAIN=local)`. With the default `GOTOOLCHAIN=auto`, `go` downloads the newer toolchain into the module cache instead.
- Production note: pin the toolchain per repo with the `go` line and an optional `toolchain` line in `go.mod`, rather than relying on what is installed on each machine. CI images and developer laptops then build with the same compiler. In an offline build, such as a Yocto recipe or an air-gapped device build, set `GOTOOLCHAIN=local` so the build fails clearly instead of trying to download a toolchain.

## 12.4 Modules

Quiz:
- What is a Go module? Answer: a collection of packages that are released together.
- Do packages in the standard library have a module path prefix? Answer: no.
- What is the import path for a package outside the standard library? Answer: a module path plus the package subdirectory.

Notes:
- Measured with `go list`: `fmt` reports `std=true`, no module, and lives in `/usr/lib/go/src/fmt`. `ch12/l01` reports module `github.com/zoumas/learn-go` and import path `github.com/zoumas/learn-go/ch12/l01`, which is the module path joined with the directory.
- A module path does not have to be a real URL until someone downloads it. A local `module nodot` builds fine, but fetching a path without a dot fails: `go: malformed module path "nodotpath/foo": missing dot in first path element`. Dotless first elements are left for the standard library, which is why `fmt` and `net/http` cannot clash with a module.
- The lesson says `go` consults the repository at the module path. By default it does not. `go env GOPROXY` is `https://proxy.golang.org,direct`, so `go` asks the public module proxy first and contacts the repository only when the proxy cannot serve it. Every download is checked against the checksum database in `GOSUMDB` (`sum.golang.org`) and recorded in `go.sum`.
- Production note: for company modules on a private Git host, set `GOPRIVATE` to the host or path prefix (for example `GOPRIVATE=gitlab.example.com/*`). That skips both the public proxy and the checksum database, so private module paths are not sent to Google's servers, and `go` fetches them with Git directly using your SSH or HTTPS credentials. Without it, `go` asks the public proxy and the public checksum database about the private path (`go help private`: by default it validates every download "regardless of source" against `sum.golang.org`), and the checksum database cannot know a private module, so verification fails.

## 12.5 Go Environment

Quiz:
- Do you need to put your code inside of your GOPATH? Answer: no, in fact you shouldn't.

Notes:
- Here `GOPATH` is `~/go` and holds only `bin` and `pkg` (the module cache at `~/go/pkg/mod`). There is no `src`, and this repo lives at `~/work/repos/github.com/zoumas/learn-go`, which follows the lesson's "workspace by remote path" layout.
- Module mode is the default: `go env GO111MODULE` prints an empty value, which means on. Measured outside any module: `go build .` fails with `go: go.mod file not found in current directory or any parent directory; see 'go help modules'`, while `go run m.go` with a file argument still works. GOPATH mode is not removed in Go 1.27: `GO111MODULE=off go build .` in the same directory succeeded. Old tutorials that set `GO111MODULE=off` or tell you to work in `$GOPATH/src` still "work", which is why they mislead.
- Production note: `$GOPATH/pkg/mod` is the module cache shared by every project. Its files are read-only, so delete it with `go clean -modcache`, not `rm -rf`. In CI, cache that directory (or `go env GOMODCACHE`) together with `go env GOCACHE` (the build cache) to make builds fast. These two caches are what the old GOPATH has become.

## 12.6 First Local Program

CLI lesson: `mkdir hellogo`, `go mod init {REMOTE}/{USERNAME}/hellogo`, `cat go.mod`, then `bootdev run` from the module root. The check runs `cat go.mod` in the current directory and expects `hellogo` in it, so running it from the repo root failed: it read `learn-go`'s own `go.mod`.

- The module lives at `ch12/hellogo` with the path `github.com/zoumas/learn-go/ch12/hellogo`. A module path that extends the repo's root module path is the normal layout for a multi-module repository (for example `golang.org/x/tools/gopls` inside `golang.org/x/tools`). Its version tags would be prefixed with the directory, `ch12/hellogo/v1.0.0`.
- A directory with its own `go.mod` is cut out of the parent module. Measured: from the parent, `go list ./...` does not list the nested module, and `go vet ./...` passed although the nested `main.go` contained a self-assignment. The repo gates must also be run inside `ch12/hellogo`.
- `go mod init` writes the running toolchain's full version into the `go` line (`go 1.27.3`), which makes Go 1.27.3 the minimum for anyone building the module (see 12.3). For a library, lower it to the oldest version you support.

## 12.7 Go Run

- `go run main.go` compiles only the files named on the command line. Measured with `main.go` calling `greet()` defined in `greet.go`: `go run main.go` fails with `./main.go:5:15: undefined: greet` in package `command-line-arguments`, while `go run .` builds the whole package and prints `hi`. Use `go run .` once a program has more than one file.
- The binary is built in a temporary directory (`go run -work .` printed `WORK=/tmp/go-build535826846`) and deleted afterwards. Nothing is written to the working directory.
- `go run` does not pass on the program's exit code. Measured: a program ending with `os.Exit(3)` printed `exit status 3`, and `go run` itself exited with `1`. Scripts and CI steps that check exit codes need `go build` and the binary.
- Production note: `go run` is for development. A service on a device or in a container runs a built binary: it starts without compiling, does not need the toolchain on the target, and returns its own exit code to systemd or the container runtime.

## 12.8 Go Build

CLI lesson: `go build` in `hellogo`, then `./hellogo`. No code change. The binary is kept out of Git by a local `.git/info/exclude` entry, `/ch12/hellogo/hellogo`.

- `go build` names the binary after the last element of the module path (`hellogo`) and writes it to the current directory. `go build -o path` sets another name.
- "Statically linked" holds only while cgo is not involved. Measured with `file`: `hellogo` is `statically linked`. A program that imports `net`, built with the default `CGO_ENABLED=1`, is `dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`. With `CGO_ENABLED=0` the same program is `statically linked`. `net` and `os/user` use the C resolver when cgo is on.
- Size: the default `hellogo` is 2,408,094 bytes. `-ldflags='-s -w' -trimpath` (strip the symbol table and DWARF, remove local paths) brings it to 1,507,488 bytes. `-trimpath` also makes the build reproducible across machines.
- Cross-compiling needs no extra toolchain: `GOOS=linux GOARCH=arm64 go build` produced `ELF 64-bit LSB executable, ARM aarch64` (2,408,930 bytes) on this amd64 machine. That stops being true once cgo is on, which then needs a C cross-compiler for the target.
- Production note: for an embedded Linux target, build with `CGO_ENABLED=0 GOOS=linux GOARCH=arm64` (or `GOARCH=arm GOARM=7`), `-trimpath` and `-ldflags='-s -w'`. The result is one static file to copy onto the device, with no dependence on the device's libc version. Set the version at build time with `-ldflags='-X main.version=...'`, or read it back with `debug.ReadBuildInfo`, which includes the VCS revision.

## 12.9 Go Install

CLI lesson: `go install` in `hellogo`, then run `hellogo` from any directory. No code change.

- `go install` writes to `GOBIN` if it is set, otherwise to `$GOPATH/bin`. Here `GOBIN=~/.local/bin`, so the binary is `~/.local/bin/hellogo` and `~/go/bin/hellogo` does not exist. `which -a hellogo` shows which copy the shell runs.
- `GOBIN` blocks cross-compiled installs. Measured: `GOARCH=arm64 go install` fails with `go: cannot install cross-compiled binaries when GOBIN is set`. Without `GOBIN`, such binaries go to `$GOPATH/bin/linux_arm64/`. Use `go build -o` for target binaries.
- `go install pkg@version` (`@latest`, `@v1.2.3`) builds in module-aware mode and ignores the `go.mod` in the current directory (`go help install`). This is how to install a CLI tool, such as the `bootdev` CLI or `golangci-lint`, from anywhere without touching a project's dependencies.
- Production note: tools a project needs for its own build (code generators, linters) belong in its `go.mod` rather than in each developer's `GOBIN`. `go get -tool <pkg>` adds a `tool` line (Go 1.24+), and `go tool <name>` runs that pinned version. This replaces the older `tools.go` file with blank imports. Everyone, including CI, then runs the same generator version.

## 12.10 Custom Package

CLI lesson: a `mystrings` module next to `hellogo` (`ch12/mystrings`, path `github.com/zoumas/learn-go/ch12/mystrings`), holding the course's `Reverse`. `go build` in a library package compiles it into the build cache and writes no file.

- A comment directly above `package` is the package doc comment. Measured: `go doc .` prints `by convention, we name our package the same as the directory` as the package description. Doc comments start with the name they document: `// Package mystrings provides ...` and `// Reverse returns ...`. A comment that is not documentation needs a blank line between it and the `package` clause.
- `for _, v := range s` decodes UTF-8 runes, so `"héllo"` (with the precomposed `é`) reverses to `"olléh"`. A rune is not a character as a reader sees it, though. Measured: `"héllo"` (an `e` plus a combining accent) gives `"olĺeh"`, with the accent moved onto the `l`. `"👍🏽x"` gives `"x🏽👍"`, with the skin tone split from its emoji. An invalid byte becomes U+FFFD: `"a\xffb"` gives `"b�a"`. Correct reversal works on grapheme clusters, which the standard library does not provide.
- Prepending to a string copies the whole result on every rune, so the course's `Reverse` is O(n²). Measured on ASCII input: 100 bytes took 7.8 µs and 100 allocations, 10,000 bytes took 18.9 ms, 10,001 allocations and 53 MB. Converting to `[]rune` and swapping in place took 98 µs and 2 allocations at 10,000 bytes. 100 times the input cost about 2,400 times the time.
- Production note: building a string in a loop with `+` is the pattern to look for in a review. Use `strings.Builder` with `Grow`, or work on a `[]byte` or `[]rune` and convert once. In a pipeline that formats every message, the quadratic version turns into GC pressure long before it shows up as CPU time.

## 12.11 Custom Package Continued

- `hellogo` imports `mystrings` through `require github.com/zoumas/learn-go/ch12/mystrings v0.0.0` plus `replace ... v0.0.0 => ../mystrings`. `go run .` prints `dlrow olleh`. The `v0.0.0` is a placeholder: no such version exists anywhere, and the `replace` points it at the directory. A local directory replacement needs no checksum, so no `go.sum` was created.
- The lesson's `go build ./hellogo` from the parent directory does not work in this repo. `ch12` belongs to the root module, so it fails with `main module (github.com/zoumas/learn-go) does not contain package github.com/zoumas/learn-go/ch12/hellogo`. Build from inside `ch12/hellogo`.
- `replace` takes effect only in the main module being built. Measured: `app` requires `lib`, and `lib`'s `go.mod` has `replace example.com/mystrings => ../mystrings`. Building `app` ignored that replace and tried to download the module: `go: downloading example.com/mystrings v0.0.0`, then `module lookup disabled by GOPROXY=off`. A library that depends on a `replace` cannot be used by anyone else.
- Production note: a committed `replace` to a sibling directory is fine inside one repo that is always built as a whole. For editing a library and an application together across repos, use an uncommitted `go.work` (`go work init ./app ./lib`) instead of editing `go.mod`. Before release, remove the `replace`, tag the library, and `require` the real version.

## 12.12 Remote Packages

- `datetest` requires `github.com/wagslane/go-tinytime v0.0.2` from `go get`, with no `replace`. `go run .` prints `1585750374 converted to a tinytime is: 2020-04-03T14:12:54Z` (2020-04-01 plus 48 hours, in UTC). `go mod verify` reports `all modules verified`, and `go mod tidy` left `go.mod` and `go.sum` unchanged.
- The `tinytime` alias at the import is not required, because the package clause is already `package tinytime`. It is good style anyway: the import path ends in `go-tinytime`, so without the alias a reader cannot tell which name the code uses (see 12.2).
- `go.sum` lists modules the program never imports, such as `testify` and `yaml.v2`. They come from the dependency's own `go.mod` (`go-tinytime` requires `testify v1.5.1`, which requires the rest). `go mod why -m github.com/stretchr/testify` traces it through `github.com/wagslane/go-tinytime.test`, the dependency's tests. `go.sum` records checksums for the module graph, not only for compiled code.
- What "tiny" costs: `unsafe.Sizeof` is 4 bytes for `TinyTime` against 24 for `time.Time`, because it stores Unix seconds in a `uint32`. That runs out on `2106-02-07T06:28:15Z`. `FromTime` returns an error past that point, but `Add` does not: measured, adding one hour to the last value gives `1970-01-01T00:00:00Z` with no error.
- Production note: before adding a dependency, check its maintenance status, license, transitive graph (`go mod graph`) and known vulnerabilities (`govulncheck ./...`). The module cache protects the build from a deleted upstream repository (the proxy keeps a copy), but not from a bug like the silent `Add` overflow. For a type as small as this one, copying the few lines you need is often better than taking the dependency ("a little copying is better than a little dependency").
