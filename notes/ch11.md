# Chapter 11: Pointers

## 11.1 Introduction to Pointers

- A pointer is one machine word: `unsafe.Sizeof(&m)` is 8 on amd64. Its zero value is `nil`, and `fmt.Println` prints a nil `*int` as `<nil>`. Dereferencing it panics with `invalid memory address or nil pointer dereference`.
- `fmt` follows a pointer to a struct one level: `%v` on `&m` prints `&{Pumpkin hi}` and `%+v` prints `&{Recipient:Pumpkin Text:hi}`. A pointer to anything else, such as a `*string`, prints as an address. Format verbs that "look right" on a struct pointer can hide that a pointer was passed.
- Returning `&x` for a local `x` is safe in Go, unlike C. The compiler moves `x` to the heap: `go build -gcflags=-m` reports `moved to heap: x`. Passing `&m` to `fmt.Printf` also moves `m` to the heap, because `fmt` takes `any` and the compiler cannot prove the pointer does not escape.
- Production note: take a pointer when the callee must change the value, when the value is large, or when the type holds something that must not be copied (`sync.Mutex`, see `go vet`'s `copylocks`). Small read-only structs like `Message` (two strings, 32 bytes) are fine to pass by value.

## 11.2 References

- Strings are immutable, so `*message = s` does not edit the caller's bytes. It replaces the caller's string header (pointer and length) with one that points to the new text. The pointer is what lets the function change which string the caller's variable holds.
- A `nil` `*string` panics on the first `*message` with `invalid memory address or nil pointer dereference`. The course signature has no error return, so the choice is to document "must not be nil" or to return early on `nil`.
- `strings.ReplaceAll` returns its input unchanged when there is no match. Measured: three passes over clean text make 0 allocations, and 3 when every word matches. `strings.NewReplacer("fubb", "****", ...)` does one pass, but it is not cheaper here: measured, 3 allocations on clean text and 3 on dirty text. Measure before swapping one for the other.
- Plain substring replacement also hits words that contain the target. Measured: `"Switch the witchcraft"` becomes `"S***** the *****craft"`. The course's "mother****er" case depends on this. A real filter matches on word boundaries.
- Production note: a function that rewrites its input through a pointer is harder to test and to use concurrently than `func clean(s string) string`. Return the new string and let the caller assign it. Pointer parameters fit best when the value is large or must be shared, not for a 16-byte string header.

## 11.3 Pass by Reference

- Go has no pass by reference. Every argument is copied, and a pointer argument is a copied address. The function can change what the address points to, but assigning a new pointer to `a` inside it changes only its own copy (the same rule as maps in 10.2 and slice headers in 9.3).
- `a.MessagesTotal` on a pointer is shorthand for `(*a).MessagesTotal`. The lesson's wrong form fails with `invalid operation: cannot indirect a.MessagesTotal (variable of type int)`, because `*` binds after the selector: it means `*(a.MessagesTotal)`.
- `a.MessagesTotal++` is a read, an add and a write, not one step. Measured: 1000 goroutines calling `analyzeMessage` on one `Analytics` gave `{950 495 486}` without `-race`: 50 updates were lost, and `495 + 486 = 981` no longer equals the total of 950. With `-race`: `Found 6 data race(s)`.
- Production note: a shared counter struct needs a `sync.Mutex` around the whole update, or `atomic.Int64` fields. Atomics make each field correct but not the set: a reader can still see `Total` updated and `Failed` not yet. If the fields must agree, use the mutex, or drop the derived field and compute `Total` as `Succeeded + Failed` when read. For a telemetry pipeline with many workers, per-worker counters merged at read time avoid contention entirely.

## 11.4 Pointers Quiz

Quiz (code: `var x int = 50`, `var y *int = &x`, `*y = 100`):
- What is the value of `*y` after the code runs? Answer: `100`.
- What is the value of `x` after the whole block runs? Answer: `100`.

Notes:
- `*y = 100` writes through the pointer into `x`. `y` itself does not change: it still holds `&x`, so `y == &x` is `true`. `*y` and `x` name the same variable.
- Taking an address does not by itself move a variable to the heap. Escape analysis decides. With `-gcflags=-m`, a variable that must live on the heap is reported as `moved to heap: x`. A line like `x escapes to heap` next to `fmt.Println(x)` is about the copy boxed into the `any` argument, not about `x`.
- Since Go 1.26, `new` takes an expression: `p := new(50)` gives a `*int` pointing at `50`. It replaces the `v := 50; p := &v` pattern and helper functions like `ptr[T any](v T) *T` used to fill optional pointer fields in JSON or AWS SDK structs (`aws.String`, `aws.Int32`).

## 11.5 Nil Pointers

- The nil check must come before the first `*message`. Copying `*message` into a local first, as 11.2 did, is the dereference that panics.
- A nil dereference is a runtime panic, `runtime error: invalid memory address or nil pointer dereference`, raised from a `SIGSEGV`. `recover()` in a deferred function of the same goroutine catches it.
- A panic in another goroutine kills the whole process. Measured: a nil dereference inside `go func() { ... }()` exited the program, and the deferred `recover()` in `main` never ran. Each worker goroutine that must survive bad input needs its own `defer recover()`.
- A nil pointer stored in an interface is not a nil interface. Measured: passing a nil `*strings.Reader` to `func check(r io.Reader)` gives `r == nil` as `false`, while passing a literal `nil` gives `true`. The `== nil` check in this lesson works because the parameter is a concrete `*string`.
- Production note: check for nil where untrusted data enters (a decoded optional JSON field, a missing CAN signal in a parsed frame), and treat nil inside the core as a programming error rather than guarding every function. A silent early return, as in this lesson, hides the caller's bug. Where nil is a valid input, say so in the doc comment.

## 11.6 Pointer Receivers

Quiz:
- Which is more widely used in Go? Answer: pointer receivers.

Notes:
- `c.setColor("blue")` on a `car` variable is shorthand for `(&c).setColor("blue")`. Go only does this when `c` is addressable. A map element or a composite literal is not: `m["a"].setColor("blue")` and `car{}.setColor("x")` both fail with `cannot call pointer method setColor on car`.
- Method sets: `*car` has both pointer and value methods, `car` has only value methods. A `car` value therefore does not satisfy an interface that needs a pointer method: `car does not implement colorer (method setColor has pointer receiver)`. Store `&car{}` in the interface.
- `for _, c := range cars { c.setColor("blue") }` changes a copy of each element. Measured: the slice stays `[{white} {white}]`. Index with `cars[i].setColor("blue")` to change the elements.
- A value receiver copies the struct, including any lock in it. `go vet` reports `get passes lock by value: recv/b.counter contains sync.Mutex`. A copied mutex does not protect the original.
- Production note: use a pointer receiver when the method changes the receiver, when the struct is large, or when it holds a `sync.Mutex` or other non-copyable state. If one method needs a pointer receiver, give all of the type's methods pointer receivers (Go Code Review Comments). Mixed receivers make the method set hard to predict when the type is stored in an interface. Small immutable values such as `time.Time` keep value receivers.
