# Chapter 7: Errors

## 7.1 The Error Interface

- `customerCost, err := ...` followed by `spouseCost, err := ...` does not create a second `err`. `:=` needs at least one new name on the left, and names that already exist in the same scope are assigned, not redeclared. Measured: `&err` is the same address after both statements. In an inner scope, such as an `if` block, `:=` creates a new `err` that shadows the outer one.
- Returning `err` unchanged loses which send failed: both failures give `can't send texts over 25 characters`. In production, wrap it with context, for example `fmt.Errorf("send to spouse: %w", err)`. The lesson's test compares `Error()` strings exactly, so wrapping would fail it here.
- Partial failure: when the spouse message fails, the customer message was already sent and paid for, but the function returns `0`. Returning the zero value with a non-nil error is the convention the lesson asks for, and it hides the cost already spent. A billing or publish path, such as two MQTT publishes to AWS IoT, has to decide this on purpose: return the partial result with the error and document it (as `io.Writer.Write` does with `n`), or make the operation retryable and idempotent.
- The test compares error strings because two errors made by separate calls are never equal. Measured: `fmt.Errorf("x") == fmt.Errorf("x")` and `errors.New("x") == errors.New("x")` are both `false`, because each call returns a new pointer. Code that must recognize an error uses a sentinel variable and `errors.Is` (lesson 7.5).
- `fmt.Errorf` without `%w` returns the same type as `errors.New`. Measured with `%T`: `*errors.errorString` without `%w`, and `*fmt.wrapError` with one `%w`.

## 7.2 Formatting Strings Review

- `%.2f` rounds the exact binary value of the float, and an exact tie rounds to even. Measured: `2.675` gives `2.67`, because the stored value is `2.67499999999999982236`. `0.125` gives `0.12` and `0.375` gives `0.38`: both are exact in binary, so they are true ties and round to the even digit. `1.005` gives `1.00`.
- Money in a `float64` is the lesson's simplification. Measured: with variables, `0.1 + 0.2` is `0.30000000000000004` and `== 0.3` is `false`. The same expression on untyped constants is `true`, because constant arithmetic is exact, so a quick test with literals hides the problem. Production billing stores integer minor units (`int64` cents) or uses a decimal type, and formats only at the edge.
- `go vet` checks `Sprintf` verbs against argument types. Measured: `%d` with `1.4` gives `fmt.Sprintf format %d has arg 1.4 of wrong type float64`. golangci-lint runs the same check (`printf` in `govet`).
- `'%s'` wraps the value in quotes without escaping it. Measured: `"it's\n"` prints as `'it's` with a raw newline in the middle of the log line. `%q` gives `"it's\n"`, a Go-quoted string that keeps one log entry on one line. Use `%q` for untrusted values such as device IDs or payloads in logs.
- For logs that backend developers search, prefer structured logging with `log/slog` over one interpolated string. Measured with `slog.NewTextHandler`: `level=ERROR msg="sms not sent" cost=1.4 recipient="+1 (435) 555 0923"`. The handler quotes values that need it, and log tooling can filter by `recipient`.

## 7.3 The Error Interface

- `divideError` has a value receiver, so both `divideError` and `*divideError` satisfy `error`. The function returns a value, and that decides which target `errors.As` matches. Measured: `errors.As(err, &dv)` with `var dv divideError` is `true`, and `errors.As(err, &dp)` with `var dp *divideError` is `false`. The standard library mostly returns pointers (`*os.PathError`, `*strconv.NumError`). Pick one form and keep to it, because callers must match it exactly.
- A struct error with comparable fields compares by value, unlike `errors.New`, which returns a new pointer each call (see 7.1). Measured: `err == divideError{10}` and `errors.Is(err, divideError{10})` are both `true`. After `fmt.Errorf("query: %w", err)`, `==` is `false` and `errors.Is` is still `true`, because `errors.Is` walks the wrapped chain.
- A function whose result is `error` must return a literal `nil`, not a nil `*divideError`. Measured: `var ptr *divideError; var e error = ptr` gives `e == nil` as `false` (see 6.1).
- `%v` on a `float64` is `%g` with the shortest representation, so it switches to exponent form early. Measured: `100000` prints `100000`, but `1000000` prints `1e+06` and `1234567` prints `1.234567e+06`. `1e-07` and `+Inf` and `NaN` also appear in the message as written. For user-facing numbers, `strconv.FormatFloat(d, 'f', -1, 64)` gives `1234567` and `0.0000001`.
- Float division by zero does not panic, so this error type is the only thing that stops it. Measured with variables: `1.0/0.0` is `+Inf`, `0.0/0.0` is `NaN`, and `-1.0/0.0` is `-Inf`. Negative zero equals zero, so `divisor == 0` also catches `-0`. Integer division by zero panics with `runtime error: integer divide by zero`, and constant division by zero is a compile error.

## 7.4 Errors Quiz

Quiz:

1. What kind of type is Go's built-in `error` type? Interface.
2. Can a type be an error and also fulfill another interface? Yes.

Notes:

- `error` is a predeclared identifier in the universe scope, not a keyword, so it can be shadowed. Measured: `error := 5` in a block compiles and prints `5`, and `go vet` reports nothing. Inside that block the `error` type is unreachable.
- Extra methods on an error type are how callers check behavior instead of concrete types: define a one-method interface and pass a pointer to it as the `errors.As` target. Measured with `type timeout interface{ Timeout() bool }`: a wrapped `os.Open` error matches as `*fs.PathError` with `Timeout()` `false`, and a wrapped `context.DeadlineExceeded` matches with `Timeout()` `true`. It also matches `net.Error`, which is `error` plus `Timeout()`. A retry loop in an MQTT or CAN gateway can retry on timeout without importing the packages that produce the errors.

## 7.5 The Errors Package

- `errors.New` inside the function returns a new error on every call, so callers can only match it by its text. In production, declare a sentinel once at package level, `var ErrDivideByZero = errors.New("no dividing by 0")`, and return it. Measured: after `fmt.Errorf("report q1: %w", err)`, `errors.Is(w, errDivByZero)` is `true` with the sentinel and `false` with the inline `errors.New`.
- Sentinel names follow `ErrFoo` (or `errFoo` when unexported). Measured: staticcheck in golangci-lint reports `ST1012: error var BadName should have name of the form ErrFoo`.
- The sentinel also saves an allocation per error. Measured with `testing.AllocsPerRun`, storing the result in a package-level variable so it escapes: inline `errors.New` makes 1 allocation per call, and the sentinel makes 0. When the result does not escape, the inlined `errors.New` is optimized to 0 allocations, so a benchmark that discards the error hides the cost. In a hot path, such as rejecting malformed CAN frames, return a sentinel or a value-type error.
- A sentinel is a package-level `var`, so any code in the package, or any importer for an exported one, can reassign it. Measured: after `ErrA = errors.New("hijacked")`, an error saved earlier no longer matches, `errors.Is(old, ErrA)` is `false`, and `go vet` reports nothing. A `const` sentinel needs a string-based error type: `type constError string` with an `Error()` method, then `const ErrB constError = "b"`. Measured: `errors.Is(fmt.Errorf("w: %w", ErrB), ErrB)` is `true`. The standard library uses `var` sentinels, so `var` is the convention.
- Go 1.26 added the generic `errors.AsType` (listed in `$GOROOT/api/go1.26.txt`). Measured: `errors.AsType[*fs.PathError](fmt.Errorf("x: %w", err))` returns the `*fs.PathError` (`Op` `open`, `Path` `/nope`) and `true`, without declaring a target variable first. The same error also satisfies `errors.Is(err, fs.ErrNotExist)`, the standard library's own sentinel.

## 7.6 Panic

Quiz:

1. Panic and recover should be used instead of errors... basically never.
2. If you want your program to cleanly exit in an unrecoverable way, which is a good alternative to panic? `log.Fatal()`.

Notes:

- `log.Fatal` prints the message and calls `os.Exit(1)`, so deferred functions do not run. Measured: with `defer fmt.Println("deferred cleanup ran")` in `main`, `log.Fatal` exits with status 1 and the deferred line never prints. A `panic` runs the panicking goroutine's deferred calls first, then prints the stack trace and exits with status 2. "Cleanly" in question 2 means no stack trace, not cleanup: buffered writers are not flushed, and an MQTT client gets no clean disconnect. In production, call `log.Fatal` only in `main` before any resources are open. After that, return an error to `main`, let its defers run, and exit with `os.Exit(1)` from a `run() error` wrapper.
- `recover` works only when the deferred function calls it directly. Measured: `defer func() { recover() }()` stops the panic, but a deferred function that calls a `helper()` which calls `recover()` gets `<nil>`, and the panic continues.
- A panic can only be recovered in its own goroutine. Measured: a `recover` deferred in `main` does not stop a panic in a goroutine started with `wg.Go`. The process exits with status 2, and the line after `wg.Wait()` never runs. `sync.WaitGroup.Go` recovers the panic itself and panics again, so the trace reads `panic: worker died [recovered, repanicked]`. The source comment explains why: calling `Done` first would let `Wait` return and `main` exit with status 0 before the panic finished. A worker pool that must survive a bad message needs a `defer`/`recover` inside each worker, and should turn the panic into an error that includes the message ID.
- Since Go 1.21, `panic(nil)` panics with a `*runtime.PanicNilError`, so `recover` no longer returns `nil` for it. Measured: `recover` returns `*runtime.PanicNilError` with text `runtime error: panic called with nil argument`. With `GODEBUG=panicnil=1` it returns `<nil>`, the Go 1.20 behavior.
- The lesson's `enrichUser` example recovers in `main` and then carries on. Code that recovers from a panic it did not expect cannot know what state the panic left behind. `net/http` recovers per request so one handler cannot crash the server, but it is the exception. Measured with `httptest`: a handler that panics logs `http: panic serving 127.0.0.1:36740: handler bug` with a stack trace, the client gets `EOF` instead of a response, and the next request returns `200`. A real use of `panic` is an impossible state, such as a `default` branch in a `switch` over an enum that should cover every value.
