Chapter 1

Variables

14 lessons

1.1 Learn Go

  • A program needs package main together with func main(). A main package without func main does not build. Only main packages become binaries with go run or go build, which is why every lesson lives in its own directory.
  • fmt.Println returns (n int, err error). Ignoring the error is normal for stdout. The same habit is a bug with files, sockets or a bufio.Writer, where a failed write or a missing Flush loses data without any error.

1.2 Declaring a Variable

  • var x T gives x the zero value of T: 0, "", false, or nil for pointers, slices, maps, channels, funcs and interfaces. Go never has an uninitialized variable.
  • Idiom: use var x T when the zero value is the starting state you mean, like a counter or a sync.Mutex. When a real value is known at declaration, use x := v, or var x = v at package level. A var followed by an assignment on the next line, as in this lesson, is the shape reviewers ask to collapse.
  • Useful zero values are a design goal: bytes.Buffer, sync.Mutex and strings.Builder all work without a constructor.
  • staticcheck S1021 flags that shape: should merge variable declaration with assignment on next line. The starter code for 1.2 and 1.3 uses it, so the warnings are left alone (one in 1.2, four in 1.3). golangci-lint prints only 3 issues with the same text by default (max-same-issues: 3), so a plain golangci-lint run ./... shows 3 of the 5. --max-same-issues=0 shows all of them.

1.3 Basic Variables

  • byte is an alias for uint8, and rune is an alias for int32. They are the same type, not just convertible: a []byte and a []uint8 can be assigned to each other.
  • The size of int and uint depends on the platform: 64 bits on amd64 and arm64, 32 bits on 386 and 32-bit ARM (GOARCH=arm). On embedded targets, use sized types (int64, uint32) for anything that crosses a wire or a file, such as CAN frames, timestamps or counters that can pass 2^31.
  • float64 cannot represent 0.05 exactly. It prints as 0.05 because fmt prints the shortest decimal that rounds back to the same float. Summing many costs builds up error. For money, store integer minor units (for example int64 millicents) and format at the edge.
  • Integer literals can be written in hex (0x1F), octal (0o17), binary (0b1011), and with _ separators (1_000_000). Println always prints decimal. Use %#x or %b to print other bases.

1.4 Short Variable Declaration

  • := takes the type from the untyped constant's default type: 21 gives int, 2.5 gives float64, 'a' gives rune, and 1i gives complex128. To get another type, write it out: x := uint8(21) or var x uint8 = 21.
  • := needs at least one new variable on the left, counted in the current scope only. Variables that already exist in that scope are assigned, not redeclared. That is why n, err := ... can reuse err.
  • Shadowing trap: in an inner block (if, for, a closure), := makes a new err that hides the outer one. A deferred check or a later return err then sees the outer value, often nil, and the failure disappears. go vet does not catch this by default. The shadow analyzer, or the govet shadow option in golangci-lint, does.
  • fmt.Println always puts a space between operands. fmt.Print adds a space only between two operands when neither is a string. That is why Print("a", 1, 2) prints a1 2.

1.5 Why Go?

  • Go never converts numeric types implicitly, not even int to int64 or int32 to int. Every conversion between typed values is written out: float64(n).
  • Untyped constants are the exception. .02 * 72 with two literals is evaluated at compile time with arbitrary precision and is exactly 1.44. Only when the value lands in a typed variable is it rounded to float64.
  • The billing bug class, measured: 0.02 * float64(72) prints 1.44, but adding 0.02 72 times in a loop gives 1.4400000000000008, and == 1.44 is false. %.2f hides the drift on display, not in the stored total. For per-message billing, keep an integer count of minor units and multiply once.
  • Converting a float variable to int truncates toward zero: with f := 1.99, int(f) is 1. Converting a variable to a smaller integer type wraps silently: with n := 300, uint8(n) is 44. A constant that does not fit is a compile error instead (uint8(300) gives constant 300 overflows uint8). Check the range before narrowing values read from sensors or the wire.

1.6 Comments

  • Idiomatic Go uses // for nearly every comment, doc comments included. /* */ is mostly used for long package docs or to disable a block of code for a moment.
  • Doc comments go directly above the declaration, start with the name (// Send delivers ...), and are full sentences. go doc and pkg.go.dev render them. Since Go 1.19, gofmt also reformats doc comments: headings (# Heading), lists and code blocks.
  • A "characters" limit is not len(s). len counts bytes, and Go strings are UTF-8. "Γειά 👋" has len 13 but 6 runes (utf8.RuneCountInString). A real SMS limit is stricter still: 160 GSM-7 characters or 70 UCS-2 code units per segment, and an emoji takes 2 UCS-2 code units.

1.7 The Compilation Process

  • go run builds a temporary binary and runs it. go build writes the binary. With CGO_ENABLED=0, the binary is statically linked, so it can go into a scratch or distroless container image or onto an embedded device with no libc.
  • Cross-compiling needs only environment variables: CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build produces an ELF 32-bit LSB executable, ARM. Cross-compiling with cgo needs a C cross toolchain, so keep cgo out of device code where possible.
  • Release flags: -trimpath removes local file paths from the binary, and -ldflags="-s -w" strips the symbol table and DWARF data. Smaller binaries mean smaller OTA payloads.
  • Every binary records its Go version and module versions. Read them with go version -m <binary> or runtime/debug.ReadBuildInfo. This is how the golangci-lint toolchain mismatch was found earlier in this chapter.
  • A runtime error in Go is a panic. An unrecovered panic prints the goroutine stack traces and exits with status 2. A panic in any goroutine kills the whole process, and a recover in main does not catch it.

1.8 Fast and CompiledQuiz

Quiz: Go code generally runs faster than interpreted languages and compiles faster than other compiled languages. Answer: faster, faster.

  • Go is slower than C, Rust or Zig mainly because of the garbage collector and runtime, not the compiler. A heap allocation costs more than a stack allocation, and every heap object adds GC work. Escape analysis decides which values go on the heap. See it with go build -gcflags=-m.
  • Go compiles fast by design: imports cannot form cycles, so packages build in dependency order and in parallel. Each package exports compact compiled data, so the compiler never re-reads the sources of its dependencies. That compiled data is the "export data" golangci-lint failed to read earlier in this chapter.
  • The GC can be tuned with GOGC (how much the heap grows between collections) and GOMEMLIMIT (a soft memory limit, since Go 1.19). On memory-constrained devices, GOMEMLIMIT makes the GC collect more often as the heap nears the limit. It helps avoid out-of-memory kills, but cannot prevent them when live data is larger than the limit.

1.9 Type Sizes

  • int(f) truncates toward zero, so int(-2.6) is -2. math.Floor(-2.6) is -3. math.Round rounds half away from zero, and math.RoundToEven gives banker's rounding. Choose on purpose when the value is money or a sensor reading.
  • A float that is out of range, or NaN, converted to an integer does not panic. The spec says the result is implementation-dependent. On amd64, int64(1e30), int64(NaN) and int32(1e30) all give the minimum value of the type (-9223372036854775808, -2147483648). Validate before converting decoded or computed floats.
  • uintptr is an integer that holds an address. The GC does not treat it as a pointer, so it does not keep the target alive. It is meant only for unsafe and syscall code.
  • Field order affects struct size because of alignment padding. On amd64, struct{ bool; int64; bool } is 24 bytes and struct{ int64; bool; bool } is 16. Chapter 5 covers memory layout. The fieldalignment analyzer reports structs that could be smaller.

1.10 Which Type Should I Use?Quiz

Quiz:

  • When should you not use a default type? Answer: when performance and memory are the primary concern.
  • What does the size of a type indicate? Answer: bits (int32 is 32 bits, or 4 bytes).

Notes:

  • Default types are bool, string, int, uint, byte, rune, float64 and complex128. Mixing sized types forces conversions everywhere and makes code harder to read.
  • The quiz leaves out one more reason to use sized types: boundaries. CAN frames, binary protocols (encoding/binary only works with fixed-size types), file formats, database columns, and code compiled for 32-bit ARM all need fixed sizes. Convert to int once at the boundary and use int inside the program.
  • unsafe.Sizeof reports a size in bytes, not bits: unsafe.Sizeof(int32(0)) is 4.

1.11 Go Is Statically Typed

  • + joins only values of the same string type. To turn a number into its digits, use strconv.Itoa(n) or fmt.Sprint(n). string(n) does not do that: it gives the character with that code point, so string(rune(12345)) is "〹". go vet rejects string(n) for a plain int with "conversion from int to string yields a string of one rune, not a string of digits".
  • The lesson's header is not real HTTP Basic auth. RFC 7617 needs base64(user:password). req.SetBasicAuth("presidentSkroob", "12345") sends Basic cHJlc2lkZW50U2tyb29iOjEyMzQ1. Base64 is encoding, not encryption, so Basic auth is safe only over TLS.
  • staticcheck ST1023 flags var x string = "..." because the type repeats what the value already says. The starter code uses that form here, so the warning is left alone.

1.12 Compiled vs. InterpretedQuiz

Quiz:

  • To run a compiled program, users need: the compiled executable.
  • Which language is interpreted? Python (of Rust, Python, Go and C++).

Notes:

  • "No runtime needed" is a simplification. Go has a runtime (goroutine scheduler, garbage collector, maps, channels) that is compiled into every binary instead of installed on the machine. On amd64 with Go 1.27.3, a fmt hello world is 2,408,006 bytes, and 1,507,488 bytes with -trimpath -ldflags="-s -w". GOMAXPROCS, GOGC and GOMEMLIMIT configure that runtime.
  • A compiled executable still depends on its target. It runs only on the GOOS/GOARCH it was built for, and with cgo it also needs the libc it was linked against.

1.13 Same Line Declarations

  • In a, b = x, y, all expressions on the right (and the index expressions on the left) are evaluated first, then the assignments happen. That makes a, b = b, a a swap with no temporary variable. With i := 0, i, s[i] = 1, 99 writes to s[0], not s[1], because s[i] is resolved before i changes.
  • For related declarations, a grouped block often reads better than one long line:
    var (
	averageOpenRate = .23
	displayMessage  = "is the average open rate of your messages"
)
  • Multiple assignment is how Go returns more than one value: n, err := f(). Chapter 4 builds on it.

1.14 Small Memory FootprintQuiz

Quiz:

  • Which language generally uses the most memory? Java (of Rust, Java, Go and C).
  • What is one purpose of the Go runtime? To clean up unused memory.

Notes:

  • Goroutines are what make the footprint matter. Measured on Go 1.27.3 amd64: 100,000 blocked goroutines use 2,054 bytes of stack each (runtime.MemStats.StackInuse). Stacks grow as needed, and since Go 1.19 the starting size follows the average stack use the program has seen. An OS thread reserves its full stack up front: glibc uses ulimit -s, which is 16 MB of virtual memory on this machine (8 MB is a common default). One goroutine per connection or per device is cheap. One thread per connection is not.
  • Measuring memory: process RSS is not the Go heap. Read runtime/metrics, or run with GODEBUG=gctrace=1. With the default GOGC=100, a heap of up to about twice the live data is normal and not a leak. A leak shows up as live data that keeps growing, often from goroutines that never exit.
Chapter 2

Constants and Formatting

9 lessons

2.1 Constants

  • Constants are compile-time values. You cannot take their address: &p fails with invalid operation: cannot take address of p (untyped string constant "x"). Only basic types (numbers, strings, booleans, runes) can be constants. const s = []int{1} fails with []int{…} (value of type []int) is not constant. For a fixed lookup table, use a package-level var or a function that returns a new slice.
  • Untyped constants are the important part. const timeout = 5 has no type until it is used, so timeout * time.Second compiles and gives 5s. A typed const timeout int = 5, or an int variable, fails with mismatched types int and time.Duration. Leave constants untyped unless the type itself carries meaning.
  • Untyped numeric constants use arbitrary precision at compile time. const big = 1 << 100 is valid, and big >> 98 prints 4. Overflow is only checked when the value is converted to a concrete type.
  • In production code, related constants usually go in a grouped const ( ... ) block at package level. A typed group with iota is Go's enum pattern, for example CAN frame IDs or device states.

2.2 Computed Constants

  • A constant expression may use other constants, operators, conversions, and some builtins (len on a constant string, unsafe.Sizeof). const n = len("abc") is 3. A function or method call is not constant, even when the result is fixed. const t = time.Now() fails with time.Now() (value of struct type time.Time) is not constant, and const h = time.Hour.Seconds() fails with time.Hour.Seconds() (value of type float64) is not constant.
  • In production code, use time.Duration instead of counting seconds by hand: time.Hour, or 5 * time.Minute. If an API needs a plain number, convert at the edge: const secs = int64(time.Hour / time.Second) is still a constant (3600). A bare int such as timeoutSecs hides its unit. With time.Duration, the unit is part of the type.

2.3 Comparing Go's SpeedQuiz

Quiz:

  • Does Go generally execute faster than Rust? No.

Notes:

  • The lesson calls the slower speed "the price we pay for memory safety". That is only half right. Rust is memory safe without a garbage collector, because the borrow checker does the work at compile time. Go's cost comes from the GC and from heap allocation, and also from a compiler that favours fast builds over aggressive optimization.
  • To see what the compiler does, use go build -gcflags=-m. It prints inlining decisions and escape analysis. Measured on Go 1.27.3: func newFrame() *frame { return &frame{...} } reports &frame{...} escapes to heap. At a call site where the function is inlined, the same value does not escape and stays on the stack. In a hot path, heap allocations matter more than the speed of individual instructions.
  • Bounds checks: -gcflags=-d=ssa/check_bce lists every check that remains. A loop over b[i] for i < 8 reports Found IsInBounds inside the loop. Add _ = b[7] before the loop and only that one check is left, outside the loop. This pattern is common in binary decoders, for example parsing 8-byte CAN payloads.
  • Tuning knobs before rewriting in another language: GOGC and GOMEMLIMIT (Go 1.19+) for GC pressure, and profile-guided optimization (default.pgo, Go 1.21+) for inlining hot paths. Profile with pprof first.

2.4 Formatting Strings in Go

  • %.1f rounds the binary value, not the decimal you typed. Measured: %.2f of 2.675 prints 2.67, because the stored double is just below 2.675. Exact halves round to even: %.1f of 0.25 is 0.2, %.0f of 0.5 is 0, and of 1.5 is 2. For money or billing, store integer cents instead of formatting floats.
  • go vet checks format strings against their arguments. It reports fmt.Printf format %d has arg 30.54 of wrong type float64 and fmt.Printf format %s reads arg #1, but call has 0 args. The same check covers your own wrapper functions when they pass format, args... through to fmt.
  • Verbs worth knowing beyond the lesson, for frame{ID: 0x18FF50E5, Data: []byte{1, 2}}:
    • %v prints {419385573 [1 2]}
    • %+v prints {ID:419385573 Data:[1 2]}, with field names, which helps in logs
    • %#v prints main.frame{ID:0x18ff50e5, Data:[]uint8{0x1, 0x2}}, as Go syntax
    • %X prints 18FF50E5, and %08b prints zero-padded binary, which suits CAN IDs and register dumps
    • %q prints a quoted string with escapes, such as "a\tb", which shows hidden whitespace
  • In production code, avoid building log lines with Sprintf. With slog.Info("open rate", "name", name, "rate", openRate) the fields stay machine-readable. In hot paths, fmt.Appendf(buf, ...) (Go 1.19+) writes into a reused buffer instead of allocating a new string.

2.5 Runes and String Encoding

  • len(s) counts bytes, and s[i] returns a byte. In "a🐻", len is 5 and s[1] is 240 (0xF0, the first byte of the emoji). range over a string decodes UTF-8 and yields the byte offset and the rune: 0 'a', then 1 '🐻'. The index jumps by the width of each rune.
  • Invalid UTF-8 does not panic. range over "a\xffb" yields U+FFFD (the replacement character) for the bad byte and carries on. Use utf8.ValidString (false here) at the boundary when strings come from devices, serial lines, or MQTT payloads.
  • rune is an alias for int32, not a separate type. %T prints int32 for both, and assigning one to the other needs no conversion. byte is an alias for uint8 in the same way.
  • A rune is a code point, not a visible character. The polar bear emoji (bear, zero-width joiner, snowflake, variation selector) is 13 bytes and 4 runes, but it shows as one character. Counting what a user sees needs grapheme segmentation, which the standard library does not provide (github.com/rivo/uniseg does).
  • []rune(s) allocates and decodes the whole string. Prefer range or utf8.DecodeRuneInString when you only need to walk it. For binary data such as CAN frames, use []byte and never string, so that nothing is treated as text by accident.

2.6 Fix Bugs

  • Go rejects type mismatches at compile time, before the program runs. For example, var startup int = "boot" fails with cannot use "boot" (untyped string constant) as int value in variable declaration. An unused local variable also fails the build: declared and not used: unused. Unused package-level variables are allowed.
  • The var x string = "..." form comes from the course's starter code. staticcheck reports ST1023 on it. That is a style warning, not a bug.

2.7 Fix Types

  • The walrus := declares a variable and infers its type. It works only inside functions. At package level it fails with syntax error: non-declaration statement outside function body. Declaring the same name twice in one scope fails with no new variables on left side of :=.
  • := with several names on the left reuses the ones that already exist in the same scope, as long as at least one name is new. That is why n, err := f() can follow an earlier err.
  • The trap is shadowing. In an inner scope (if, for, a closure), n, err := read() declares a new err. The outer err stays nil. In the measured example, read returned bus off and the program still printed outer err: <nil>. Default go vet does not report this. When an inner block must set an outer variable, declare n first and assign with =. Named result values combined with a defer that inspects err are a common place for this bug.

2.8 Type Inference

  • := gives an untyped constant its default type. 2 becomes int. 2.0 and 2e0 become float64. 'x' becomes rune (which %T prints as int32). 1i becomes complex128. The literal decides the type, so the .0 matters.
  • 1/2 is integer division and gives 0. 1/2.0 gives 0.5. If one operand of a constant expression is a float, the result is a float.
  • Constants and variables differ in precision. Measured: const ok = 0.1 + 0.2 == 0.3 is true, because constants are exact at compile time. With float64 variables, x+y is 0.30000000000000004 and x+y == 0.3 is false. Adding 0.1 ten times gives 0.9999999999999999.
  • The lesson stores fractions of a penny in a float64. Production billing code would use a fixed-point integer instead, such as int64 micro-cents, or a decimal library. This is the same advice as for 2.4: errors from repeated float addition build up over millions of messages.

2.9 Format Practice

  • A wrong verb is not a compile error. At run time fmt writes a marker into the output instead. Measured: Sprintf("%d %s %.1f", false, 45, "x") gives %!d(bool=false) %!s(int=45) %!f(string=x). go run and go build do not run vet, so this slips through. go vet, and the vet subset that go test runs, catch it.
  • The lesson's log line is a formatted string. In production code, the same record as slog fields reads level=INFO msg=user name="Dalinar Kholin" age=45 rate=0.5 subscribed=false with a TextHandler, and turns into JSON with a JSONHandler. Log pipelines such as CloudWatch Logs Insights can query those fields directly. With a free-text message, they would have to parse it first.

Conditionals

4 lessons

3.1 Conditionals

  • The opening brace must be on the same line as the condition. This is not a style rule. The lexer inserts a semicolon at the end of a line that ends in an identifier, so if x > 0 followed by { on the next line fails with syntax error: unexpected newline, expected { after if clause.
  • if takes an optional init statement: if n, err := read(); err != nil { ... }. Variables declared there are in scope in every branch of the chain, including else if and else, and nowhere after it. Using n after the closing brace fails with undefined: n.
  • Go has no ternary operator. Use an if/else that assigns, or a small function.
  • The lesson uses if/else with two branches of equal weight, which is fine here. In production code, CodeReviewComments "Indent Error Flow" prefers handling the error or the rejected case first and returning early, so the normal path stays at the left margin. For example, if len(msg) > maxLen { return ErrTooLong }, then send.

3.2 The Initial Statement of an If BlockQuiz

Quiz:

  1. Why would you use the 'initial' section of an if statement? To keep the code concise and the scope limited.
  2. Which is valid Go syntax? if x := 5; x > 3 {. The form with parentheses, if (x := 5; x > 3) {, is not.

Notes:

  • Parentheses around a plain condition compile: if (x > 0) { is valid, and gofmt rewrites it to if x > 0 {. Parentheses around the init statement and condition together do not compile: syntax error: unexpected :=, expected ). The parser reads the parentheses as an expression, and := is a statement.
  • The init statement is any simple statement, not only a declaration. Measured: if x++; x > 1 and if fmt.Println("call init"); x > 1 both compile and run. A declaration with := is the only common use.
  • The common production form is if err := f(); err != nil { return fmt.Errorf("...: %w", err) } for a call that returns only an error. When the call also returns a value that is needed after the if, declare it outside: v, err := f(), then if err != nil. The value is out of scope after the if closes (see 3.1).

3.3 Switch

  • Cases do not fall through, so no break is needed. fallthrough moves into the next case's body without testing that case's condition. Measured: with x := 1, case x > 0: followed by fallthrough ran the body of case x > 100:. fallthrough in the final case fails with cannot fallthrough final case in switch.
  • A break inside a switch leaves the switch, not an enclosing for. Measured: a break in case 1: inside a for i := range 3 loop still printed i 0, i 1 and i 2. To leave the loop, use a labelled break, or return. This often bites in event loops that switch on a message type or a CAN ID.
  • One case can list several values: case 1, 2:. Duplicate constant cases fail to compile: duplicate case "a" (constant of type string) in expression switch. A switch with no tag (switch { case x > 0: ... }) is the idiomatic replacement for a long if/else if chain.
  • The lesson returns 0.0 for an unknown plan, so a typo such as "Pro" is billed at zero with no error. Production code would make the plan a named type with constants and return (float64, error) from the default case. The exhaustive linter in golangci-lint can then report a switch that misses one of the constants. Money as float64 has the same problem as in 2.8.

3.4 Calculate Balance

  • In a compound assignment, the right-hand side is evaluated as a whole before the operator is applied, so finalCost *= 1 - discountRate needs no parentheses. Measured: x := 2.0; x *= 1 + 2 gives 6, and the forms with and without parentheses give the same 67.5. The parentheses are harmless and some readers prefer them.
  • The check finalCost > accountBalance counts as insufficient funds only when the cost is strictly greater, so an exact balance succeeds. With floats, "exact" is not reliable. Measured: a cost built as 0.1 + 0.2 is 0.30000000000000004, which is greater than a balance of 0.3, so the purchase fails. The same comparison with int64 cents (10 + 20 against 30) is not greater, so it succeeds. This is the 2.8 advice again: keep money in integer minor units.
  • In production, the check and the subtraction are a read-modify-write. Two concurrent purchases can both pass the check and overdraw the account. Do both under one mutex, or let the database do them in one statement (UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1) and check the affected row count.
  • The var x T = v declarations come from the starter code and give staticcheck ST1023 warnings. They are not findings.
Chapter 4

Functions

17 lessons

4.1 Functions

  • Adjacent parameters of the same type can share one type: func concat(s1, s2 string) string. Every parameter still needs a type. func f(x, y) int does not mean "infer the type": the parser reads it as two unnamed parameters of types x and y. Measured: the compiler reports undefined: x and undefined: y, not a missing-type error.
  • Function order in a file does not matter, and neither does order across files in a package. Package-level declarations are resolved before any body is checked.
  • s1 + s2 allocates a new string, because strings are immutable. One expression with several operands is still one allocation. Measured with testing.AllocsPerRun: a + b + c + d makes 1 allocation. s += a in a loop of 100 makes 99, and the copying is quadratic in the final length. A strings.Builder with Grow makes 1. Build log lines or payloads in a loop, for example joining decoded CAN frame fields, with strings.Builder, strings.Join, or fmt.Fprintf to a writer.

4.2 Multiple ParametersQuiz

Quiz:

  1. Which is the shortest and clearest way to write a valid function signature? func createUser(firstName, lastName string, age int). The form firstName string, lastName string, age int is valid but longer. The form firstName, age, lastName string int does not compile.

Notes:

  • A type applies to the run of names before it, back to the previous type. Grouping only works for adjacent parameters, so firstName string, age int, lastName string cannot be shortened without reordering.
  • Two types in a row is a syntax error. Measured: func createUser(firstName, age, lastName string int) fails with syntax error: unexpected name int in parameter list; possibly missing comma or ). Mixing named and unnamed parameters also fails: func f(a int, string) gives syntax error: missing parameter type.
  • gofmt -s does not merge repeated types. The gocritic check paramTypeCombine does. Measured: it reports func(firstName string, lastName string, age int) could be replaced with func(firstName, lastName string, age int). It is off by default in golangci-lint.
  • Several adjacent parameters of one type are easy to swap at the call site, and the compiler cannot catch it: createUser("Smith", "Jane", 30) compiles. In production, a struct parameter or distinct named types (for example type DeviceID string and type Topic string in an IoT publisher) make a swap a compile error.

4.3 Unit Test Lessons

  • A main package with no func main passes go vet and go test, but go build fails. Measured: runtime.main_main·f: function main is undeclared in the main package. The course's test-driven lessons rely on this. In a real project, put the function in a non-main package and keep main thin.
  • 100 * penniesPerDollar is a constant expression. The compiler folds it to 10000, so it costs nothing at run time. An untyped constant takes its type from context, here int from the return type. The first version named the constant inPennies, which reads like a unit label. penniesPerDollar says what the factor is.

4.5 Passing Variables by Value

  • Go passes every argument by value. For slices, maps, channels, pointers and functions, the value copied is a small header or pointer that refers to shared data. That is why they look like "pass by reference", and it is not the same thing. Measured:
    • Slice: s[0] = 99 inside the function is visible to the caller. An append that exceeds capacity gives the function a new backing array, so a later s[1] = 77 is not visible. The caller still saw [99 2 3].
    • Map: m["k"] = 1 is visible to the caller. Assigning a new map to the parameter is not: the caller's nil map stayed nil.
    • Struct: a frame with an [8]byte array is copied whole, so f.data[0] = 0xFF on the copy left the caller's byte at 0. Through *frame, the caller saw 255.
  • Arrays are values, unlike C, where an array decays to a pointer. A CAN frame struct with a [8]byte payload is 12 bytes or more and cheap to copy. Pass it by value unless the function must change it.
  • Returning the result, as this lesson does, is the idiomatic fix. An out-parameter (func getBill(..., bill *int)) is C style and rare in Go.
  • var lastMonthBill int followed by lastMonthBill = getBillForMonth(...) is two lines where lastMonthBill := getBillForMonth(...) is one. The var declarations look like starter code; that could not be checked. Here, return getBillForMonth(c, this) - getBillForMonth(c, last) reads just as well.

5.1 Structs in Go

  • A struct's zero value has every field set to its zero value, so var m messageToSend is ready to use. Measured: %v prints {0 }, %+v prints {phoneNumber:0 message:}, and %#v prints main.messageToSend{phoneNumber:0, message:""}. Use %+v in log lines so that an empty string field stays visible.

  • Size is the sum of the fields plus alignment padding. Measured on amd64: messageToSend is 24 bytes (8 for int, 16 for the string header). The lesson's car is 48 bytes. Field order affects padding when small and large fields are mixed.
  • int is 32 bits on 32-bit targets. The course's test cases use 148255510981, which needs more than 32 bits. Measured: GOARCH=arm GOARM=7 go vet ./ch05/l01 fails with cannot use 148255510981 (untyped int constant) as int value in struct literal (overflows). 6.1 Interfaces in Go

  • A type satisfies an interface implicitly: it only needs the methods. There is no implements keyword. Measured: when the method has a pointer receiver, the value does not satisfy the interface, and vet reports t does not implement message (method getMessage has pointer receiver).

Measured with testing.AllocsPerRun: assigning a 40-byte birthdayMessage to an escaping message variable makes 1 allocation, and assigning &bm makes 0. 6.7 Type Assertions in Go

  • Use the two-value form, v, ok := e.(email). The one-value form panics when the type is wrong. Measured: e.(email) on an sms panics with interface conversion: main.expense is main.sms, not main.email. Asserting on a nil interface does not panic in the two-value form, and ok is false.
  • The lesson calls this a cast. Go has no casts. float64(n) is a conversion, which is checked at compile time. e.(email) is a type assertion, which is checked at run time against the dynamic type stored in the interface. A type assertion never changes the value: it only gets it back out.
  • Two if statements with assertions work. A switch v := e.(type) (lesson 6.8) is shorter for more than one type, and it has a default case for "any other type".
  • The asserted type can also be an interface. This is how optional behavior is detected. Measured: an io.Writer holding a *bytes.Buffer asserts to io.StringWriter as true and to io.Closer as false. An io.Writer holding os.Stdout asserts to io.Closer as true. The standard library does this, for example io.Copy checks for io.WriterTo and io.ReaderFrom, and an HTTP handler checks for http.Flusher to stream a response.
  • Asserting to concrete types in a function like getExpenseReport means every new expense type needs a new branch. Production code adds a method to the interface (for example recipient() string), so a new type cannot be forgotten: it fails to compile until it has the method.

6.9 Clean InterfacesQuiz

Quiz:

  1. Interfaces should have as ___ methods as possible. Few.
  2. It's okay for interfaces to be aware of the types that satisfy them. False.
  3. According to the lesson, what is the primary goal of keeping interfaces small? To only define the essential behaviors.
  4. Interfaces allow you to define a method's implementation once and use it for many different types. False.

Notes:

The lesson gives three rules: keep interfaces small, an interface knows nothing about the types that satisfy it, and interfaces are not classes. The official guidance adds where to put an interface and when to create one.

Keep interfaces small

  • Go Proverbs (Rob Pike, Gopherfest 2015): "The bigger the interface, the weaker the abstraction." Every method added to an interface is one more thing each implementation and each test fake must provide, and one fewer type that can satisfy it.
  • The standard library follows it. Measured by counting the entries in each exported interface in src/io/io.go: 12 interfaces have one entry, 7 have two, and 3 have three. None has more. The larger ones are built by embedding smaller ones: ReadWriter is Reader plus Writer.
  • The lesson's http.File example has five entries, three of them embedded io interfaces. In Go 1.27 the source (src/net/http/fs.go) returns fs.FileInfo, not os.FileInfo as in the lesson. os.FileInfo is an alias of fs.FileInfo, so both spellings name the same type (src/os/types.go: type FileInfo = fs.FileInfo).
  • A function should ask for the smallest interface it uses. A function that only writes takes an io.Writer, not an *os.File and not an io.ReadWriteCloser. Then a file, a bytes.Buffer, a TCP connection, a serial port and a test fake all work.

An interface knows nothing about the types that satisfy it

  • IsFiretruck() bool on car forces every car to know about firetrucks. The fix in the lesson is a larger interface that embeds the smaller one, and a type assertion to it. Measured: with type firetruck interface { car; HoseLength() int }, describe(c car) uses if ft, ok := c.(firetruck); ok and prints red firetruck, hose 30 for a type with HoseLength, and blue car for one without. This is the optional-interface pattern from 6.7, the same one io.Copy uses for io.WriterTo.
  • The same smell in production: a Device interface with IsGateway() bool or SupportsOTA() bool. Use a separate updater interface { Update(ctx context.Context, image io.Reader) error } and assert to it where it matters.

Interfaces are not classes

  • An interface has no data, no constructor, and no implementation. It only lists method signatures. Question 4 is false for this reason: each of five fmt.Stringer types still writes its own String().
  • To share an implementation, use one of these:
    • Embed a struct that has the method. The method is promoted and counts toward the outer type's method set. Measured: sedan embeds base, which has String() and Color(), so sedan satisfies fmt.Stringer and prints car:blue.
    • Write one function that takes the interface, such as fmt.Fprintf(w io.Writer, ...).
    • Write a generic function (Go 1.18 and later) when the code must keep the concrete type, for example to return it.
  • Embedding is not inheritance. The embedded base does not know about sedan, so a method on base that calls another method calls base's version, never one that sedan overrides. Measured: base.describe() returns "I am " + b.name(), and sedan{}.describe() prints I am base even though sedan has its own name().

Where an interface goes (CodeReviewComments, "Interfaces")

  • "Go interfaces generally belong in the package that uses values of the interface type, not the package that implements those values. The implementing package should return concrete (usually pointer or struct) types." This is the rule behind "accept interfaces, return structs". The producer can then add methods without breaking anyone.
  • "Do not define interfaces on the implementor side of an API 'for mocking'." The consumer declares the small interface it needs, and its test defines a fake for it.
  • "Do not define interfaces before they are used." Without a real caller, there is no way to tell which methods the interface needs, or whether it is needed at all.
  • Example from the IoT domain: a telemetry uploader needs one call from the MQTT client. The uploader package declares type publisher interface { Publish(ctx context.Context, topic string, payload []byte) error }, and an adapter wraps the AWS IoT SDK client to satisfy it. The uploader's test uses a fake that records the published messages. Nothing in the uploader depends on the SDK's full client type, and swapping the transport (MQTT over WebSocket, a local broker, a file on the device for offline buffering) changes only the adapter.
  • "interface{} says nothing" (Go Proverbs). A parameter of type any gives the compiler nothing to check. Use a small interface or a type parameter instead.

8.1 Loops in Go

  • The solution uses for i := range numMessages (range over int, Go 1.22) instead of the lesson's three-clause for i := 0; i < numMessages; i++. Both run 0 to n-1. A negative or zero count gives zero iterations. Measured: for range -5 runs 0 times.
  • Since Go 1.22, the three-clause loop also creates a new i for each iteration. Measured: closures that capture i in for i := 0; i < 3; i++ print 0 1 2. In a file with //go:build go1.21, the same code prints 3 3 3. The per-file build tag sets the language version, so old semantics can come back in one file of a 1.27 module. Range over int is also rejected there: cannot range over -5 (untyped int constant): requires go1.22 or later (file declares //go:build go1.21).
  • Adding 0.01 again and again in a float64 drifts. Measured: for 30 messages the loop gives 34.349999999999994, and the closed form n + 0.01*n*(n-1)/2 gives 34.350000000000001. The test passes only because it compares %.2f strings. Summing integer cents (100 + i) gives exactly 3435. See 7.2 for money in float64.
  • The loop is O(n), and the total has a closed form that is O(1). The lesson asks for a loop on purpose. In a billing path, use the formula in integer cents.

8.2 Omitting Conditions from a for Loop in Go

  • for i := 0; ; i++ with no condition runs until return or break. The loop has no exit at the bottom, so the function needs no final return. The compiler accepts this because a for with no condition and no break is a terminating statement.
  • The check acc > thresh comes after the add, so i is the count of messages that fit. thresh = 100 returns 1 and thresh = 0 returns 0. A negative thresh also returns 0. Measured: maxMessages(-1) is 0.
  • The loop terminates only because acc reaches thresh. Near math.MaxInt, acc overflows and wraps negative before it passes thresh. Signed overflow in Go wraps silently. It is not undefined behavior and does not panic. Measured: maxMessages(math.MaxInt) did not return after 20s. In production, bound the loop or compute the answer directly.
  • The answer has a closed form: the largest n with 100n + n(n-1)/2 <= thresh, from the quadratic formula, plus an integer correction step for float rounding. Measured: it matches the loop for every thresh from -500 to 2000000. A budget check in a billing or rate-limit path should use the formula, or at least cap the iteration count.

8.3 There Is No While Loop in Go

  • The fix is the condition for balance > 0. Go has no while keyword. A for with only a condition is the while loop, and a bare for {} is the infinite loop.
  • The loop terminates only when the costs sum past the budget. With costMultiplier < 1, the costs form a convergent geometric series, so the total never exceeds 1/(1-m). With costMultiplier == 0, every message after the first is free. Measured: (0.5, 2), (0.5, 3) and (0, 5) did not return after 3s. (1.0, 5) returns 5 and (0.5, 1) returns 1.
  • With m = 1.0 and budget 5, balance reaches exactly 0.0. Whole numbers are exact in float64, so the balance < 0 check does not fire and the answer is 5. With fractional multipliers, an exact zero depends on rounding. Production code would validate costMultiplier > 1 at the boundary, or cap the message count, and keep money in integer pennies (see 7.2 and 8.1).

8.4 Fizzbuzz

  • Check the combined case first. The i%3 == 0 && i%5 == 0 branch must come before the single checks, or 15 prints fizz. i%15 == 0 is the same test, because 3 and 5 are coprime.
  • Idiom: a tagless switch is the Go way to write a long if/else if chain. Effective Go: "It's therefore possible—and idiomatic—to write an if-else-if-else chain as a switch." Cases are checked top to bottom and the first match wins, with no fallthrough.
    switch {
case i%15 == 0:
    fmt.Println("fizzbuzz")
case i%3 == 0:
    fmt.Println("fizz")
case i%5 == 0:
    fmt.Println("buzz")
default:
    fmt.Println(i)
}
  • os.Stdout is an unbuffered *os.File, so each fmt.Println is one Write, which is one syscall. Measured with a writer that counts calls: 100 lines make 100 Write calls directly, and 1 call through bufio.NewWriter followed by Flush. For high-volume output, such as a log or CAN frame dump on a slow embedded console, wrap the writer in bufio and Flush before exit. A missed Flush drops the tail of the output silently. Taking an io.Writer parameter instead of printing to os.Stdout also makes the function testable.

8.5 Continue & Break

  • continue skips to the next iteration (the post statement still runs). break leaves the innermost for, switch or select. A break inside a switch or select inside a loop only exits that switch or select, not the loop. To leave the loop, use a label: outer: for ... { switch { case x: break outer } }. This catches people in for { select { ... } } event loops, which are common in concurrent pipelines.
  • The parameter name max comes from the starter code. It shadows the max builtin added in Go 1.21. The code is legal, but inside the function the builtin can no longer be called. Measured: max(max, 3) fails with invalid operation: cannot call max (variable of type int): int is not a function. The predeclared linter flags this, but the golangci-lint config here does not enable it. Avoid max, min, len, new, clear and cap as identifiers in your own code.
  • n <= max reads better than n < max+1 and does the same thing. Both are wrong at math.MaxInt: max+1 wraps to MinInt and the loop does not run, while n <= MaxInt is always true.
  • The output matches a reference built from coreutils factor for 10, 20 and 30, including the headings. Trial division up to sqrt(n) is O(n·sqrt(n)) for the whole range. To print every prime up to max, the sieve of Eratosthenes is O(n log log n). For a single large number, math/big's (*Int).ProbablyPrime runs Miller-Rabin plus Baillie-PSW.

8.6 Connections

  • Each new person connects to everyone already in the group, so the total is 0 + 1 + ... + (n-1). The solution runs i from 1 to n and adds n - i. The last iteration adds 0, so i < groupSize saves one pass. With range over int, for i := range groupSize { c += i } adds the same sum in the other order, and needs no - i.
  • A loop guards the input for free. A zero or negative groupSize gives 0 iterations and returns 0. The formula n*(n-1)/2 does not: measured, -3 gives 6. A formula version needs an explicit if n < 2 { return 0 }.
  • The lesson forbids the formula, but production code would use it, and it overflows earlier than the result does. The product n*(n-1) wraps before the /2. 9.1 Arrays in Go

  • The length is part of the type. [3]int and [4]int are different types, and an array literal can let the compiler count: [...]int{5: 1} has length 6.
  • Arrays are values, not references. Assignment, passing to a function, and returning all copy every element. Measured: after b := a; b[0] = 7 and a call that sets a[0] = 99 on its parameter, a is still [1 2 3]. This is the main difference from slices, which share a backing array.
  • Arrays of comparable elements are comparable with ==, so they can be map keys: map[[2]int]string works. The course test compares six elements one by one; actualMessages != test.expectedMessages || actualCosts != test.expectedCosts does the same.
  • len on a string counts bytes, not characters. Measured: len("café") is 5, utf8.RuneCountInString("café") is 4. The lesson's cost is bytes, which is the right unit for an SMS or MQTT payload budget, but not for a character count shown to a user.
  • Size: [3]string is 48 bytes (three 16-byte headers, pointer and length), [3]int is 24 on amd64. The string data itself is not copied when the array is copied, only the headers.
  • Production note: a fixed-size array is the natural type for fixed-layout data, for example a CAN frame payload [8]byte. It lives on the stack or inline in a struct, needs no allocation, and copying it is cheap. For a variable number of retries, a slice fits better.

9.2 Slices in Go

  • A slice is a header of three words: pointer to the backing array, length, and capacity. a[low:high] gives length high-low and capacity cap(a)-low, so the elements after high are still reachable.
  • Measured on the free-plan result: messages[:2] has len 2, cap 3, and s[:cap(s)][2] still reads the third message. An append(s, "X") does not allocate. It writes "X" into the third element of the shared backing array. A caller that appends to a returned slice can overwrite data the callee still holds.
  • The full slice expression a[low:high:max] caps the capacity at max-low. messages[:2:2] has cap 2, so the next append must copy to a new array. Use it when returning a sub-slice of an array or buffer the function keeps.
  • messages is an array parameter, so the function slices its own copy, not the caller's array. Slicing a local array makes the compiler move it to the heap: go build -gcflags=-m reports moved to heap: messages. The returned slice never aliases the caller's array.
  • A nil slice has len 0, and range, len and append all work on it. Return nil, not []string{}, on the error path. The difference shows only in == nil checks and in JSON, where nil encodes as null and an empty slice as [].
  • Production note: a function that returns a fixed error text usually declares a sentinel, var ErrUnsupportedPlan = errors.New("unsupported plan"), so callers can test it with errors.Is. errors.New in the return statement makes a new value each call, and callers can only compare the message string.

9.3 Slices ReviewQuiz

Quiz:

  1. Which references the other? Slices reference arrays.
  2. Multiple slices can point to the same array. True.
  3. A function that only has access to a slice can modify the elements of the underlying array. True.

Notes:

  • Overlapping slices see each other's writes. Measured: with a := arr[0:2] and b := arr[1:3], setting b[0] = 99 inside a function changes arr[1] and a[1] too.
  • The slice header is passed by value, so a callee can change the elements but not the caller's length or capacity. Measured: a function that runs s = append(s, 4) on arr[:3] writes 4 into arr[3], because the capacity allowed it, but the caller's slice still has len 3. The new element is in memory and invisible to the caller.
  • When append has to grow, the callee's slice moves to a new array and later writes stop reaching the caller. Measured: on []int{1, 2, 3} (full capacity), append then s[1] = 77 leaves the caller's slice as [1 2 3]. Whether a write is visible depends on the capacity at run time. That is why functions that grow a slice return it, as append itself does.
  • io.Reader's Read(p []byte) (n int, err error) follows this rule. The caller owns the buffer and its length is the limit. The callee fills p[:n] and returns n, not a new slice. In a pipeline that reuses one read buffer, data a consumer keeps must be copied out before the next Read, or it is overwritten. The same applies to frames from a bufio.Scanner: Bytes() is only valid until the next Scan.

9.4 Make

  • make([]T, n) gives len n, cap n, filled with zero values, so the loop assigns by index: costs[i] = .... make([]T, 0, n) gives len 0, cap n, and the loop must append. Mixing the two is a common bug: make([]T, n) followed by append leaves n zeros at the front. The course test checks cap(output), so either form must preallocate exactly len(messages).
  • for i, msg := range messages replaces for i := 0; i < l; i++ plus messages[i]. It needs no length variable and cannot index out of range.
  • Float money is not exact. Measured: float64(57) * 0.01 is 0.5700000000000001, while float64(57) / 100 is 0.57. Ten additions of 0.1 give 0.9999999999999999. The course test compares with !=, and passes only because its message lengths happen to round cleanly. Dividing by 100 gives the correctly rounded result because 100 is exact in binary and 0.01 is not.
  • Production note: store money as integer minor units (cents, or a smaller unit for per-message pricing) in int64, and format at the edge. Compare computed floats in tests with a tolerance, for example cmpopts.EquateApprox. The same applies to sensor values: keep raw integer counts from the device and scale once, not on every step of a pipeline.

9.5 Len and Cap ReviewQuiz

Quiz:

  1. What does the cap() function return? The maximum length of the slice before reallocation of the array is necessary.
  2. What does the len() function return? The current length of the slice.
  3. What do len() and cap() do when a slice is nil? Return 0.

Notes:

  • len and cap never panic on nil. Measured: a nil slice, map (len only), channel, and string all give 0. A nil *[3]int gives len 3, cap 3, because the length is part of the type and the pointer is never read. Ranging over that nil pointer with a value variable does read it, and panics with invalid memory address or nil pointer dereference.
  • The lesson's Append, from Effective Go, shows what the built-in append does: if len + len(data) fits in cap, it reslices in place (slice[0:l+len(data)]) and copies. Otherwise it allocates a bigger array and copies the old elements first. The reslice past len and up to cap is legal; past cap it panics.
  • The real growth rule is not "double". Measured on go1.27.3, amd64, appending one int at a time: 4 8 16 32 64 128 256 512 848 1280 1792 2560. It doubles up to 256 elements, then grows by a smaller factor that falls toward 1.25×, and every step is rounded up to a malloc size class, which is why 848 appears. Appending single bytes gives 32 64 128: the first allocation is already a 32-byte size class. Do not write tests or logic that depend on these values.
  • Production note: append on a slice that is about to grow costs one allocation plus a copy of every element. For a buffer that collects readings per batch, allocate once with make([]T, 0, batchSize) and reuse it with buf = buf[:0], which keeps the capacity. slices.Grow(s, n) reserves room for n more elements in one step when the count is known later.

9.6 Variadic

  • Inside the function, nums ...int is a plain []int. Called with no arguments it is nil. Called as f(s...), the function gets s itself, not a copy. Measured: a function that sets nums[0] = 0 changes the caller's slice when called as zero(s...), and leaves a and b unchanged when called as zero(a, b), because Go builds a new slice from separate arguments.
  • nil... and []int{}... pass through unchanged: nums == nil is true for f() and f(nil...), and false for f([]int{}...).
  • Separate arguments and a spread slice cannot be mixed. sum(1, s...) fails with too many arguments in call to sum and have (number, []int...). Build the slice first, for example sum(append([]int{1}, s...)...).
  • A []string does not spread into ...any. fmt.Println(names...) fails with cannot use names (variable of type []string) as []any value in argument to fmt.Println. []string and []any have different memory layouts, so the conversion needs a loop that builds a []any.
  • Production note: log/slog uses variadic key-value pairs, logger.Info("msg", "device", id, "rssi", v), and go vet checks them for a missing value. Functional options, New(addr string, opts ...Option), are the common pattern for constructors with optional settings, for example an MQTT client's timeouts and TLS config.

9.7 Append

  • The lesson asks for an empty, non-nil slice, so []float64{} is required here, not var dayCosts []float64. append works on both. The difference shows in JSON: measured, a nil []float64 encodes as null and an empty one as []. An API whose clients expect an array must return the non-nil form.
  • []float64{} has cap 0, so the first append allocates. When the result count is unknown, that is fine. When an upper bound is cheap, make([]float64, 0, len(costs)) allocates once, at the cost of holding unused capacity.
  • Always assign the result of append, to the same slice in most cases. append writes into the old array when the capacity allows. Measured: y := append(x[:1], 9) on x = [1 2 3 4] gives y = [1 9] and changes x to [1 9 3 4].
  • Production note: the standard library has no slices.Filter. The plain loop is the idiom. For a large batch filtered in place, reuse the input array: out := costs[:0], then append the kept elements. Measured on [1 2 3 4 5 6], keeping even values: out is [2 4 6] and the input becomes [2 4 6 4 5 6], so the input is no longer usable. slices.DeleteFunc does the same and zeroes the tail: the input becomes [2 4 6 0 0 0], which lets the garbage collector free pointers in the removed elements.

9.8 Range

  • The element variable is a copy. Measured: for _, d := range ds { d.seen++ } on a []dev leaves every seen at 0. To change the elements, index: for i := range ds { ds[i].seen++ }. Copying also costs time for large structs, which is another reason to index or to range over a slice of pointers.
  • range evaluates its operand once, before the loop starts. Measured: appending inside for range s on a 3-element slice runs 3 iterations and leaves len 6. The loop does not see the new elements.
  • Over a slice, the loop reads each element when it gets there, so writes to later elements are visible. Over an array, range arr copies the whole array first, so they are not. Measured: setting element 2 to 99 during iteration 0 gives v = 99 for the slice and v = 3 for the array. range &arr or range arr[:] avoids the copy.
  • The nested loop is O(len(msg) × len(badWords)), and returning from inside both loops is the clean exit; no labeled break is needed. The standard library form is slices.IndexFunc(msg, func(w string) bool { return slices.Contains(badWords, w) }), measured to return 3 on the lesson example.
  • Production note: for a word list of real size, build a map[string]struct{} set once, outside the per-message path, so each lookup is O(1). The same applies to an allow-list of device IDs or CAN arbitration IDs checked per frame. A real profanity filter also normalizes case and punctuation before the lookup.

9.9 Slice of Slices

  • [][]int is a slice of slice headers. Each row is a separate slice with its own backing array, length and capacity, so rows can have different lengths. Measured: append(m[0], 7) on a 2×3 matrix gives [[0 0 0 7] [0 1 2]]. Nothing keeps the matrix rectangular.
  • range rows and range cols (range over int, Go 1.22) suit this loop. createMatrix(0, 0) returns an empty, non-nil slice with len 0, which is what the test's [][]int{} compares against. A negative size panics with runtime error: makeslice: len out of range.
  • The test compares with slices.EqualFunc(output, test.expected, slices.Equal). Passing the generic slices.Equal as a value works because the compiler infers its type argument ([]int) from EqualFunc's parameter type.
  • One make per row means one heap allocation per row. A single backing array, sliced into rows, needs one: buf := make([]int, rows*cols), then s[i] = buf[i*cols : (i+1)*cols : (i+1)*cols]. Measured for 100×100: 100 allocations and 8327 ns per call against 1 allocation and 4664 ns. The full slice expression caps each row, so an append on one row cannot overwrite the next row.
  • Production note: for numeric work, a flat []T with data[i*cols+j] indexing keeps the data in one block, which is faster to scan and to pass to C or the GPU. A [][]T fits jagged data, for example a list of message batches of different sizes.

Quiz:

  1. Why is 5 the final value in the last index of j? j and g point to the same underlying array, so g's append overwrote j.
  2. Why doesn't the bug regarding slices j and g in example 2 occur in example 1 as well? The array's cap() is exceeded, so a new underlying array is allocated.

10.2 Mutations

  • The comma-ok lookup is the only way to tell a missing key from a stored zero value. Here it also returns the user, so one lookup serves both checks. delete needs no existence check of its own: measured, delete on a missing key and on a nil map are both no-ops.
  • "Maps are reference types" is shorthand. A map variable is one pointer (measured: unsafe.Sizeof(m) is 8 on amd64) to the runtime's map structure, and the pointer is passed by value. Measured: a function that adds a key changes the caller's map, but a function that assigns m = map[string]int{...} changes only its own copy of the pointer.
  • Struct values in a map cannot be changed in place. u["x"].del = true fails with cannot assign to struct field u["x"].del in map, because map elements are not addressable (the runtime can move them when the map grows). Read the struct, change it, and store it back, or use map[string]*user.
  • delete does not give memory back. Measured: a map of 100,000 entries of 64 bytes used about 10,573 KiB, still 10,573 KiB after deleting every key, and 327 KiB once the map itself was dropped (keep = nil). clear(m) (Go 1.21) does not either: measured, 10,572 KiB after clear. A long-lived map with high churn, such as a session or device cache, must be replaced from time to time to shrink.
  • Production note: for a privacy deletion the map entry is only one copy. Logs, backups and downstream consumers that received the record also need to forget it, so a real deletion is an event that other services handle, not only a delete call.

10.3 Key TypesQuiz

Quiz:

  1. What makes a type qualify to be used as a map key? The type is comparable.
  2. Which is simpler? To use a struct directly as a key.

Notes:

  • Slices, maps and functions cannot be keys. Measured: map[[]int]int fails with invalid map key type []int. Arrays and structs of comparable fields can, which makes [2]int or a struct a natural composite key.
  • An interface key type compiles, but the check moves to run time. Measured: storing a []int in a map[any]int panics with runtime error: hash of unhashable type []int.
  • The struct key needs no setup. Measured: hits[key{"/doc/", "au"}]++ works on an empty map, while the same increment on an empty nested map panics with assignment to entry in nil map, because the inner map does not exist yet. That is the add helper the lesson shows.
  • The nested map still wins when you need everything under one outer key, for example all countries for one path, because a struct-keyed map can only answer that by scanning every entry.
  • Keys compare by ==, which has two traps. Pointer keys compare addresses, not values: measured, &b does not find an entry stored under &a, although a == b. And NaN != NaN: measured, two writes under math.NaN() create 2 entries, and neither can be read back. clear is the only way to remove them.
  • Production note: a struct key such as struct{ DeviceID string; Channel uint8 } fits per-sensor state in a telemetry pipeline. It keeps the fields typed and cannot collide the way a joined string can ("a/b"+"c" against "a"+"b/c"). Allocation is not the reason to prefer it: measured, a lookup with m[dev+"/"+strconv.Itoa(ch)] makes 0 allocations, the same as the struct key, because the compiler builds a temporary key for lookups without allocating.

10.4 Count Instances

  • m[k]++ on a missing key reads the zero value and stores 1, so it creates the key. Measured: without the existence check, counting ["cersei", "tywin"] into {"cersei": 0} gives map[cersei:1 tywin:1]. The comma-ok check is what keeps invalid users out. The if v, ok := ...; ok form scopes ok to the if.
  • The map is changed through the caller's pointer (see 10.2), so the function returns nothing. That fits the rule from 9.13: mutate in place and return nothing, or return a new value and leave the input alone.
  • A zero count and a missing key look the same on a plain read: both give 0. Only the comma-ok form tells them apart, which is why the valid users are stored with explicit 0 values.
  • Production note: counting into a map from several goroutines needs a lock, or each worker counts into its own map and the results are merged at the end. The second form needs no lock in the hot path, and fits per-partition counters in a concurrent pipeline. A fixed set of known keys can also use one atomic.Int64 per key.

10.5 Effective GoQuiz

Quiz:

  1. Maps can have at most ___ value(s) associated with the same key. 1.
  2. Attempting to get a value from a map where the key doesn't exist... Returns the zero value.
  3. A function can mutate the values stored in a map and those changes ___ the original values. Affect.
  4. What does the second return value from a retrieve operation in a map indicate? A boolean that indicates whether the key exists.

Notes:

  • One value per key, but the value can be a slice, which gives a multimap: m[k] = append(m[k], v). This works on a missing key, because m[k] returns a nil slice and append accepts it. Measured: two appends give map[a:[1 2]].
  • The result of append must be stored back in the map. Measured: s := m["a"]; s = append(s, 3) leaves the map at [1 2]. Writing to an element in place, m["x"][0] = 9, does reach the map, because the stored slice header points to the same array. This is the same rule as 9.3, one level down.
  • Comma-ok on a nil map returns the zero value and false, with no panic (measured: 0 false).
  • Sets: map[string]struct{} against map[string]bool. Measured on go1.27.3 for 100,000 string keys: about 3,444 KiB with bool and 1,855 KiB with struct{}. A bool set reads more simply (if set[k]), and a struct{} set needs comma-ok. A bool set also has a third state, a key stored with false, which is usually a bug.
  • Production note: for a set of known IDs on a small device, such as allowed CAN IDs, a sorted slice with slices.BinarySearch or a bitmap can use far less memory than either map form. Speed is not the reason: measured on amd64 for 32 uint32 IDs, lookup took 3.3 ns with the map, 3.5 ns with slices.BinarySearch, and 5.1 ns with slices.Contains. The common claim that a linear scan beats hashing for small sets did not hold here.

10.6 Nested

  • The empty-name guard is needed. Measured: []rune("")[0] panics with index out of range [0] with length 0.
  • []rune(name) decodes and copies the whole string to read one character. Measured: 1 allocation per name for a 38-character name. r, size := utf8.DecodeRuneInString(name) reads only the first character, makes 0 allocations, and returns size 0 for an empty string, which replaces the length check: if size == 0 { continue }. A for _, r := range name { first = r; break } loop does the same.
  • Invalid UTF-8 does not fail. Measured: utf8.DecodeRuneInString("\xffabc") returns '�' (utf8.RuneError) with size 1, and []rune also turns the bad byte into U+FFFD. All names that start with a bad byte share one bucket under '�'.
  • The inner map can be fetched once: inner := m[first]; if inner == nil { inner = make(map[string]int); m[first] = inner }; inner[name]++. This is the lesson 10.3 add helper. The solution's comma-ok check and the second m[first] both hash the key again.
  • Production note: a nested map is the right shape here, because callers ask "all names under one letter", which a struct key cannot answer without a full scan (see 10.3). For grouping by first letter in a UI, fold case and accents first. unicode.ToUpper handles case only: measured, it maps 'e' to 'E' but 'é' to 'É', so accented names still land in their own group. Removing accents needs Unicode normalization, for example golang.org/x/text.

10.7 Distinct Words

  • strings.FieldsSeq (Go 1.24) yields the fields as an iterator instead of building a []string. Measured on a 10-word message: strings.Fields makes 1 allocation, FieldsSeq makes 0. When the fields are only looped over once, the Seq form is the better default.
  • Fields splits on any Unicode white space, not only spaces. Measured: "a\tb\nc d e" gives [a b c d e], including the no-break space. It also keeps punctuation: "Hello, hello! HELLO" gives 3 distinct words after lowering. The course tests count "Bar!" as its own word, so this matches the spec, but real word counting strips punctuation first, for example with strings.FieldsFunc and unicode.IsLetter.
  • The lesson says struct{} "uses no memory" and bool "uses 1 byte". The value itself does, but map slots are padded. Measured in 10.5: 100,000 string keys took about 3,444 KiB with bool and 1,855 KiB with struct{}, a far larger gap than 1 byte per entry.
  • The map keys are substrings of the lowered message, so they share its memory. Each key keeps the whole message alive. Measured: keeping one short word from each of 100 messages of 100 KB retained about 10,416 KiB; with strings.Clone(w) before storing, 7 KiB. Clone keys that outlive a large input, for example tags pulled from MQTT payloads into a long-lived index.
Chapter 11

Pointers

9 lessons

11.1 Introduction to Pointers

  • A pointer is one machine word: unsafe.Sizeof(&m) is 8 on amd64. Its zero value is nil, and fmt.Println prints a nil *int as <nil>. Dereferencing it panics with invalid memory address or nil pointer dereference.
  • fmt follows a pointer to a struct one level: %v on &m prints &{Pumpkin hi} and %+v prints &{Recipient:Pumpkin Text:hi}. A pointer to anything else, such as a *string, prints as an address. Format verbs that "look right" on a struct pointer can hide that a pointer was passed.
  • Returning &x for a local x is safe in Go, unlike C. The compiler moves x to the heap: go build -gcflags=-m reports moved to heap: x. Passing &m to fmt.Printf also moves m to the heap, because fmt takes any and the compiler cannot prove the pointer does not escape.
  • Production note: take a pointer when the callee must change the value, when the value is large, or when the type holds something that must not be copied (sync.Mutex, see go vet's copylocks). Small read-only structs like Message (two strings, 32 bytes) are fine to pass by value.

11.2 References

  • Strings are immutable, so *message = s does not edit the caller's bytes. It replaces the caller's string header (pointer and length) with one that points to the new text. The pointer is what lets the function change which string the caller's variable holds.
  • A nil *string panics on the first *message with invalid memory address or nil pointer dereference. The course signature has no error return, so the choice is to document "must not be nil" or to return early on nil.
  • strings.ReplaceAll returns its input unchanged when there is no match. Measured: three passes over clean text make 0 allocations, and 3 when every word matches. strings.NewReplacer("fubb", "****", ...) does one pass, but it is not cheaper here: measured, 3 allocations on clean text and 3 on dirty text. Measure before swapping one for the other.
  • Plain substring replacement also hits words that contain the target. Measured: "Switch the witchcraft" becomes "S***** the *****craft". The course's "mother****er" case depends on this. A real filter matches on word boundaries.
  • Production note: a function that rewrites its input through a pointer is harder to test and to use concurrently than func clean(s string) string. Return the new string and let the caller assign it. Pointer parameters fit best when the value is large or must be shared, not for a 16-byte string header.

11.3 Pass by Reference

  • Go has no pass by reference. Every argument is copied, and a pointer argument is a copied address. The function can change what the address points to, but assigning a new pointer to a inside it changes only its own copy (the same rule as maps in 10.2 and slice headers in 9.3).
  • a.MessagesTotal on a pointer is shorthand for (*a).MessagesTotal. The lesson's wrong form fails with invalid operation: cannot indirect a.MessagesTotal (variable of type int), because * binds after the selector: it means *(a.MessagesTotal).
  • a.MessagesTotal++ is a read, an add and a write, not one step. Measured: 1000 goroutines calling analyzeMessage on one Analytics gave {950 495 486} without -race: 50 updates were lost, and 495 + 486 = 981 no longer equals the total of 950. With -race: Found 6 data race(s).
  • Production note: a shared counter struct needs a sync.Mutex around the whole update, or atomic.Int64 fields. Atomics make each field correct but not the set: a reader can still see Total updated and Failed not yet. If the fields must agree, use the mutex, or drop the derived field and compute Total as Succeeded + Failed when read. For a telemetry pipeline with many workers, per-worker counters merged at read time avoid contention entirely.

11.4 Pointers QuizQuiz

Quiz (code: var x int = 50, var y *int = &x, *y = 100):

  • What is the value of *y after the code runs? Answer: 100.
  • What is the value of x after the whole block runs? Answer: 100.

Notes:

  • *y = 100 writes through the pointer into x. y itself does not change: it still holds &x, so y == &x is true. *y and x name the same variable.
  • Taking an address does not by itself move a variable to the heap. Escape analysis decides. With -gcflags=-m, a variable that must live on the heap is reported as moved to heap: x. A line like x escapes to heap next to fmt.Println(x) is about the copy boxed into the any argument, not about x.
  • Since Go 1.26, new takes an expression: p := new(50) gives a *int pointing at 50. It replaces the v := 50; p := &v pattern and helper functions like ptr[T any](v T) *T used to fill optional pointer fields in JSON or AWS SDK structs (aws.String, aws.Int32).

11.5 Nil Pointers

  • The nil check must come before the first *message. Copying *message into a local first, as 11.2 did, is the dereference that panics.
  • A nil dereference is a runtime panic, runtime error: invalid memory address or nil pointer dereference, raised from a SIGSEGV. recover() in a deferred function of the same goroutine catches it.
  • A panic in another goroutine kills the whole process. Measured: a nil dereference inside go func() { ... }() exited the program, and the deferred recover() in main never ran. Each worker goroutine that must survive bad input needs its own defer recover().
  • A nil pointer stored in an interface is not a nil interface. Measured: passing a nil *strings.Reader to func check(r io.Reader) gives r == nil as false, while passing a literal nil gives true. The == nil check in this lesson works because the parameter is a concrete *string.
  • Production note: check for nil where untrusted data enters (a decoded optional JSON field, a missing CAN signal in a parsed frame), and treat nil inside the core as a programming error rather than guarding every function. A silent early return, as in this lesson, hides the caller's bug. Where nil is a valid input, say so in the doc comment.

11.6 Pointer ReceiversQuiz

Quiz:

  • Which is more widely used in Go? Answer: pointer receivers.

Notes:

  • c.setColor("blue") on a car variable is shorthand for (&c).setColor("blue"). Go only does this when c is addressable. A map element or a composite literal is not: m["a"].setColor("blue") and car{}.setColor("x") both fail with cannot call pointer method setColor on car.
  • Method sets: *car has both pointer and value methods, car has only value methods. A car value therefore does not satisfy an interface that needs a pointer method: car does not implement colorer (method setColor has pointer receiver). Store &car{} in the interface.
  • for _, c := range cars { c.setColor("blue") } changes a copy of each element. Measured: the slice stays [{white} {white}]. Index with cars[i].setColor("blue") to change the elements.
  • A value receiver copies the struct, including any lock in it. go vet reports get passes lock by value: recv/b.counter contains sync.Mutex. A copied mutex does not protect the original.
  • Production note: use a pointer receiver when the method changes the receiver, when the struct is large, or when it holds a sync.Mutex or other non-copyable state. If one method needs a pointer receiver, give all of the type's methods pointer receivers (Go Code Review Comments). Mixed receivers make the method set hard to predict when the type is stored in an interface. Small immutable values such as time.Time keep value receivers.

11.7 Pointer Receiver Code

  • The bug was a value receiver: setMessage changed a copy of the email. Changing the receiver to *email fixes it, and the call site test.e.setMessage(...) stays the same, because Go takes &test.e for the call.
  • The automatic &e does not force a heap allocation. With -gcflags=-m, a method that only writes through its receiver reports e does not escape, and the caller's local e has no moved to heap line. Escape analysis looks at what the method does with the pointer, not at the &.
  • Calling a method on a nil pointer receiver is legal. The panic comes at the first field access inside the method: p.setMessage("boom") with var p *email fails on e.message = s with invalid memory address or nil pointer dereference. A method can check if e == nil and handle it, as a String() returning "<no email>" did when measured. The standard library does this: (*big.Int).String returns "<nil>" for a nil *big.Int.
  • Production note: Go does not use getters and setters for plain fields. Within a package, e.message = "..." is the normal form. An exported setter earns its place when it keeps an invariant (validation, a lock, an updated timestamp). Effective Go names a getter Message(), not GetMessage(), and the setter SetMessage.

11.8 Pointer PerformanceQuiz

Quiz:

  • Where are the values to which pointers point usually stored in Go? Answer: heap.
  • Which is typically more performant to pass to a function, especially for small amounts of data? Answer: value.

Notes:

  • The quiz's "heap" is the course's simplification. Escape analysis decides, not the &. Measured with -gcflags=-m: func sumPtr(p *point) reports p does not escape, so the caller's point stays on the stack. Only return &point{...} reported &point{...} escapes to heap.
  • Returning a pointer is where the cost is. Measured on a 24-byte point with //go:noinline: newVal returning point took about 2 ns and 0 allocs/op, newPtr returning *point about 27 ns and 1 alloc/op (24 B). Passing the same struct into a function by value or by pointer measured the same, about 2 ns.
  • Copying cost shows up only for large values. Measured on a 4 KiB struct: by value about 20 ns/op, by pointer about 1.6 ns/op, both 0 allocs/op. The pointer stayed on the stack (b does not escape), so the lesson's "the value will probably move to the heap" does not apply when the callee does not keep the pointer.
  • Production note: return values from constructors of small types (time.Time, netip.Addr), and use pointers for identity or shared state. In a hot path such as a frame-decoding loop, a func decode() *Frame per frame means one heap allocation and more GC work per message. Decoding into a caller-owned value or buffer (func decode(dst *Frame) error) keeps it at zero. Check with -benchmem and -gcflags=-m, not by intuition.

11.9 Update Balance

  • The withdrawal check t.amount > c.balance allows a withdrawal of the whole balance and returns before the subtraction, so the balance stays unchanged on error, as the spec asks. default catches every other transactionType. A named string type does not limit its values: the test passes the untyped constant "unknown", which converts to transactionType without a cast.
  • float64 is wrong for money. Measured: a balance of 0.3 and three withdrawals of 0.1 gives 0.19999999999999998, then 0.09999999999999998, then insufficient funds on the third. Store integer minor units (int64 cents) or use a decimal type.
  • The function trusts its input. Measured: a withdrawal of -500 raised a balance of 100 to 600 with a nil error, and a deposit with customerID: 99 was applied to customer 1. The spec asks for neither check. Real code rejects amount <= 0 and a customerID that does not match c.id.
  • errors.New inside the function creates a new error value on each call, so callers can only compare the text. Measured: errors.Is(err, errors.New("insufficient funds")) is false. Declare var ErrInsufficientFunds = errors.New("insufficient funds") at package level and return that, so callers can use errors.Is.
  • Production note: updating a balance is a read, a check and a write. With many goroutines the check can pass for two withdrawals that together overdraw the account (see 11.3). Hold one lock per customer around the check and the write, or let the database do it in one statement (UPDATE ... SET balance = balance - $1 WHERE id = $2 AND balance >= $1) and check the affected row count.

12.1 Packages

  • Only package main with a func main() builds an executable. The same file under package mailio still compiles: go build exits 0, writes no binary, and func main is an ordinary unexported function. go run refuses it with package pkg/lib is not a main package.

12.13 Clean PackagesQuiz

Quiz:

  • Should you export code from the main package? Answer: no.
  • When should you NOT export a function, variable, or type? Answer: when the end user doesn't need to know about it.
  • Should you often change a package's exported API? Answer: no, try to keep changes to internal functionality.

The lesson's four rules: hide internal logic behind a small exported API, don't change exported APIs, don't export from main, and a package should know nothing about the packages that use it. Each rule below comes with what the toolchain actually enforces, measured in a scratch module example.com/lib (packages can, internal/codec, cmd/tool) and a consumer module example.com/other.

Hide internal logic

  • Lowercase names hide identifiers. The internal/ directory hides whole packages. Measured: importing example.com/lib/internal/codec from another module fails with use of internal package example.com/lib/internal/codec not allowed. Code under lib/ can import it, code outside cannot. This is how to share helpers between your own packages without making them public API.
  • An exported function that returns an unexported type leaks half of it. Measured: can.NewReader() returning *reader compiles, and the caller can use the value, but cannot name its type: var x can.reader fails with name reader not exported by package can. The caller cannot declare a field or a parameter of that type. revive flags it as unexported-return: exported func NewReader returns unexported type *can.reader, which can be annoying to use, but revive is not in golangci-lint's default linter set: the default run reported 0 issues, and --enable-only revive found it. Return an exported type, or an exported interface.

Don't change exported APIs

Some changes break callers in ways that are not obvious:

  • Adding a method to an exported interface breaks every implementation outside the package. Measured: adding Reset() to can.Decoder gave myDecoder does not implement can.Decoder (missing method Reset) in the consumer. Keep interfaces small, and add a new interface instead (the io.Reader / io.ReaderAt pattern).
  • Adding a field to an exported struct breaks callers that use unkeyed literals. Measured: adding DLC uint8 to can.Frame made can.Frame{1, nil} fail with too few values in struct literal of type can.Frame. go vet warns about the unkeyed literal before that happens: example.com/lib/can.Frame struct literal uses unkeyed fields.
  • A breaking change needs a new major version, and from v2 the major version is part of the module path. Measured: require example.com/lib v2.0.0 for a path without /v2 fails with version "v2.0.0" invalid: should be v0 or v1, not v2. The module must be renamed example.com/lib/v2, so every importer changes its imports. That cost is deliberate: it is why rule 2 matters.
  • Below v1.0.0, Go's semantic versioning makes no compatibility promise. Tag v1 only when the API is meant to stay.

Don't export from main

  • Measured: importing example.com/lib/cmd/tool fails with import "example.com/lib/cmd/tool" is a program, not an importable package. An exported name in main is visible to no one, so the capital letter only misleads the reader. Code that another program, or a test in another package, might need belongs in a library package that main imports (see 12.1).

Packages shouldn't know about their dependents

  • Interfaces in Go are satisfied implicitly, so a package does not need to import its consumers to work with them. Measured: myDecoder in other satisfies can.Decoder without can knowing it exists. The usual direction is the reverse: the consumer declares the small interface it needs (type frameSource interface { Next() (can.Frame, error) }), and the library returns concrete types ("accept interfaces, return structs").
  • The compiler enforces one consequence of getting this wrong. Measured: a importing b and b importing a fails with import cycle not allowed. A cycle usually means a low-level package has learned something about the application, for example a CAN decoder that imports the telemetry uploader to call it. Return the data, or take a callback or an interface, and let the application connect the two.

Production note

  • Package by responsibility, not by kind. can, uploader, ota read well at call sites (can.Frame, uploader.New). models, utils, handlers collect unrelated code, and they tend to create cycles.
  • Keep packages few and the exported API small. Each exported name is a promise. Starting with everything unexported and exporting on demand is cheap. Unexporting later breaks someone.
  • A common layout for a service repo: cmd/<binary>/main.go (wiring only), library packages at the root or under internal/ when no other repo should import them. For a fleet of device services in one repo, internal/ keeps shared code private while still allowing reuse across binaries.
  • Use doc comments on every exported name, starting with the name (12.10). go doc and pkg.go.dev render them, and that is the API documentation most users read.

13.1 Concurrency

  • go func() { ... }() starts the closure and returns at once, so Email sent prints first and Email received 250 ms later. The closure captures the parameter message, which no one changes afterwards, so sharing it is safe. go run -race reports nothing.
  • The order on screen comes from the sleeps (250 ms in the goroutine, 500 ms in test), not from any synchronization. The Go memory model orders events only through synchronization (channels, sync, atomic). A sleep does not order anything, so on a loaded machine the 250 ms goroutine could in principle print after test moves on.
  • When main returns, the program exits and every other goroutine stops mid-flight. Measured: without the sleep in test, a main that starts the goroutine and prints sent prints only sent. received never appears, and there is no error. The next lessons replace the sleep with channels; sync.WaitGroup (chapter 14) is the other common way to wait.
  • Goroutines are cheap but not free. Measured: 100,000 goroutines blocked on a channel used 2,053 bytes of stack each (the initial 2 KiB stack) and about 2.7 KB of total memory each, about 270 MB in all. A blocked goroutine is never collected, so one that waits forever is a memory leak.
  • Production note: every goroutine needs an owner who knows how it ends, usually through a context.Context and a WaitGroup or errgroup.Group. "Send thousands of emails at once" means one goroutine per email only up to a limit: bound the concurrency with a worker pool or a semaphore, or the remote server's rate limit, the file descriptor limit, or memory will set the limit for you. To test timing code like this without real sleeps, use testing/synctest (stable since Go 1.25). Measured: inside synctest.Test, a goroutine sleeping 250 ms reports fake elapsed: 250ms while the test takes 0.004s.

13.2 Channels

  • Fix: go sendIsOld(isOldChan, emails), then three receives on the calling goroutine. Before the fix, main sends on an unbuffered channel with no receiver. Measured: fatal error: all goroutines are asleep - deadlock! with goroutine 1 [chan send]. Tests pass under go test -race with -count=200 and GOMAXPROCS set to 1, 2 and 16.
  • Why it is correct (memory model): on an unbuffered channel the send and the receive meet, and a send is synchronized before the matching receive completes. The three values arrive in the order they were sent, because a channel is FIFO and there is a single sender. No memory is shared: emails is an array, so go sendIsOld(..., emails) copies it, and the bools are copied through the channel. That is why -race finds nothing.
  • Deadlock detection only fires when *every* goroutine is blocked. Measured: with one unrelated goroutine looping on time.Sleep, an extra <-ch hangs forever and nothing fatal is printed (killed by timeout). The same extra receive inside go test shows no deadlock message either. It hangs until -timeout (panic: test timed out after 3s; the default is 10m). A production service always has live goroutines, so a deadlock there shows up as a stall, not a crash.
  • The receiver must take exactly as many values as the sender sends. Too many receives deadlock (above). Too few leak the sender. Measured: 1000 runs that read 2 of 3 values left goroutines: 1001, each sender stuck forever in chan send. for i := range isOld { isOld[i] = <-isOldChan } removes the repetition but keeps the coupling. The usual fix is for the sender to close the channel and the receiver to range over it, which comes later in this chapter.
  • time.Date normalizes out-of-range fields. Measured: time.Date(2020, 0, 0, ...) is 2019-11-30 (month 0 is December 2019, day 0 is the last day of the month before), so the cutoff in sendIsOld is not 2020-01-01. time.Date(2019, 2, 0, ...) is 2019-01-31.
  • Production note: a pipeline stage that sends with a bare ch <- v leaks as soon as its consumer stops early (error, shutdown, a break in the loop). Make every blocking send cancellable: select { case out <- v: case <-ctx.Done(): return ctx.Err() }. Measured: the 1000-run leak above with the sender selecting on ctx.Done() and the receiver calling cancel() ends with goroutines: 1. The unbuffered handoff is also natural backpressure: a slow consumer (an MQTT publish, say) slows the CAN reader instead of letting a queue grow without limit.

13.3 Channels

  • waitForDBs receives one token per database: for range numDBs { <-dbChan }. A bare <-ch waits for the signal and throws the value away. chan struct{} is the usual type for a signal, since the value carries no data.
  • The course's own code has a data race. The browser passes because it runs Go as WebAssembly, and the race detector is not available there (measured: -race is not supported on js/wasm). Without -race, the test also passes locally. Under go test -race, the test's reads of *count (main_test.go:37) race with count++ in the goroutine. The goroutine increments the count *after* its send. A receive only makes visible the writes the sender did *before* the matching send. So the test's read has no synchronization with the increment.
  • Running on one thread does not hide a race. Measured: GOMAXPROCS=1 go test -race still reports it. The detector checks happens-before order (vector clocks), not whether two threads actually ran at the same time.
  • Repo change from the course: count++ moved above ch <- struct{}{} in the "don't touch" code. Now the final receive in waitForDBs comes after the last increment, so the test's read is synchronized. Measured: go test -race -count=50 is clean with GOMAXPROCS set to 1, 2 and 16.
  • The test's for *count != n { ... } is a spin-wait on shared memory. The Go memory model gives a matching example (for !done {}) and says a racy read like this is not guaranteed to ever see the write. Measured: a call-free spin on a racy *p did see the write today, but that is luck from today's compiler, not a guarantee.
  • Production note: to wait until N dependencies are up, use sync.WaitGroup (or errgroup.Group if startup can fail) rather than counting tokens. To share a counter, use atomic.Int64, or send the value through the channel. Never spin on shared memory. A boot wait also needs a deadline: select on the ready signal and on ctx.Done(), so a database that never comes up fails startup instead of hanging it.

13.4 Buffered Channels

  • make(chan string, len(emails)) gives the channel room for every email, so the function can send them all on its own goroutine and return. len(ch) is the number of values queued in the buffer, and cap(ch) is the buffer size. Tests pass under go test -race -count=50 with GOMAXPROCS set to 1, 2 and 16.
  • With a buffer one slot too small, the last send has no free slot and no receiver. Measured: fatal error: all goroutines are asleep - deadlock! with goroutine 1 [chan send]. For an empty slice, make(chan string, 0) is an unbuffered channel (measured: len 0, cap 0). That is harmless here, because nothing is sent.
  • Memory model: a send happens before the matching receive completes, buffered or not. A buffered channel also has a rule for capacity C: the kth receive happens before the (k+C)th send completes. That rule is why a buffered channel works as a semaphore that limits how many goroutines run at once (sem <- struct{}{} to acquire, <-sem to release). Unlike an unbuffered channel, a buffered send does not wait for the receiver, so the sender learns nothing about whether the value was received.
  • The whole buffer is allocated up front. Measured: make(chan string, 1_000_000) allocated 16,012,600 bytes, 16 bytes per string header (16,000,000) plus some overhead, before any value was sent.
  • len(ch) is a snapshot. Here only one goroutine touches the channel, so it is exact. With concurrent senders or receivers it is stale as soon as it returns. Use it for metrics (queue depth), never for decisions like "if len(ch) < cap(ch) then send".
  • Idiom: return <-chan string. The course returns chan string, but the caller should only receive. The test still compiles, since len works on a receive-only channel. A send by the caller is a compile error. Measured: invalid operation: cannot send to receive-only channel <-chan string.
  • Buffering makes a handoff cheaper: fewer goroutine park and wake-ups. Measured with one producer and one consumer, in ns per value: buffer 0 597, 1 424, 16 165, 128 119, 1024 148 with GOMAXPROCS=16. With GOMAXPROCS=1 they were 196, 115, 43, 33, 29. The single-P run is faster, because the handoff never crosses a core.
  • Production note: a buffer absorbs bursts. It does not fix a consumer that is slower on average; that only delays the moment the producer blocks, and a buffer as big as the input removes backpressure entirely. Size it from a measured burst (for example, CAN frames per publish interval), and export len(ch) as a queue-depth gauge. Values still in the buffer at shutdown are lost unless the consumer drains them: close the channel, then range until it is empty, before exiting.

13.5 Closing Channels in Go

  • countReports loops with num, ok := <-numSentCh, breaks on !ok, and sums. This matches the spec, which asks for an infinite for loop. Tests pass under go test -race -count=50 with GOMAXPROCS set to 1, 2 and 16. Next lesson's for num := range numSentCh does the same loop and the ok check in one line.
  • ok is false only when the channel is closed *and* empty. Buffered values sent before close are still delivered. Measured on a buffer holding 1 and 2, then closed: 1 true, 2 true, 0 false, 0 false. After that, every receive returns the zero value at once.
  • Without the ok check, the loop never ends. A closed channel never blocks, so it spins adding zeros. Measured: acc 5 and 1,194,618 receives in 100 ms. That is a hot CPU loop, not a deadlock, so the runtime reports nothing.
  • Measured panics and deadlocks:
    • panic: send on closed channel
    • panic: close of closed channel
    • panic: close of nil channel
    • A receive on a nil channel blocks forever: fatal error: all goroutines are asleep - deadlock!, goroutine 1 [chan receive (nil chan)]. So countReports(nil) would hang.
  • Memory model: closing a channel happens before a receive that returns because the channel is closed. Everything sendReports wrote before close(ch) is visible to the receiver once it sees ok == false. That is why close works as a broadcast "done" signal to any number of receivers.
  • Only the sender closes, and only when it is the *only* sender. Measured: two goroutines send on a buffered channel and one of them closes it. Without -race, 29 of 200 runs panicked with send on closed channel, and the other 171 printed survived. With -race, 20 of 20 runs reported DATA RACE (runtime.closechan against the send). The race detector catches the bug even on runs that do not panic.
  • Production note: in fan-in with N producers, no producer closes the output channel. A separate goroutine does wg.Wait(); close(out), so the consumer's range ends exactly once, after every producer is done. Closing is optional for garbage collection: an unreferenced channel is collected, open or closed. But a goroutine blocked on a channel that will never get another value is a leak (13.2), so close every channel that a receiver ranges over.

13.6 Range

  • concurrentFib makes the channel, starts go fibonacci(n, ch), and does for x := range ch { xs = append(xs, x) }. Ranging over a channel receives until the channel is closed and empty, which is the 13.5 ok loop in one line. Tests pass under go test -race -count=50 with GOMAXPROCS set to 1, 2 and 16.
  • n is known in advance, so xs := make([]int, 0, n) saves the repeated grows. For n == 0, var xs []int returns nil. The test passes anyway, because slices.Equal compares lengths. JSON tells them apart. Measured: json.Marshal gives null for the nil slice and [] for []int{}. That matters when the slice goes into an API response.
  • The range loop depends on the producer closing the channel. Without close(ch) in fibonacci, the loop deadlocks after the last value (13.2). If the consumer stops early, the producer leaks. Measured: 1000 runs that break out of the range loop left goroutines: 1001, each fibonacci stuck on its next send.
  • int overflows silently. Measured: F(92) = 7540113804746346429 is the last value that fits, and F(93) prints -6246583658587674878.
  • Go 1.23+: a channel used only as a generator inside one goroutine's flow is better written as an iterator, iter.Seq[int] (range-over-func). It needs no goroutine, cannot leak (when the loop breaks, yield returns false and the iterator returns), and is far cheaper. Measured for n=90: channel 54,765 ns/op, 905 B, 3 allocs. iter.Seq 415 ns/op, 768 B, 1 alloc (the preallocated slice). That is about 130 times faster, because every channel value costs a goroutine handoff. The same 1000 early breaks with iter.Seq added no goroutines.
  • Production note: use channels when there is real concurrency — the producer does I/O (reading a CAN socket, consuming MQTT) or runs in parallel with the consumer. Use iter.Seq for a pure sequence. In a channel pipeline, the producer selects on ctx.Done() around every send, and the consumer cancels the context when it stops early. That turns "break leaks the producer" into a clean shutdown.

13.7 Select

  • logMessages loops forever over a select with one case per channel. It logs each value and returns on the first !ok, as the spec asks. The lesson has no test file, so this was checked by running the program. Measured: go run -race prints the same output with GOMAXPROCS set to 1 and 16 (same md5), the run takes about 5.2 s, and there are no race reports. The order is the same every run because rand.NewSource(0) fixes the sleep times.
  • Returning on the first close is safe here only because of how the course code is built. sendToLogger waits for both sends of every pair (<-done twice) and closes both channels only at the end, so nothing is left unread. In general, returning when one input closes abandons the other one. Measured: 100 runs where emails closed at once while one SMS was still pending left goroutines: 101, each SMS sender stuck on its send.
  • To drain both channels, set a closed channel to nil. A nil channel is never ready, so select skips its case. Loop for chEmails != nil || chSms != nil. Measured: one email and three SMS were all logged, then both drained.
  • A closed channel is always ready. Without the ok check, its case wins every time the other channel is quiet. Measured: 439,930 iterations in 100 ms, a hot loop that never deadlocks.
  • When several cases are ready, select picks one uniformly at random. Measured over 1,000,000 selects with both ready: a: 498969 b: 501031. Case order is not a priority, so prefer one channel by writing a nested select, or by checking it first with a default case (next lesson). select {} blocks forever. Measured with no other goroutines: fatal error: all goroutines are asleep - deadlock!, goroutine 1 [select (no cases)].
  • Memory model: select adds no rule of its own. The chosen case is an ordinary send or receive, so the happens-before rules from 13.2 to 13.5 apply to whichever case runs.
  • Production note: a pipeline stage's main loop is a select over its inputs and <-ctx.Done(), for example CAN frames, MQTT acks and a ticker for flush or heartbeat. Nil out each input as it closes, return on ctx.Done(), and decide on purpose whether shutdown drains what is buffered or drops it. Random choice also means a flood on one input cannot starve the others completely, but it does not give priority either. A control channel that must win needs its own check first.

13.8 Select Default Case

  • saveBackups loops over a select with three branches. A tick calls takeSnapshot. saveAfter calls saveSnapshot and returns. default calls waitForData and sleeps 500 ms. saveSnapshot closes logChan, which ends the test's range. Tests pass under go test -race -count=5 with GOMAXPROCS set to 1, 2 and 16. Each run takes about 3.7 s of real time.
  • The test depends on how ties resolve, not only on the durations. Ticks fall at 1.5 s and 3.0 s, and the 500 ms sleeps end at the same instants. With a real clock, the expected log works because each loop iteration adds a little drift, so the sleep ends just after the tick. Under testing/synctest the times are exact. Measured: logs at 0s 500ms 1s 1.5s(snapshot) 1.5s 2s 2.5s 3s(snapshot) 3s 3.5s(saved), matching the course's expected list, in 0.004 s instead of 3.5 s. Inside the bubble, the timers due at an instant fire before the goroutines blocked on them run, so the tick is already ready when select looks.
  • Measured: every go test -race run in this chapter takes about 1 s because the race runtime sleeps 1 s at exit (GORACE=atexit_sleep_ms, default 1000). With GORACE=atexit_sleep_ms=0, the synctest run took 0.016 s instead of 1.023 s.
  • default turns select into a non-blocking poll. default plus Sleep is polling: up to 500 ms of extra delay on every event, and it wakes even when nothing happened. The idiomatic form blocks on all the events, with a ticker for the "still alive" log: case <-heartbeat.C: log(...). Use default for "try to send, otherwise drop or count": select { case out <- v: default: dropped++ }.
  • Since Go 1.23, with go.mod at go 1.23 or later, timer channels are unbuffered. Measured: len(t.C) and cap(t.C) are both 0. A ticker sends only when its receiver is ready, and ticks that come while the receiver is busy are dropped. Measured: a 100 ms ticker with 250 ms of work per tick delivered 4 ticks in about 1 s, not 10. Also since 1.23, an unreferenced time.Tick ticker is garbage collected, so the old "time.Tick leaks" advice no longer holds. time.NewTicker plus defer t.Stop() is still the clearer choice when the owner is a long-lived function.
  • Directional parameters (<-chan time.Time, chan<- string) state each goroutine's role in the signature. logChan should be chan<- string in the course helpers, since they only send and close.
  • Production note: a backup or flush loop selects on ctx.Done(), a flush ticker, and the data channel. It does not sleep in default. For drop-on-full backpressure (telemetry on a constrained link), the default send above is the idiom. Export the drop counter, so the drops can be seen.
  • Repo change from the course: the test body is wrapped in synctest.Test(t, func(t *testing.T) { ... }), and nothing else changed. The ticker, the time.After and logChan are all created inside the bubble, so the fake clock drives them. Measured with GORACE=atexit_sleep_ms=0: one run takes 0.016 s instead of 3.52 s, and -race -count=100 takes 0.08 to 0.13 s with GOMAXPROCS set to 1, 2 and 16.
  • synctest gotchas, measured:
    • A time.Tick created *outside* the bubble runs on the real clock. The test waited a real 1.00 s while the bubble reported fake elapsed: 0s.
    • A goroutine blocked on a channel created outside the bubble is not "durably blocked", so fake time stops advancing. A time.Sleep(time.Second) in the bubble never returned, and the test ended with panic: test timed out after 5s.
    • Real I/O, syscalls and cgo do not count as durable blocking either. Use in-memory fakes such as net.Pipe.
    • synctest.Wait() blocks until every goroutine in the bubble is durably blocked. That makes checks like "nothing yet at 249 ms, done at 250 ms" deterministic (100 runs under -race in 0.046 s).

13.10 Ping Pong

  • Bug: the course's pingPong ran the pong-receiving loop as go func() { ... }(). pingPong returned at once, main ran all three games and exited, and every goroutine was killed before it printed anything (13.1). Fix: run the loop on the calling goroutine. The loop ends when ponger closes pongs, and ponger closes it after pinger closes pings. So pingPong returns only after the whole chain has finished. Measured: go run -race gives the same output on 15 runs with GOMAXPROCS set to 1, 2 and 16, with no race reports, in about 2.3 s (1.25 s of pinger sleeps plus the race runtime's 1 s exit pause).
  • Idiom: once the go is gone, the func() { ... }() wrapper does nothing. Write the for range pongs loop directly in pingPong. for i := range pongs does not work here, because ranging over a channel gives values, not indexes, so the counter stays.
  • Only part of the output order is guaranteed. Channel operations order sending ping i before got ping i, and got ping i before got pong i, because each print happens before the send that the next goroutine receives. The order of got pong i relative to sending ping i+1 comes only from pinger's growing sleeps, since nothing makes pinger wait for a pong. Measured: with the sleep set to 0, 200 runs produced 116 different outputs (for example sending ping 1 printed before got pong 0), still with no races. Interleaving is not a race, and the logic stays correct.
  • The game is not lock-step: pinger never waits for a pong. A real request/response exchange gives the requester a reply channel, or receives the pong before it sends the next ping.
  • Production note: this is a three-stage pipeline (pinger, then ponger, then the consumer). Each stage closes its output when its input closes, and the close travels down the chain. That is the shutdown rule for channel pipelines: closing the source channel drains and stops every stage in order, and the last stage's range ending is the "done" signal. Add ctx.Done() to every send so the chain can also be stopped from the far end.

14.1 Mutexes in Go

  • inc and val each take sc.mu.Lock() and defer sc.mu.Unlock() around the slow helper. val locks too, because a read that overlaps a write is still a data race. go test -race passes for all four cases.
  • Without the locks, a normal build crashes with fatal error: concurrent map writes, and -race reports WARNING: DATA RACE. Both measured. The crash is a runtime fatal error, not a panic, so recover cannot catch it.
  • The value receivers work only because mu is a *sync.Mutex and counts is a map. Each method call copies the struct, but the copies share the same mutex and the same map. With a sync.Mutex field held by value, every call would lock its own copy and nothing would be protected. go vet catches it: inc passes lock by value: scratch/valmu.c contains sync.Mutex (measured).
  • Production note: the usual form is a sync.Mutex value field (its zero value is ready to use, so no constructor) with pointer receivers, and the mutex declared directly above the fields it guards. A pointer mutex adds a separate allocation and a nil value to forget. Keep the critical section short: here it includes time.Sleep, which serializes every goroutine on that sleep. In a pipeline that counts per-device messages, lock only the map update, never the I/O.

14.2 Why Is It Called a "mutex"?Quiz

Quiz:

  1. What does the term 'mutex' refer to? Mutual Exclusion.

Notes:

  • A mutex excludes all goroutines but one from the guarded data at a time. By convention the field is named mu and sits directly above the fields it guards.
  • A Go mutex has no owner. One goroutine can lock it and a different goroutine can unlock it. Measured: unlocking from a second goroutine works, as the sync.Mutex.Unlock doc states.
  • A Go mutex is not reentrant. A second Lock on the same goroutine blocks forever. Measured: fatal error: all goroutines are asleep - deadlock!. The common case is an exported method that locks and then calls another exported method that also locks. Fix: put the logic in an unexported helper that assumes the lock is held, and lock only in the exported method.

14.3 Mutex ReviewQuiz

Quiz:

  1. How many goroutines can hold the same mutex lock at once? 1.
  2. Why would you use a mutex? To safely access shared resources concurrently.

Notes:

  • The lesson says the unguarded map "can panic". It is a runtime fatal error, not a panic, so recover cannot catch it (14.1). Measured on 16 cores: the course's unguarded writeLoop/readLoop program stopped with fatal error: concurrent map iteration and map write in 3 of 3 runs. The runtime detects this only on a best-effort basis. -race is the reliable check.
  • The course calls Lock/Unlock without defer inside the loops, and that is right. A defer in a loop runs only when the function returns, so defer mu.Unlock() in writeLoop would never release the lock, and the second Lock would deadlock (14.2: not reentrant). To use defer per iteration, move the loop body into its own function.
  • readLoop holds the lock across the whole range and every fmt.Println, so the writer waits for terminal I/O. Production fix: copy the data under the lock, unlock, and then do the I/O on the copy. maps.Clone (Go 1.21) makes that copy in one call. When reads far outnumber writes, sync.RWMutex lets readers share the lock.

14.4 RW Mutex

  • val takes RLock/RUnlock and inc keeps Lock/Unlock. go test -race passes all four cases.
  • Why the course test hangs before the fix: the test calls sc.mu.RLock() and defer sc.mu.RUnlock() itself, then calls sc.val. The defer sits in a loop, so the read lock stays held until Test returns (14.3). A val that calls Lock then waits for that reader forever. Measured: with Lock in val, go test -timeout 5s ends with panic: test timed out after 5s in sync.(*RWMutex).Lock.
  • The fixed version passes only because no writer is waiting. That is a recursive read lock: the test goroutine already holds RLock and val takes a second one. The sync.RWMutex doc forbids this. A waiting Lock blocks new readers, so the second RLock waits for the writer, and the writer waits for the first RLock. Measured: RLock, then a goroutine calls Lock, then RLock again gives fatal error: all goroutines are asleep - deadlock!. The course test avoids this only because wg.Wait() runs before it.
  • Writer preference is the point of that rule. Once a writer waits, new readers queue behind it, so a constant stream of readers cannot starve the writer.
  • Production note: RLock is not free. Every RLock and RUnlock does an atomic add on one shared readerCount field, so parallel readers still fight over one cache line. Measured with b.RunParallel around a one-key map read: with 1 CPU, Mutex takes 7.7 ns/op and RLock 7.7 ns/op. With 16 CPUs, Mutex takes 37.8 ns/op and RLock 16.9 ns/op. Reads get faster, but they do not scale linearly. RWMutex pays off when reads clearly outnumber writes. Benchmark your own workload before you switch. Per-device counters with many writers fit a plain Mutex, sharding, or atomic.Int64 values better.

14.5 Read/Write Mutex ReviewQuiz

Quiz:

  1. How many writers can access a RWMutex at once? 1.
  2. How many readers can access a RWMutex at once? infinite.
  3. Can readers and writers lock a RWMutex at the same time? No.

Notes:

  • "Infinite" is the course's simplification. sync/rwmutex.go caps readers at rwmutexMaxReaders = 1 << 30. Lock subtracts that value from readerCount to tell new readers that a writer is waiting. No real program comes close to the cap.
  • Concurrent reads of a map with no writer are safe. Measured: 8 goroutines ranging over the same map 10,000 times each, under -race, report no race. A single writer anywhere makes every access need the lock.
  • Writers are not starved. Measured: one writer and four goroutines that hold RLock in a tight loop. The writer completed 534,506 Lock/Unlock cycles in 1 s, because a waiting writer blocks new readers (14.4).
  • Production note: for a map that is written once and then only read, such as config or a device lookup table loaded at startup, no lock is needed at all. Publish it before you start the readers, or swap a fresh copy through atomic.Pointer[map[K]V] for hot reload. sync.Map fits keys that are written once and read many times, or goroutines that touch disjoint keys. For everything else, the sync.Map doc recommends a plain map with its own lock, for better type safety and easier upkeep of other invariants.

15.1 Generics in Go

  • getLast[T any](s []T) T returns s[len(s)-1], or the zero value from var zero T when the slice is empty. go test -race passes all four cases.
  • var zero T; return zero is the usual way to write a generic zero value. return *new(T) does the same in one line and also compiles. T{} does not work for every T, because int or *int have no composite literal.
  • The zero value is ambiguous. Measured: getLast([]int{}) and getLast([]int{0}) both print 0. Production code returns (T, bool), as a comma-ok map lookup does. The standard library has no slices.Last. slices.Max makes the opposite choice and panics on an empty slice ("It panics if x is empty").
  • Type inference: callers write getLast(v), not getLast[int](v), because T is inferred from the argument. An untyped nil argument gives the compiler nothing to infer from, so getLast(nil) fails with in call to getLast, cannot infer T and needs getLast[*int](nil) (measured).
  • The course test compares the T result with an any field (output != test.expected). That compiles because a value is comparable with an interface value its type implements. The comparison is done at run time and is true only when the dynamic type and the value both match.

15.2 Why Generics?Quiz

Quiz:

  1. Which code would generics be most likely to help with? A binary tree.
  2. Go's approach to language design is... Resist adding new features unless they're extremely important.
  3. Generics will probably be used more heavily in... Library packages.

Notes:

  • The standard library shows where generics pay off: containers and algorithms that do not care about the element type. Examples: slices and maps, cmp.Ordered, sync/atomic.Pointer[T], and the iterator types iter.Seq[V] and iter.Seq2[K, V].
  • Rule of thumb from the Go blog post "When To Use Generics" (Ian Lance Taylor): write the concrete code first, and add a type parameter only when the same logic repeats for different types. When the types differ in behavior rather than in data, use an interface. A method set gives dynamic dispatch, and a type parameter cannot replace it.
  • Production note: in application code, generics fit small helpers. Examples: a typed ring buffer for sensor samples, a Set[K comparable], or one decode-and-validate function for several message types. A device's protocol handlers differ in behavior, so they stay behind an interface.

15.3 Constraints

  • chargeForLineItem[T lineItem] returns nil, 0, errors.New("insufficient funds") when cost > balance. Otherwise it appends newItem and subtracts the cost. A cost equal to the balance goes through, which is the right edge. go test -race passes.
  • A constraint is an interface, so T can be the interface type itself. The course test passes lineItem values, so T is inferred as lineItem, not as subscription. The function body then calls GetCost through the interface as usual. A type parameter gives a different result from a plain []lineItem parameter only when the caller passes a concrete slice such as []subscription: the generic version returns []subscription, and a non-generic version would not accept it.
  • append(oldItems, newItem) writes into the caller's backing array when it has spare capacity. Measured: two calls on the same make([]int, 2, 4) history both returned [0 0 20], because the second append overwrote the first. In production, copy before you append (slices.Clip(oldItems) forces a fresh array on the next append), or document that the function takes ownership of the slice.
  • Production notes:
    • Return a sentinel, var errInsufficientFunds = errors.New("insufficient funds"), so callers can test it with errors.Is instead of comparing error strings, which the course test does.
    • Do not keep money in float64. Measured: x, y := 0.1, 0.2; x+y == 0.3 is false. The constant expression 0.1+0.2 == 0.3 is true, because untyped constants are exact, and that hides the bug in small examples. Store integer cents (int64) or use a decimal type.

15.4 Interface Type ListsQuiz

Quiz:

  1. Why might you create an interface using a type list? You know exactly which types satisfy your interface.

Notes:

  • The lesson's Ordered is word for word cmp.Ordered (Go 1.21). Import it instead of writing your own. Since Go 1.21, the built-in min and max already take any ordered type and any number of arguments, so a Min[T] helper is not needed. Measured: min(3, 1, 2) is 1.
  • ~T means "any type whose underlying type is T". Without the ~, named types are rejected. Measured with type celsius float64 against interface{ float64 }: celsius does not satisfy exact (possibly missing ~ for float64 in exact). With cmp.Ordered, lo(celsius(21.5), 19) compiles and returns 19. Domain types like celsius, deviceID or canID are why the standard constraints use ~ everywhere.
  • An interface that contains a type list is a constraint only. It cannot be the type of a variable, field or parameter. Measured: var x num gives cannot use type num outside a type constraint: interface contains type constraints. Go has no sum types, so int | float64 cannot be a runtime "either". Use a sealed interface with an unexported method, or a type switch over any.
  • A constraint can list types and methods together, for example interface{ ~int; String() string }. A type must then satisfy both, and the body can use + and < as well as the method. Measured: canID with a String method passes. type plain int fails with T (type plain) does not satisfy idLike (missing method String).

15.5 Parametric Constraints

  • biller[C customer] declares Charge(C) bill and Name() string. userBiller satisfies biller[user] and orgBiller satisfies biller[org]. go test -race passes both tests.
  • A generic interface is a family of interfaces, one for each type argument. Each instance is a separate type:
    • biller on its own is not a type. Measured: []biller{userBiller{}, orgBiller{}} gives cannot use generic type biller[C customer] without instantiation.
    • biller[user] and biller[org] do not mix. Measured: var _ biller[user] = orgBiller{} gives orgBiller does not implement biller[user] (wrong type for method Charge), with have Charge(org) bill and want Charge(user) bill.
    • So one slice cannot hold both billers. Code that must loop over every biller needs a non-generic interface (for example Name() string plus Charge(customer) bill), with a type assertion inside each Charge.
  • What the parameter buys: Charge takes the concrete user or org, not the customer interface. A wrong pairing such as an org passed to a userBiller fails to compile instead of failing a type assertion at run time. The course's testBiller[C customer](b biller[C], c C, ...) infers C from the c argument and then checks b against biller[C].
  • Production note: var _ biller[user] = userBiller{} at package level is the usual compile-time check that a type implements an interface. It costs nothing at run time and fails the build as soon as a method signature drifts.

15.6 Naming Generic TypesQuiz

Quiz:

  1. The name of a type parameter... ...can be anything, but 'T' is a common convention.

15.7 Generic Structs

  • envelope[T any] holds recipient string and payload T. createEnvelopes[T any] appends one envelope[T] per recipient and starts from []envelope[T]{}, so no recipients gives an empty, non-nil slice. go test -race passes.
  • Spec trap: "one entry per recipient, in the same order" means one envelope per element of recipients, not one per unique address. The lesson never mentions deduplication. The test checks len(envelopes) == len(recipients) and envelopes[i].recipient == recipients[i]. Deduplicating fails the count check and shifts every index after the first duplicate. Treat the function as a 1:1 map over its input, and let the caller decide whether duplicates are allowed.
  • A generic struct literal always needs its type argument (envelope[T]{...}). Only function calls infer type arguments. Inside the generic function, the type parameter T that is in scope serves as the argument.
  • The course test writes var envelopes []envelope[T] = createEnvelopes(...), which staticcheck flags as ST1023. In a test, the explicit type is a compile-time assertion that the function returns []envelope[T].
  • Production note: the payload is copied into each envelope only one level deep. Measured: with tags []string in the payload, es[0].payload.tags[0] = "CHANGED" also shows in es[1]. Before you fan one payload out to many senders, especially concurrent ones, make it immutable or deep-copy it per envelope. Otherwise one change reaches every message, and concurrent writes race.

15.8 Generic Methods

  • func (i inbox) Select[T any]() []T starts from []T{} and appends every event where the type assertion e.(T) succeeds. Order is kept, nothing matching gives an empty, non-nil slice, and i.events is only read. go test -race passes. golangci-lint v2.15.0 parses the Go 1.27 method type parameter; its only report is ST1023 in the course test.
